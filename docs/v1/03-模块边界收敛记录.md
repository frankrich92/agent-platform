# 模块边界收敛记录

## 本轮调整

本轮在不修改业务语义、不调整数据库表结构、不修改 `.apboa/` 的前提下，先完成 `infra-common` 的第一批瘦身：

- 将 `common.dto`、`common.vo` 迁入 `agent-api`，作为 REST/API 契约对象。
- 将 `common.enums` 迁入 `agent-domain`，作为领域枚举。
- 将低耦合实体迁入 `agent-domain`，包括会话、消息、账号、附件、任务、绑定关系等不直接依赖 AgentScope、Spring 或 JsonNode TypeHandler 的实体。
- 将 `SerializableEnable`、`TableConst`、`QueryDefine`、`QueryCondition` 迁入 `agent-domain`，避免迁移实体反向依赖 `infra-common`。
- 将剩余 `common.entity` 全部迁入 `agent-domain`，`infra-common/common/entity` 已清空。
- 将 `JsonNodeTypeHandler`、`ModelConfigWrapper`、`ExtendConfigHelper` 下沉到 `agent-domain`，用于兼容第一阶段 MyBatis JSON 字段映射和模型配置聚合逻辑。
- 用领域枚举 `RagMode`、`StructuredOutputReminderMode` 替代实体和 API 契约中直接暴露的 AgentScope 枚举；AgentScope runtime 在适配层转换为 `RAGMode`、`StructuredOutputReminder`。
- 移除 `JobLog` 实体上的 Spring `DateTimeFormat` 注解，避免领域对象依赖 Web 绑定能力。
- 将 `UserDetail`、`PageParams` 迁入 `agent-domain`，移除 `agent-api` 对 `infra-common` 的过渡依赖。
- 将 MyBatis 查询构造工具 `MP`、`ConditionBuilder` 下沉到 `repo-mybatis`，并让实际使用分页/查询构造的业务、管理和文件模块显式依赖 `repo-mybatis`。
- 将所有 `Mapper/BaseMapper` 接口迁入 `repo-mybatis`，并将 `ChatMessageMapper.xml`、`ChatSessionMapper.xml` 移入 `repo-mybatis/src/main/resources`，保持 mapper namespace 不变。
- 将 `admin-agent` 中的 `AgentStudioService`、`StudioConfigService` 从 MyBatis-Plus `IService/ServiceImpl` 继承中解耦，改为显式业务接口和 Mapper 委托实现。
- 将 `admin-system` 中的 `ParamsService` 从 MyBatis-Plus `IService/ServiceImpl` 继承中解耦，保留分页、删除、按 ID 查询和参数值读写的显式服务方法。
- 将 `biz-task` 中的 `QuartzInfoService`、`QuartzLogService` 从 MyBatis-Plus 通用 Service 中解耦，控制器和初始化逻辑不再调用 `lambdaQuery()`，改为 `listEnabled`、`getAgentJobByBizId` 等任务语义方法。
- 将 `infra-files` 中的 `AttachService`、`AttachLogService`、`StorageProtocolService` 从 MyBatis-Plus 通用 Service 中解耦，并将存储协议配置更新收敛为 `updateProtocolConfig`，避免控制器直接构造 `UpdateWrapper`。
- 将 `biz-knowledge` 重新上传文档时对附件的通用 `removeById` 调用改为附件服务的 `batchDeleteV2` 语义方法，减少跨模块 CRUD 泄漏。
- 将 `admin-provider` 中的 `ModelProviderService`、`ModelConfigService` 从 MyBatis-Plus 通用 Service 中解耦，保留模型分页、详情、保存、更新、删除和模型运行时读取配置的显式方法。
- 将 `admin-iam` 中的 `AccountService`、`AccountRoleService`、`SecretKeyService` 从 MyBatis-Plus 通用 Service 中解耦；账号角色控制器调用改为 `listByAccountId`、`deleteByAccountIds` 等语义方法，账号删除事务收敛到账号服务层。
- 将 `admin-capability` 中的 `SensitiveWordConfigService`、`SystemPromptTemplateService` 从 MyBatis-Plus 通用 Service 中解耦，保留分页、详情、保存、分类列表、关联 Agent 查询和运行时按 ID 读取的显式方法。
- 将 `admin-capability` 中的 `HookConfigService`、`AgentHookService` 从 MyBatis-Plus 通用 Service 中解耦，运行时 Hook 工厂保留 `listByIds` 显式读取方法，Hook 关联删除改为 `deleteByHookConfigIds`。
- 将 `admin-capability` 中的 `AgentToolService`、`SkillToolService` 从 MyBatis-Plus 通用 Service 中解耦，工具和技能绑定关系改为按 Agent、Tool、Skill 维度的显式查询和删除方法。
- 将 `admin-capability` 中的 `ToolService`、`SkillPackageService`、`AgentSkillPackageService` 从 MyBatis-Plus 通用 Service 中解耦；工具/技能包运行时读取改为 `getByToolId`、`listEnabledBriefByIds`、`listWithScripts` 等显式方法。
- 将 `admin-capability` 中 MCP 相关 `McpServerService`、`McpToolService`、`AgentMcpServerService`、`AgentMcpToolService` 从 MyBatis-Plus 通用 Service 中解耦，MCP 删除链路改为先清理工具治理和绑定关系，再删除服务器配置。
- 将 `biz-agent` 中 Agent 定义、子 Agent、A2A、ChatKey、代码执行配置/绑定、会话和消息服务从 MyBatis-Plus 通用 Service 中解耦；运行时和控制器只依赖 `getById`、`getByAgentCode`、`pageSessions`、`deleteBySessionId` 等业务语义方法。
- 将 `biz-knowledge` 中知识库配置和 Agent-知识库绑定服务从 MyBatis-Plus 通用 Service 中解耦，知识库删除链路通过 `deleteByKnowledgeIds` 清理关联并触发 Agent 重新注册。
- 当前 `source/agent-platform` 内服务层已完成第一轮 `IService/ServiceImpl` 继承清零，跨模块调用不再直接依赖 MyBatis-Plus 通用 Service 能力。
- 在 `repo-spi` 中新增 Agent/A2A/ChatKey/代码执行/知识库绑定等第一批仓储接口，并在 `repo-mybatis` 中提供 MyBatis 实现。
- 将 `biz-agent` 中 A2A、子 Agent、Agent 定义非分页 CRUD、ChatKey、代码执行配置/绑定服务改为依赖 repository SPI，减少业务服务对 Mapper 和 MyBatis Wrapper 的直接依赖。
- 将 `biz-knowledge` 中知识库配置详情/保存/更新/删除/批量读取和 Agent-知识库绑定服务改为依赖 repository SPI；分页查询仍作为过渡保留 MyBatis 查询对象。
- 将 `biz-agent` 中会话、消息、统计、Agent 定义分页和 Controller 聚合查询继续迁移到 repository SPI；分页返回通过 `RepoPage` 在业务层转换为现有 `IPage` 契约。
- 将 `biz-knowledge` 中 RAG 文档、文档分块和知识库分页迁移到 repository SPI，`RagDocumentController` 与 `LocalRagService` 不再直接依赖 Mapper。
- 将 `admin-agent` 中 Studio 配置和 Agent-Studio 绑定迁移到 repository SPI，服务实现不再直接依赖 `AgentStudioMapper`、`StudioConfigMapper`。
- 将 `admin-system` 中 Params 查询、按 key 读取、保存、删除和参数值更新迁移到 repository SPI；`ParamsController` 与 `ParamsAdapter` 不再直接构造 MyBatis 查询对象。
- 将 `biz-task` 中任务信息和任务日志持久化迁移到 repository SPI；`QuartzInfoServiceImpl`、`QuartzLogServiceImpl` 不再直接依赖任务 Mapper。
- 将 `biz-agent` 代码执行配置、`biz-knowledge` 知识库配置中的 Agent 名称聚合查询改为复用 `AgentDefinitionRepository.listByIds`，移除业务层 `JdbcTemplate` 拼 SQL。
- 将 `admin-provider` 中模型供应商、模型配置分页/CRUD/关联查询迁移到 repository SPI；模型配置与供应商删除、更新时的 Agent 重新注册查询改为 `AgentDefinitionRepository.listByModelConfigIds`。
- 将 `admin-iam` 中账号、账号角色、SecretKey 持久化迁移到 repository SPI；账号列表查询改为 DTO 语义方法，控制器和服务不再直接构造 MyBatis Wrapper。
- 将 `infra-files` 中附件、附件分片、附件日志和存储协议持久化迁移到 repository SPI；附件与存储协议控制器不再直接构造 MyBatis 查询对象。
- 将 `admin-capability` 中敏感词配置和系统提示词模板迁移到 repository SPI；分类查询、分页、CRUD 和关联 Agent 查询不再由服务层直接依赖 Mapper/JdbcTemplate。
- 将 `admin-capability` 中 Hook 配置、Agent-Hook 绑定、Tool 配置和 Agent-Tool 绑定迁移到 repository SPI；内置 Hook/Tool 启动同步、分类查询、分页和绑定清理不再由服务层直接依赖 Mapper。
- 将 `admin-capability` 中 Skill 包、Agent-Skill 绑定、Skill-Tool 绑定迁移到 repository SPI；技能导入、脚本加载、分类查询和关联 Agent 查询保留原业务语义。
- 将 `admin-capability` 中 MCP 服务器、MCP 工具、Agent-MCP 绑定、Agent-MCP-Tool 绑定迁移到 repository SPI；激活请求 CAS 更新、运行时自动降级条件更新和工具治理查询下沉到 `repo-mybatis`。
- 将 `biz-knowledge` 的 PgVector SQL 操作隔离到 `repo-mybatis` 的 `PgVectorRepository` 实现，`PgVectorStore` 仅保留向量存储业务接口适配和检索结果转换。

## 当前过渡依赖

- `agent-domain` 暂时保留 MyBatis-Plus 注解依赖，用于兼容第一阶段不改表、不改持久化映射的约束。
- `agent-domain` 暂时保留 Jackson 依赖，用于兼容 `JsonNode` 字段和 JSON TypeHandler。
- `agent-api` 当前只依赖 `agent-domain`。
- `infra-common` 暂时依赖 `agent-domain`，用于兼容仍留在 common 中的安全、工具、包装对象对领域枚举和实体的引用。
- `repo-mybatis` 当前承载 `MP`、`ConditionBuilder`、全部 MyBatis Mapper 接口和现有 Mapper XML。
- `repo-spi` 已开始承载第一批业务仓储接口；当前仍与领域实体共享包名兼容，尚未引入独立持久化模型。

## 下一轮建议

下一轮优先处理持久化边界和 infra-common 继续瘦身：

处理策略：

- JsonNode TypeHandler 相关注解后续下沉到 `repo-mybatis`，领域对象保留纯字段语义。
- `common.wrapper` 中仍依赖 AgentScope 的 `KnowledgeWrapper` 应移动到 `runtime-agentscope` 或 runtime adapter 包。
- `common.mp` 中剩余查询注解和分页参数当前位于 `agent-domain`，后续可继续评估是否拆出更独立的 API 查询契约包。
- 当前已完成 `admin-agent`、`admin-system`、`admin-provider`、`admin-iam`、`admin-capability`、`biz-agent`、`biz-knowledge`、`biz-task`、`infra-files` 的第一轮服务和持久化边界收敛；后续新增能力应默认按“控制器调用面收窄、业务语义方法替换通用 CRUD、实现层委托 repository”的节奏推进。
- 下一步应重点处理领域对象上的 MyBatis/Jackson 注解剥离、repo 层查询模型与领域模型拆分，以及 infra-common 中安全、数据库、Redis/Web 工具的继续拆分。
- `infra-common` 中安全、数据库配置、Redis/Web 工具继续迁入对应 `infra-security`、`repo-mybatis`、`infra-stream` 或 adapter 模块。
