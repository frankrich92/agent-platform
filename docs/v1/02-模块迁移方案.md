# Apboa 模块迁移方案

## 1. 背景

本方案用于指导将当前 `.apboa` 源码转换为新的 Maven 多模块架构。参考结构不是简单照搬，而是结合 Apboa 当前已有能力进行重新整理，目标是让代码从现有的 `common/core/biz/console` 模式，演进为更清晰的“领域 + API 契约 + 业务应用 + 管理后台 + 平台能力 + Agent 运行时 + 存储适配 + 启动装配”结构。

当前 Apboa 的主要问题是：

- `common` 过重，同时包含实体、DTO、VO、鉴权、MyBatis、Redis、Web 配置、AgentScope SDK、模型 SDK、RAG SDK。
- `core` 职责过多，混合了 Agent 装配、模型、工具、MCP、RAG、Hook、Skill、Workspace、AGUI 注册。
- `biz/agent` 同时承担 Agent 定义、会话、消息、统计、工作空间、代码执行配置等多类职责。
- Controller、业务服务、运行时适配和基础设施适配边界不够清晰。

新的模块结构应优先解决依赖方向和边界问题，而不是只做目录重命名。

## 2. 固定工程约束

本次迁移采用以下固定决策，后续实施不得再临时变更：

- 后端 Maven 多模块新代码统一落在 `source/agent-platform/`。
- 前端从后端 Maven 工程中抽离，独立落在 `source/agent-platform-ui/`。
- Java 包名前缀统一调整为 `com.htam.agent`。
- Maven `groupId` 统一使用 `com.htam.agent`。
- 后端根父工程 `artifactId` 使用 `agent-platform`。
- `.apboa/` 永远只作为只读参考目录，任何迁移动作不得修改其中内容。
- 第一阶段优先保证结构迁移、包名统一、接口兼容和可启动，不同步做业务语义重构。
- 第一阶段数据库表结构保持不变，只迁移代码。

### 2.1 目标目录布局

```text
source/
├── agent-platform/                 # 后端 Maven 多模块工程
│   ├── agent-domain
│   ├── agent-api
│   ├── agent-biz
│   ├── agent-admin
│   ├── agent-infra
│   ├── agent-runtimes
│   ├── agent-repo
│   ├── agent-adapter
│   └── agent-boot
│
└── agent-platform-ui/              # 前端独立工程，不进入后端 Maven reactor
```

### 2.2 Maven 坐标与包名规范

```text
groupId: com.htam.agent
root artifactId: agent-platform
java base package: com.htam.agent
```

模块内包名按职责继续细分，例如：

- `com.htam.agent.domain`
- `com.htam.agent.api`
- `com.htam.agent.biz.chat`
- `com.htam.agent.infra.security`
- `com.htam.agent.runtime.agentscope`
- `com.htam.agent.repo.mybatis`
- `com.htam.agent.adapter.rest`
- `com.htam.agent.boot`

原 Apboa 包名前缀 `com.hxh.apboa` 不作为新工程包名前缀沿用；迁移代码应按新职责重新落到 `com.htam.agent` 下。

### 2.3 第一阶段兼容策略

第一阶段只调整工程结构、模块边界、包名和依赖方向，外部调用契约优先保持兼容：

- REST 路径先保持 Apboa 当前路径，降低前端迁移压力。
- AGUI 路径先保持兼容 `/apboa/agui`，或通过配置映射到新路径。
- WebSocket endpoint 第一阶段保持兼容。
- 数据库表结构第一阶段保持不变，只迁移代码；不重命名表、不重命名字段、不调整字段类型、不新增迁移脚本。
- 前端独立放在 `source/agent-platform-ui/`，通过配置访问后端 API，不依赖后端 Maven 打包。

## 4. 模块职责说明

### 4.1 agent-domain

纯领域模型模块，放置平台核心领域对象。

建议内容：

- Entity/Aggregate
- Value Object
- Enum
- Domain Event
- Domain Service interface

迁移来源：

- `.apboa/common/src/main/java/com/hxh/apboa/common/entity`
- `.apboa/common/src/main/java/com/hxh/apboa/common/enums`
- 部分 `key`、`message`、`wrapper` 中与领域强相关的对象

约束：

- 不依赖 Spring。
- 不依赖 MyBatis。
- 不依赖 AgentScope。
- 不依赖 Web、Redis、数据库和第三方模型 SDK。

迁移初期如成本较高，可以短期保留少量 MyBatis 注解，但应作为过渡状态，后续移动到 `repo-mybatis` 的持久化对象或映射层。

### 4.2 agent-api

API 契约模块，放置接口请求、响应、DTO、VO 和对外 facade 契约。

建议内容：

- REST request/response DTO
- VO
- OpenAPI contract
- 内部 SDK interface
- 业务 facade interface

迁移来源：

- `.apboa/common/dto`
- `.apboa/common/vo`
- 对外暴露接口需要复用的 request/response 对象

约束：

- 不放 Controller 实现。
- 不放 Service 实现。
- 尽量不依赖具体 runtime 类型，例如 AgentScope 的 `ReActAgent`、`Model`、`AguiEvent`。

### 4.3 agent-biz

用户侧业务应用模块，负责平台核心业务闭环。

#### biz-agent

负责 Agent 定义、发布、版本、配置聚合、能力绑定。

迁移来源：

- `.apboa/biz/agent` 中的 Agent Definition 相关能力
- `agent_definition`
- `agent_tools`
- `agent_mcp_servers`
- `agent_mcp_tool`
- `agent_skill_packages`
- `agent_knowledge_bases`
- `agent_hooks`
- `agent_sub_agents`
- `agent_studio`
- `agent_code_execution`
- `agent_a2a`

#### biz-session

负责会话和消息树，不直接关心 AgentScope。

迁移来源：

- `ChatSessionService`
- `ChatMessageService`
- `chat_session`
- `chat_message`

职责：

- 会话创建、查询、分页、置顶、删除。
- 消息树保存。
- 当前分支 `current_message_id` 管理。
- 重新生成与分支切换。

#### biz-chat

负责一次对话运行的应用层编排。

职责：

- 串联 session、agent、runtime、stream。
- 管理一次用户请求到 Agent 运行结果的业务流程。
- 屏蔽具体 AgentScope runtime。

Apboa 当前聊天逻辑分散在前端 AGUI 调用、`ChatSessionServiceImpl` 和 `AguiRequestProcessor` 中，迁移后应由 `biz-chat` 形成清晰应用服务。

#### biz-memory

负责记忆业务抽象。

建议保持 Core，因为记忆已经影响对话主链路。实现可拆分：

- Core：记忆开关、记忆策略、会话记忆元数据。
- Ext：长期记忆、压缩记忆、外部记忆库适配。

迁移来源：

- Agent 记忆配置字段。
- AgentScope Session 持久化相关业务语义。
- AutoContextMemory 配置映射。

#### biz-execution

负责执行类业务能力。

迁移来源：

- 代码执行配置。
- 工作空间业务。
- 工具执行确认。
- Agent ChatKey 中与运行调用相关的部分。

职责：

- 代码执行环境配置。
- 工作空间生命周期。
- 工具调用人工确认。
- 执行记录和状态。

#### biz-knowledge

负责知识库和 RAG 业务。

迁移来源：

- `.apboa/biz/knowledge`
- `.apboa/biz/rag`
- RAG 文档上传、解析、分块、重建、检索测试、分块编辑

说明：

Apboa 的知识库/RAG 不应只归为平台能力，它包含明显业务流程，例如文档状态、知识库配置、文档重处理、分块维护、检索测试和后续权限过滤，因此建议单独作为 Core 业务模块。

#### biz-task

负责定时任务和 Agent 周期调度。

迁移来源：

- `.apboa/job`

可标记为 Ext。如果内部已有统一调度平台，后续可替换为外部调度触发。

#### biz-workflow

负责可视化工作流和多 Agent 编排。

当前 Apboa Roadmap 中包含可视化编排，建议作为 Ext 预留。

### 4.4 agent-admin

管理后台业务模块，负责配置管理、后台页面 API 和治理流程。

#### admin-iam

迁移来源：

- `.apboa/biz/account`
- `.apboa/biz/sk`

职责：

- 账号、角色、登录。
- Secret Key。
- 内部 SSO/IAM 适配。

#### admin-agent

负责 Agent 后台管理接口。

职责：

- Agent CRUD。
- Agent 配置编辑。
- Agent 启禁用。
- Agent 版本管理、发布、下线。

#### admin-capability

负责能力配置管理。

迁移来源：

- `.apboa/biz/tool`
- `.apboa/biz/mcp`
- `.apboa/biz/skill`
- `.apboa/biz/hook`
- `.apboa/biz/sensitive`
- `.apboa/biz/prompt`

职责：

- Tool 管理。
- MCP 服务管理和工具目录同步。
- Skill 管理和导入。
- Hook 管理。
- Prompt 模板管理。
- 敏感词管理。

#### admin-provider

负责模型、Embedding、向量库、存储等 Provider 配置管理。

迁移来源：

- `.apboa/biz/model`
- 部分知识库和 RAG Provider 配置。

#### admin-knowledge

负责知识库后台管理。

迁移来源：

- 知识库配置页面。
- RAG 文档管理页面。

#### admin-task

负责定时任务后台管理。

迁移来源：

- `.apboa/job/controller`

#### admin-system

负责系统参数和基础配置。

迁移来源：

- `.apboa/biz/params`
- 系统参数配置。

#### admin-audit

负责审计查询和审计规则。

当前 Apboa 缺少统一审计模块，建议作为新模块补齐。

### 4.5 agent-infra

平台基础设施层，放置业务无关但平台通用的能力抽象和基础实现。

#### infra-common

迁移来源：

- `.apboa/common/r`
- `.apboa/common/exception`
- `.apboa/common/util` 中不依赖外部框架的基础工具
- 通用常量

职责：

- 统一返回结构。
- 通用异常。
- 基础工具类。
- 通用常量。

#### infra-security

迁移来源：

- `.apboa/common/config/auth`
- `.apboa/security/script-security`

职责：

- 认证注解。
- 权限检查。
- Token 工具。
- 脚本安全检查 SPI。
- 动态代码安全策略。

#### infra-stream

迁移来源：

- `.apboa/cluster`
- `.apboa/websocket` 中偏平台事件和推送能力的部分
- AGUI 事件抽象

职责：

- 平台事件模型。
- SSE/WebSocket/Redis PubSub 抽象。
- 运行事件广播。
- 多节点消息分发。

#### infra-capability

迁移来源：

- `.apboa/core/tool` 的抽象部分
- `.apboa/core/mcp` 的 SPI 部分
- `.apboa/core/skill` 的抽象部分
- `.apboa/core/hook` 的抽象部分

职责：

- Tool SPI。
- Skill SPI。
- MCP SPI。
- Hook SPI。
- Capability registry。

约束：

- 不放 CRUD 管理逻辑。
- 不放具体 AgentScope 装配逻辑。
- 不直接变成新的 `common`。

#### infra-provider

迁移来源：

- `.apboa/core/model`
- `.apboa/core/rag/embedding`
- 存储、向量库、模型供应商抽象

职责：

- LLM Provider 抽象。
- Embedding Provider 抽象。
- Vector Provider 抽象。
- Storage Provider 抽象。
- 内部模型网关适配。

#### infra-files

迁移来源：

- `.apboa/biz/resource`
- `.apboa/core/workspace`
- `.apboa/common/util/ZipExtractUtils`

职责：

- 附件。
- 分片上传。
- 工作空间文件。
- 本地/S3/FTP 存储协议。
- 路径安全校验。
- ZIP 安全解压。

#### infra-observability

职责：

- Trace。
- Metrics。
- Audit Event SPI。
- 运行日志上下文。
- Agent 调用、工具调用、MCP 调用、知识命中等观测事件。

当前 Apboa 缺少完整观测模块，建议新增。

#### infra-orchestration

职责：

- 规划。
- 多 Agent 编排。
- Workflow 引擎适配。

可作为 Ext。

### 4.6 agent-runtimes

Agent 运行时适配层，封装具体 Agent 引擎。

#### runtime-spi

定义业务层可依赖的运行时接口。

建议接口：

- AgentRuntime
- AgentRunRequest
- AgentRunResult
- AgentEvent
- AgentFactory
- RuntimeSession
- ToolExecutionContext

业务层只依赖 `runtime-spi`，不要直接依赖 AgentScope。

#### runtime-agentscope

迁移来源：

- `.apboa/core/agent`
- `.apboa/core/agui`
- `.apboa/console/src/main/java/io/agentscope/...`
- `.apboa/core/model` 中与 AgentScope `Model` 绑定的部分
- `.apboa/core/tool` 中与 AgentScope `Toolkit` 绑定的部分
- `.apboa/core/mcp` 中与 AgentScope MCP Tool 绑定的部分
- `.apboa/core/hook` 中与 AgentScope Hook 绑定的部分
- `.apboa/core/skill` 中与 AgentScope SkillBox 绑定的部分

职责：

- ReActAgent 装配。
- A2A Agent 装配。
- AgentScope Session 持久化。
- AgentScope 事件转换为平台事件。
- AgentScope Tool/Skill/Hook/MCP 适配。

#### runtime-sandbox

负责代码执行沙箱。

迁移来源：

- 代码执行配置。
- `script-security` 的执行前检查能力。
- 后续容器沙箱适配。

可作为 Ext，但企业内部上线前建议尽早补齐。

#### runtime-hermes

预留其他 Agent Runtime，可暂时 Off。

### 4.7 agent-repo

持久化适配层。

#### repo-spi

定义仓储接口，供业务层依赖。

建议按聚合拆分：

- AgentRepository
- SessionRepository
- MessageRepository
- ModelConfigRepository
- CapabilityRepository
- KnowledgeRepository
- RagDocumentRepository
- TaskRepository
- AccountRepository

#### repo-mybatis

迁移来源：

- 当前各 biz 模块 Mapper。
- `.apboa/common/config/mybatis`
- MyBatis TypeHandler。

职责：

- MyBatis-Plus 实现。
- Mapper XML。
- PO 与领域对象转换。

#### repo-vector

迁移来源：

- `.apboa/core/rag/store`
- pgvector/milvus/qdrant 适配。

职责：

- 向量写入。
- 向量检索。
- 向量删除。
- 索引维护。

### 4.8 agent-adapter

入口适配层，用于隔离传输协议和业务逻辑。

#### adapter-rest

迁移来源：

- 当前所有 Controller。

职责：

- REST Controller。
- 参数校验。
- DTO 转换。
- 调用 biz/admin 应用服务。

#### adapter-websocket

迁移来源：

- `.apboa/websocket`

职责：

- WebSocket endpoint。
- WebSocket 鉴权。
- 连接管理。
- 消息推送适配。

#### adapter-agui

迁移来源：

- `.apboa/core/agui`
- `.apboa/console/src/main/java/io/agentscope/spring/boot/agui`

职责：

- AGUI SSE endpoint。
- AGUI 请求到 runtime-spi 的适配。
- AGUI Event 到 infra-stream 的转换。

### 4.9 agent-boot

启动装配模块。

迁移来源：

- `.apboa/console`
- `Application.java`
- `application.yml`
- `application-dev.yml`
- 启动装配配置

职责：

- Spring Boot 启动入口。
- Profile 配置。
- 模块自动装配。
- 外部化配置。

### 4.10 agent-platform-ui

前端模块。

迁移来源：

- `.apboa/ui`

说明：

前端固定抽离为独立工程 `source/agent-platform-ui/`，不进入后端 Maven reactor，不由后端 Maven 打包。前端通过环境配置访问后端 REST、AGUI 和 WebSocket 接口。

## 6. 目标依赖方向

依赖方向必须严格控制，否则迁移后仍会形成新的大模块和循环依赖。

```text
agent-boot
  -> agent-adapter/*
  -> agent-admin/*
  -> agent-biz/*
  -> agent-runtimes/*
  -> agent-infra/*
  -> agent-repo/*

agent-adapter/*
  -> agent-api
  -> agent-biz/*
  -> agent-admin/*

agent-admin/*
  -> agent-biz/*
  -> agent-api
  -> agent-domain

agent-biz/*
  -> agent-domain
  -> agent-api
  -> repo-spi
  -> runtime-spi
  -> platform-*

runtime-agentscope
  -> runtime-spi
  -> infra-capability
  -> infra-provider
  -> infra-stream
  -> infra-files
  -> agent-domain

repo-mybatis
  -> repo-spi
  -> agent-domain

repo-vector
  -> repo-spi
  -> infra-provider
  -> agent-domain

agent-domain
  -> no Spring / no MyBatis / no AgentScope
```

`source/agent-platform-ui/` 是独立前端工程，不参与上述后端 Maven 依赖图。

## 7. 关键设计约束

### 7.1 biz-chat 必须单独拆出

Apboa 当前聊天链路跨越前端、`ChatSessionServiceImpl`、`AguiRequestProcessor`、AgentScope Session。迁移后 `biz-chat` 应负责一次对话运行的应用层编排，业务层通过 `runtime-spi` 调用具体运行时。

### 7.2 biz-session 只管会话和消息树

`biz-session` 负责 `chat_session`、`chat_message`、消息分支、分页、置顶、删除，不直接依赖 AgentScope。

### 7.3 biz-agent 管 Agent 定义和能力绑定

Agent 定义、能力绑定、启用状态、版本、发布流程都归 `biz-agent`。运行时装配不放在 `biz-agent`，而放到 `runtime-agentscope`。

### 7.4 runtime-agentscope 封装所有 AgentScope 细节

业务层只能依赖 `runtime-spi`。不要让 `ReActAgent`、`Model`、`Toolkit`、`AguiAgentRegistry` 等 AgentScope 类型进入 biz 或 api。

### 7.5 infra-capability 放抽象，不放管理业务

Tool、MCP、Skill、Hook 的运行抽象和注册机制放在 `infra-capability`。配置管理、CRUD、导入、审批放在 `admin-capability`。

### 7.6 infra-provider 统一模型和向量 Provider

OpenAI、DashScope、Anthropic、Ollama、Gemini、Embedding Provider、向量库 Provider 都应从当前 `core/model` 和 `core/rag` 中拆出。

### 7.7 repo-spi 先定义仓储接口

业务层不直接依赖 MyBatis Mapper。Mapper 和 MyBatis-Plus 实现放在 `repo-mybatis`。这样后续替换存储技术或接入内部数据规范时影响面更小。

### 7.8 新源码目录和包名前缀固定

后端新源码只能落在 `source/agent-platform/`。前端新源码只能落在 `source/agent-platform-ui/`。新增 Java 代码包名必须以 `com.htam.agent` 开头，禁止继续使用 `com.hxh.apboa` 作为新工程包名前缀。

## 8. 推荐迁移顺序

### 阶段一：工程骨架与版本基线

1. 在 `source/agent-platform/` 建立后端父工程。
2. 建立统一 BOM 或 `agent-dependencies`。
3. 统一 Java、Spring Boot、AgentScope、MyBatis-Plus 等后端版本号。
4. 建立后端模块空壳和 Maven 聚合结构，`groupId` 固定为 `com.htam.agent`。
5. 建立独立前端工程 `source/agent-platform-ui/`，不加入后端 Maven reactor。

### 阶段二：迁移领域和 API

1. 迁移 `agent-domain`：实体、枚举、领域对象。
2. 迁移 `agent-api`：DTO、VO、请求响应对象。
3. 处理包名和依赖方向。
4. 短期允许部分兼容代码，确保可编译。

### 阶段三：拆平台基础能力

1. 拆 `infra-common`。
2. 拆 `infra-security`。
3. 拆 `infra-stream`。
4. 拆 `infra-files`。
5. 拆 `infra-provider`。
6. 拆 `infra-capability`。

### 阶段四：建立持久化层

1. 建 `repo-spi`。
2. 迁移 MyBatis Mapper 到 `repo-mybatis`。
3. 迁移 MyBatis 配置、TypeHandler、分页插件。
4. 迁移向量存储到 `repo-vector`。

### 阶段五：拆业务模块

1. 拆 `biz-agent`。
2. 拆 `biz-session`。
3. 拆 `biz-chat`。
4. 拆 `biz-execution`。
5. 拆 `biz-knowledge`。
6. 拆 `biz-task`。

### 阶段六：拆运行时

1. 定义 `runtime-spi`。
2. 迁移 `runtime-agentscope`。
3. 将 AgentScope 相关类型限制在 runtime 内。
4. AGUI、Tool、MCP、Skill、Hook、Knowledge 等运行适配统一收敛。

### 阶段七：拆入口适配层

1. 迁移 Controller 到 `adapter-rest`。
2. 迁移 WebSocket endpoint 到 `adapter-websocket`。
3. 迁移 AGUI SSE endpoint 到 `adapter-agui`。

### 阶段八：启动装配与验证

1. 迁移 `agent-boot`。
2. 接入配置文件。
3. 启动全量模块。
4. 跑通登录、Agent 配置、Chat、Tool、MCP、RAG、WebSocket、定时任务。

### 阶段九：前端迁移

1. 前端固定迁移到 `source/agent-platform-ui/`。
2. 后端接口稳定前，前端优先通过环境变量和代理配置访问兼容路径。
3. 后端接口稳定后，再调整 API 路径、菜单权限和前端模块命名。
4. 前端独立执行安装、构建和发布，不依赖后端 Maven 打包。

## 9. 验收标准

### 9.1 后端验收

- 在 `source/agent-platform/` 可执行 Maven 全量构建。
- 新增 Java package 均以 `com.htam.agent` 开头。
- 后端 Maven reactor 不包含 `source/agent-platform-ui/`。
- REST、AGUI、WebSocket 第一阶段保持兼容访问。
- 数据库表结构与迁移前保持一致。
- `.apboa/` 无任何变更。

### 9.2 前端验收

- 在 `source/agent-platform-ui/` 可独立安装依赖和构建。
- 前端通过配置访问后端 API，不依赖后端 Maven 打包。
- 第一阶段确认现有 REST、AGUI、WebSocket 路径可兼容访问。

## 10. 迁移后的收益

- `agent-domain` 纯净，后续可独立复用。
- 业务层不再直接依赖 AgentScope。
- 平台能力可替换，例如模型网关、沙箱、向量库、WebSocket、审计系统。
- 后台管理和用户侧业务边界更清楚。
- `common` 和 `core` 大模块被拆解，降低循环依赖风险。
- 更适合对接内部 IAM、模型网关、密钥系统、审计系统和运维规范。

## 11. 结论

以参考结构为基础转换 Apboa 是可行的，但需要针对 Apboa 当前能力增加三个关键模块：

- `biz-knowledge`：Apboa 的 RAG/知识库是核心业务，不应只算平台能力。
- `infra-files`：附件、工作空间、存储协议是 Agent 执行的重要基础设施。
- `agent-adapter`：REST、WebSocket、AGUI 应从业务和 runtime 中剥离出来。

最终目标是将 Apboa 从当前的“功能模块堆叠”整理为“领域 + API 契约 + 业务应用 + 管理后台 + 平台能力 + 运行时 + 存储适配 + 启动装配”的后端架构，并将前端独立为 `source/agent-platform-ui/` 工程，为后续统一内部技术栈、版本号和平台治理能力打基础。
