# 历史归档文档可吸收内容分析

日期：2026-05-22

## 1. 调研结论

`docs/历史归档文档/` 中可复用价值最高的不是旧工程路径或旧版本基线，而是三类内容：

- 产品与平台边界：从“通用聊天应用”演进到“企业内部 Agent 中台”的定位、用户角色、Agent 库、能力治理、任务中心、工作流和运行观测。
- 运行链路与治理原则：AgentScope Java 作为普通 Chat / ReAct 执行底座，AgentScope Runtime Java 作为高风险沙箱候选底座，Hermes 仅作为 API / Run / Capability / AI Native 方法参考。
- 工程交付方法：小工程切片、contract slice、owned modules / files、L0-L5 验收等级、Playwright 真实 E2E、`testRunId` 数据隔离、ADR 和任务交接模板。

需要明确改写后再吸收的内容也很多：

- 归档中的 `source/htam-agent-platform`、`source/v3-agent-platform`、`source/v3-agent-platform-ui` 不再适用；当前落点必须是 `source/agent-platform/` 和 `source/agent-platform-ui/`。
- 归档 V3 的 `agent-platform/platform-*` 模块名不适用；当前工程对应为 `agent-infra/infra-*`，例如 `platform-capability` 应映射到 `infra-capability`。
- 归档中的 Spring Boot 4、Maven 4 RC、Element Plus、PostgreSQL + R2DBC 等结论不能直接采用；当前项目已按 Apboa / 内部基线使用 Spring Boot 3.4.9、Maven 3.9.12、Vue 3 + Ant Design Vue，并要求第一阶段数据库表结构保持不变。
- V1/V2 自研阶段提出的 `agent_session`、`agent_message`、`agent_message_part` 等表结构不能直接替换 Apboa 的 `chat_session`、`chat_message`、`agentscope_sessions`；可吸收其 typed parts、Run、Span、SSE checkpoint 等语义，后续通过兼容表或新表增量设计。

## 4. 可直接吸收的内容

### 4.1 产品定位与能力分层

可吸收点：

- 当前平台应定位为企业内部 Agent 中台，而不是单一 Chat 页面。
- Agent 是可复用资产，应沉淀定义、版本、状态、负责人、标签、能力边界、可见范围和授权关系。
- 用户侧与管理侧应分离：业务用户使用 Agent / Chat / Task / Workflow，管理员配置 Agent / Provider / Capability / IAM / Audit。
- 后续能力应按阶段进入：`chat-minimal`、`admin-config`、`task-center`、`workflow-sequential`、`external-agent`、`hardening-ci`、`input-ocr`。

建议落点：

| 内容 | 当前落点 |
| --- | --- |
| 产品范围和阶段切片 | `docs/v2/` 后续正式规划文档 |
| Agent 库用户侧能力 | `source/agent-platform/agent-biz/biz-agent` |
| 管理侧 Agent 配置 | `source/agent-platform/agent-admin/admin-agent` |
| Provider 管理 | `source/agent-platform/agent-admin/admin-provider`、`agent-infra/infra-provider` |
| Capability 管理 | `source/agent-platform/agent-admin/admin-capability`、`agent-infra/infra-capability` |
| 任务中心 | `source/agent-platform/agent-biz/biz-task`、`agent-admin/admin-task` |
| 工作流 | `source/agent-platform/agent-biz/biz-workflow`、`agent-infra/infra-orchestration` |

注意：归档中的管理侧 `admin-workflow` 当前不存在，不应擅自新增；如果后续工作流管理复杂度上升，再通过正式设计决定新增模块还是归入现有管理模块。

### 4.2 AgentScope / Runtime / Hermes 取舍

可吸收点：

- 普通 Chat 和低风险 ReAct 能力优先复用 `agentscope-java`，平台不自研 ReAct 循环、MCP 调用执行引擎或 Skill 加载循环。
- Shell、Python、Browser 自动化、文件写入、系统命令等高风险动作应进入 `runtime-sandbox` 或被拒绝，不能进入普通 `runtime-agentscope`。
- Hermes 可作为 API、Run、Capability、外部 Agent adapter 和 AI Native 方法参考；`runtime-hermes` 保留占位即可，不作为默认执行底座。

建议落点：

| 内容 | 当前落点 |
| --- | --- |
| Runtime Java 契约 | `agent-runtimes/runtime-spi` |
| AgentScope 适配 | `agent-runtimes/runtime-agentscope` |
| 高风险执行 | `agent-runtimes/runtime-sandbox`、`agent-infra/infra-security` |
| Hermes 占位 / 外部 Agent 参考 | `agent-runtimes/runtime-hermes` |
| 能力裁剪和运行路由 | `agent-infra/infra-capability` |

吸收时应保留当前 Apboa 已有的 ReActAgent 装配价值：模型、Prompt、Tool、MCP、Skill、Knowledge、Hook、Memory、Workspace 和 AGUI 注册链路已经存在，当前工作应优先做模块边界收敛和平台治理补强，而不是重写执行引擎。

### 4.3 API、SSE 与 Runtime 契约思想

可吸收点：

- 前端只依赖平台 API / SSE，不直接依赖 AgentScope 原始事件、Hermes 原始事件或模型厂商原始协议。
- SSE event 应有稳定 envelope，至少包含 `eventId`、`eventType`、`sequence`、`runId`、`sessionId`、`messageId`、`traceId`、`timestamp`、`payload`。
- RuntimeEvent 和 SSE event 不要求一一对应，但映射后必须保留 run / span / trace / sequence 关系。
- 流式链路应支持 heartbeat、取消、失败、终态、`Last-Event-ID` 恢复和未知事件兼容。
- 错误码应稳定追加，不随意删除、重命名或改变既有语义。

建议落点：

| 内容 | 当前落点 |
| --- | --- |
| HTTP DTO、SSE DTO、错误结构 | `agent-api` |
| REST / AGUI / WebSocket 接入 | `agent-adapter/adapter-rest`、`adapter-agui`、`adapter-websocket` |
| RuntimeEvent Java 契约 | `agent-runtimes/runtime-spi` |
| SSE envelope、sequence、checkpoint 语义 | `agent-infra/infra-stream` |
| Chat 主流程编排 | `agent-biz/biz-chat` |

需要改写点：

- 归档 V2 / V3 的接口路径不应直接覆盖 Apboa 当前 REST / AGUI / WebSocket 兼容路径。第一阶段应保持 Apboa 外部契约兼容，再逐步新增 v2 风格契约。
- 归档的两步 `POST /api/chat/send` + `GET /api/chat/{runId}/stream` 可作为新接口目标形态，但不能破坏当前 AGUI 链路。

### 4.4 数据、安全与审计原则

可吸收点：

- 默认拒绝，显式授权。
- Agent 可见范围、用户授权、能力授权和运行风险必须分开建模；标签只做检索和展示，不替代权限或能力授权。
- `traceId` 应贯穿 HTTP、SSE、RuntimeEvent、Run / Span、Audit。
- 高风险工具、外部 Agent、Provider 配置、权限变更、Capability 审核必须审计。
- 普通用户只看脱敏摘要；工具原始参数、MCP 请求、外部响应、密钥引用、OCR 原文等敏感数据必须按权限展示。
- 所有 E2E 数据应带 `testRunId`，清理只能按同一 `testRunId` 清理，不允许模糊清理真实数据。

建议落点：

| 内容 | 当前落点 |
| --- | --- |
| 领域状态、枚举、值对象 | `agent-domain` |
| 仓储端口 | `agent-repo/repo-spi` |
| MyBatis 实现 | `agent-repo/repo-mybatis` |
| 向量存储 | `agent-repo/repo-vector` |
| 安全与脚本安全 | `agent-infra/infra-security` |
| 审计与观测 | `agent-infra/infra-observability`、`agent-admin/admin-audit` |

需要改写点：

- 归档中的 `agent_run`、`agent_span`、`agent_message_checkpoint` 等表可以作为未来观测模型参考，但第一阶段不能直接替换 Apboa 表结构。
- 当前 Apboa 已有 `chat_session`、`chat_message` 消息树和 `agentscope_sessions`，应先围绕这些表做兼容迁移和边界收敛。

### 4.5 Chat 体验与前端工程经验

可吸收点：

- Chat 工作台应包含会话列表、Agent 选择、消息区、输入区、停止生成、重新生成、编辑重发、运行状态和执行详情。
- thinking 与最终回复应分区展示；无 thinking 时不展示空区域。
- 流式生成中同会话应有互斥或排队策略，服务端仍应有 `SESSION_BUSY` 兜底。
- 长会话需要分页 / 游标加载；上下文组装不能依赖前端已加载消息。
- Markdown、代码高亮、表格、复制、运行详情抽屉、会话搜索 / 重命名 / 收藏 / 导出属于成熟 Chat 体验的高价值增强。
- SSE 客户端宜使用 fetch + ReadableStream / AbortController，以便携带认证头、取消和恢复信息。

建议落点：

| 内容 | 当前落点 |
| --- | --- |
| Chat 工作台 | `source/agent-platform-ui/` |
| 前端状态管理 | `source/agent-platform-ui/src` 下现有 Pinia / store 体系 |
| SSE client | `source/agent-platform-ui/src` 中 API / composable / service 层 |
| 执行详情 | 后端 `biz-execution` + 前端执行详情页面或抽屉 |

需要改写点：

- 归档 V1/V2 以 Element Plus 为基线，当前前端已使用 Ant Design Vue，UI 吸收时只吸收交互和状态模型，不迁移组件库。
- 归档 V1 的“前端排队消息不落库”只适合轻量 Chat；当前 Agent 平台应优先由后端掌握权威 Run、Message 和失败态。

### 4.6 工程交付与文档治理方法

可吸收点：

- 用小工程切片推进，不一次性冻结完整 Agent 中台。
- 每个小工程先冻结 contract slice，再并行开发。
- 每个任务明确 owned modules / owned files、禁止修改范围、目标验收等级和验证命令。
- 契约细化先写入任务目录 `contract-notes.md`，再由主 Agent / Review Agent 统一决定是否合入正式文档。
- L0-L5 验收等级可直接吸收：
  - L0 文档 / 静态检查
  - L1 单元测试
  - L2 模块集成测试
  - L3 API / SSE E2E
  - L4 Playwright UI E2E
  - L5 真实 LLM / AgentScope / DB / SSE / 前端链路

建议落点：

| 内容 | 当前落点 |
| --- | --- |
| v2 小工程目录 | `docs/v2/工程迭代/`，后续需要时创建 |
| ADR / 任务单 / 测试报告模板 | 可从归档 `v3-agent中台/templates/` 改写后放入 `docs/v2/templates/` |
| E2E 规范 | `source/e2e_test/` 现有测试体系和未来前端 Playwright 目录 |
| 总追踪表 | 可在后续建立 `docs/v2/RTK.md` |

## 5. 需要改写吸收的内容

### 5.1 V1 / V2 对话数据模型

V1 / V2 的 `agent_session`、`agent_message`、`agent_message_part` 对 typed parts 和 thinking / text 分段有参考价值，但当前 Apboa 已使用 `chat_session`、`chat_message` 消息树：

- `parent_id`、`path`、`depth` 支持重新生成、分支切换和当前分支续聊。
- `chat_session.current_message_id` 表达当前分支叶子节点。
- AgentScope 状态由 `agentscope_sessions` 承载。

因此当前应吸收“消息分段、运行观测、最终内容收敛、错误状态”的语义，而不是直接迁移旧表。

建议：

- 短期：在现有 `chat_message` 内容结构和状态字段范围内承载 text / thinking / tool / error 语义。
- 中期：如需要精确 checkpoint / chunk 回放，再新增兼容的流式事件或 checkpoint 表，不能破坏既有会话消息表。
- 长期：Run / Span / ToolCall 独立模型成熟后，再决定是否引入专门表。

### 5.2 R2DBC / PostgreSQL 流式 checkpoint

归档 V3 选择 MyBatis-Plus + R2DBC，面向 PostgreSQL SSE 高频 checkpoint。当前 Apboa 基线是 MySQL + MyBatis-Plus + Redis + pgvector，第一阶段仍保持原表结构。

建议：

- 先吸收“逐 token 不用阻塞 CRUD 写入、checkpoint 幂等、final flush 可观测、断线恢复”的原则。
- 不直接引入 R2DBC 作为当前门禁。
- 如果未来需要高频流式持久化，可先在 `agent-infra/infra-stream` 和 `agent-repo/repo-spi` 定义端口，再评估 MySQL / Redis Stream / R2DBC / 消息队列的实现选择。

### 5.3 input-ocr

归档 V3 的 input-ocr 设计有前瞻性：图片、扫描页、文件内嵌图片通过受控 OCR / input-preprocessor 转为派生上下文，非多模态主模型不直接接收图片原件。

当前项目已有 `infra-files`、`biz-knowledge`、`repo-vector` 等基础模块，可吸收以下原则：

- OCR 是 capability，不是前端直连模型。
- 附件、派生上下文、OCR 文本和结构化识别结果都按用户输入数据治理。
- OCR provider / model 通过 `admin-provider` / `infra-provider` 配置，不在业务代码硬编码。
- 未授权、文件过大、不支持、provider 不可用时返回明确错误。

建议落点：

- 短期仅在文档登记为后续小工程，不进入 Apboa 第一阶段迁移。
- 未来可先归入 `infra-files` + `infra-capability` + `infra-provider` + `biz-chat`，必要时再评估新增独立 `infra-input`。

## 6. 暂不建议吸收的内容

| 内容 | 不建议直接吸收原因 |
| --- | --- |
| `source/htam-agent-platform`、`source/v3-agent-platform` 路径 | 与当前仓库落点冲突 |
| Spring Boot 4.0.x / Maven 4 RC 工具链结论 | 当前项目已按 Apboa / 内部基线使用 Spring Boot 3.4.9、Maven 3.9.12 |
| Element Plus 前端基线 | 当前前端使用 Ant Design Vue |
| V1 `X-App-Code -> userCode` 作为长期鉴权 | 只能作为历史 mock 思路；当前应对齐 Apboa 账号、Token、ChatKey 和后续内部 IAM |
| V1/V2 新建表替换现有会话消息表 | 第一阶段数据库表结构保持不变 |
| Hermes 作为默认执行底座 | 技术栈和治理边界不适合作为当前主路径 |
| 前端直接连接 Hermes / AgentScope Studio | 会绕过平台权限、审计、会话和消息主数据 |
| 自动 Skill 创建、自修复、Cron 长任务、桌面接管 | 范围过大，安全和运营治理不足，不应进入当前阶段 |
| 真实业务副作用动作直接进入 Agent runtime | 发邮件、改业务数据、提交审批、支付、写 CRM / 工单等需要独立安全设计 |
| 归档任务报告中的 L5 状态 | 是旧工程过程结果，不能证明当前 `source/agent-platform` 已达到同等验收 |

## 7. 建议后续落地顺序

### 7.1 文档层

建议在 `docs/v2/` 下按当前迁移主线逐步补齐：

1. `docs/v2/01-产品范围与阶段切片.md`：吸收 V3 产品蓝图，但改写为 Apboa 迁移阶段。
2. `docs/v2/02-运行时与能力治理调研结论.md`：固化 AgentScope / Runtime / Hermes 取舍和 Capability gate 边界。
3. `docs/v2/03-API-SSE-运行时契约草案.md`：从归档 V3 抽取统一 envelope、错误码和 RuntimeEvent，但保留 Apboa 兼容接口。
4. `docs/v2/04-数据安全审计调研结论.md`：在不改表前提下定义用户隔离、审计、trace、testRunId 和敏感字段边界。
5. `docs/v2/05-测试与交付门禁.md`：吸收 L0-L5、Playwright、真实 E2E 和验证命令汇报规则。
6. `docs/v2/templates/`：按当前目录和模块名改写 ADR、AI 任务单、测试报告、交接记录模板。

### 7.2 代码层

短期优先级：

- 继续按 `docs/v1/03-模块边界收敛记录.md` 推进 repo-spi、infra-common 瘦身和领域对象去基础设施依赖。
- 在 `runtime-spi` 明确当前 AgentScope 运行请求、运行事件和结果边界，避免业务层直接依赖 AgentScope 实现类型。
- 在 `infra-capability` 固化能力计划：用户授权、Agent 白名单、能力启停、风险等级、环境健康、runtime 路由。
- 在 `infra-observability` 和 `admin-audit` 逐步引入 Run / Span / Audit 语义，但不要破坏现有表结构和 Apboa 外部接口。
- 在 `adapter-rest` / `adapter-agui` 维持兼容路径，同时为后续 v2 API 契约预留统一错误结构和 traceId。

中期优先级：

- 将当前 Chat / AGUI 链路从“前端消费事件后再落库”的弱一致模式，逐步收敛为后端掌握 Run、Message、SSE final flush 和失败态的权威链路。
- 为停止生成、重新生成、编辑重发、分支切换、执行详情建立统一状态机。
- 对工具、MCP、Skill、Hook、动态脚本执行建立默认拒绝、风险分级、脱敏审计和沙箱路由。
- 补齐 API / SSE E2E、前端真实 E2E 和 `testRunId` 数据隔离。

### 7.3 评审层

每个后续小工程启动前建议固定三件事：
