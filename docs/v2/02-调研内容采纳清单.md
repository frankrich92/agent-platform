# v2 调研内容采纳清单

## 1. 范围与判断标准

本文综合分析 `docs/v2/调研/` 下现有调研文档，判断哪些建议适合吸收进当前 `agent-platform` 的架构和后续改造路线。

已分析资料：

- `README.md`
- `Agent平台定位分析.md`
- `gpt-v2.md`
- `claude4.7-v2.md`
- `claude-code-architecture-research.md`
- `dpsk-v4.md`
- `glm5.1-v2.md`
- `kimi-k2.6-v2.md`
- `gemini3.1-falsh-v2.md`
- `历史归档文档可吸收内容分析.md`

采纳判断标准：

- 是否符合“通用底座 + 专家智能体 Profile”的平台定位。
- 是否能落到 `Profile / Run / Runtime / Workflow / Capability / Worker / Governance` 目标模块。
- 是否能在第一阶段保持数据库表结构基本不变，只迁移和收敛代码职责。
- 是否能降低 AgentScope、Hermes、CLI Agent 等具体实现对业务模块的侵入。
- 是否能增强企业场景需要的权限、审计、回放、人工审批、隔离和可观测性。
- 是否能小步落地，避免一次性引入高风险大改造。

## 2. 总体结论

调研内容整体方向是合理的，且多份文档在关键判断上高度一致：当前平台不应把某一个 CLI Agent、AgentScope 或 LangGraph 当成全部底座，而应建设企业 Agent 平台自己的稳定中间层。

最值得采纳的主线是：

```text
专家 Agent Profile
  -> CapabilityPlan 能力装配与权限收敛
  -> AgentRunService 运行源头
  -> Runtime SPI 屏蔽具体运行时
  -> Run / Step / ToolCall / Event 可追踪账本
  -> Tool / MCP / Skill / Knowledge 统一治理
  -> Worker / Sandbox 承接高风险执行
```

其中，近期优先级最高的不是“换一个更强的 Agent 框架”，而是把平台自己的 Profile、Run、Runtime SPI、CapabilityPlan、审计事件和安全边界建立起来。

## 3. 直接采纳清单

以下内容与当前平台定位高度一致，可直接进入近期架构和代码改造路线。

| 编号 | 可采纳内容 | 采纳原因 | 推荐落点 | 优先级 |
| --- | --- | --- | --- | --- |
| A01 | 企业 Agent 平台采用“通用底座 + 专家智能体 Profile” | 能兼顾复用、治理、审计、评测和多场景扩展 | `agent-profile`、`agent-runtime`、`agent-governance` | P0 |
| A02 | CLI Coding Agent 作为 Worker，不作为平台唯一 Runtime | Codex CLI、Qwen Code、opencode 更适合执行代码任务，不适合承担企业平台全部治理责任 | `agent-worker` | P0 |
| A03 | AgentScope 收敛到 Runtime Adapter 后面 | 避免业务模块直接依赖 AgentScope 类型，便于后续替换或接入多 Runtime | `agent-runtime/runtime-spi`、`agent-runtime/runtime-agentscope` | P0 |
| A04 | 建立后端 `AgentRunService` 作为运行源头 | 会话、消息、工具调用、异常、审计应由后端统一记录，前端只消费事件流 | `agent-run/run-core` | P0 |
| A05 | 建立 Run / Step / ToolCall / Event 运行账本 | 支持回放、审计、问题定位、成本统计、失败恢复和人工审批 | `agent-run`、`agent-governance` | P0 |
| A06 | 保留现有会话树，同时补充运行账本 | 会话树适合产品体验，运行账本适合工程治理，二者职责不同 | `agent-run`、`agent-repo` | P0 |
| A07 | 引入统一 `RuntimeEvent` 流式事件包 | 统一 SSE、AG-UI、审计、回放和前端渲染边界 | `agent-api`、`agent-run`、`agent-runtime` | P0 |
| A08 | 引入 `CapabilityPlan` | 在运行前明确本次 Agent 可见的模型、Prompt、Skill、Tool、MCP、Knowledge、Hook、Worker 和权限 | `agent-capability`、`agent-profile` | P0 |
| A09 | Skill 从全量注入改为 progressive disclosure | 避免上下文污染和 Token 浪费，先注入索引，按需读取 Skill 内容 | `agent-capability/capability-skill`、`agent-runtime` | P0 |
| A10 | Skill 元数据最小规范 | 用描述、触发条件、允许工具、风险等级、版本、来源、摘要哈希支撑治理 | `agent-profile`、`agent-capability` | P0 |
| A11 | 拆分会话历史、上下文压缩、长期记忆 | 三者生命周期、权限和用途不同，不能都塞进 AgentScope Memory | `agent-run`、`agent-runtime/runtime-memory` | P0 |
| A12 | MCP 增加命名空间、启停、白名单、密钥引用和审计 | 企业 MCP 接入必须可控、可审计、可降级 | `agent-capability/capability-mcp`、`agent-governance` | P0 |
| A13 | 动态工具、Hook、MCP 和 Worker 统一纳入权限策略 | 高风险能力必须默认关闭或需要人工确认 | `agent-governance`、`agent-capability`、`agent-worker` | P0 |
| A14 | 工具调用记录结构化 | 记录工具名、参数摘要、风险等级、审批状态、耗时、结果摘要和错误 | `agent-run/run-toolcall`、`agent-governance` | P0 |
| A15 | 高风险代码执行迁出主 JVM | Shell、Python、Node、浏览器、文件写入、CLI Coding Agent 应进入 Worker/Sandbox 边界 | `agent-worker` | P0 |
| A16 | traceId 贯穿 HTTP、SSE、Run、Event、ToolCall、Audit | 企业排障和合规审计需要统一链路追踪 | `agent-governance/governance-observability` | P0 |
| A17 | 权限策略按平台、Agent、会话分层 | 平台基线约束、Profile 默认策略、会话临时授权需要分层合并 | `agent-governance/governance-policy` | P0 |
| A18 | 采用“小切片、契约先行、可验证”的迁移方式 | 与当前迁移工程更匹配，避免大范围搬运或一次性重构 | 全模块 | P0 |

## 6. 暂不采纳清单

以下内容不建议进入当前方案，或明确不能照搬。

| 编号 | 不采纳内容 | 原因 |
| --- | --- | --- |
| D01 | 用某个 CLI Agent 替代企业 Agent 平台底座 | CLI 更适合作为 Worker，缺少平台级 Profile、权限、审计、租户和生命周期管理 |
| D02 | Hermes 作为默认 Runtime | Hermes 可参考 API、Run、Capability 和方法论，但不适合作为 Java 主平台默认运行时 |
| D03 | 前端直接保存 assistant/tool/error 消息作为事实源 | 会导致审计、回放和一致性问题；后端 Run/Event 才应是事实源 |
| D04 | 用线性 transcript 替换现有 `chat_message` 树 | 现有树结构对产品体验仍有价值，运行账本应补充而非替换 |
| D05 | 所有 Skill 内容全量注入 Prompt | Token 成本高，且容易污染上下文，应改为索引 + 按需读取 |
| D06 | 将长期记忆简单追加为 AgentScope Memory 消息 | 长期记忆需要来源、作用域、权限、TTL、删除和召回治理 |
| D07 | 动态 Groovy / Java 工具在主 JVM 内任意执行 | 风险过高，必须经过沙箱、白名单和审批治理 |
| D08 | MCP、动态工具、Hook 绕过权限治理直接暴露给 Agent | 企业场景不可接受，必须进入 CapabilityPlan 和 Policy 计算 |
| D09 | 自动发布自生成 Skill、自修复脚本或无人审核长任务 | 可能造成权限和业务副作用风险，只能做人审草稿或受控执行 |
| D10 | 第一阶段直接换表、换存储、换 Spring Boot/Maven 大版本 | 与当前迁移约束冲突，容易放大风险 |
| D11 | 直接采用旧归档文档中的路径、模块名和 UI 技术栈 | 当前工程已有新模块边界，历史方案只能提炼原则 |
| D12 | 在 Runtime 中直接执行真实业务副作用动作 | 业务系统写操作、审批、发布、转账等动作应进入独立审批和幂等设计 |

## 8. 推荐落地顺序

### 8.1 第一阶段：收敛运行主链路

- 完成 Runtime SPI 与 AgentScope Runtime Adapter 的边界收敛。
- 建立 `AgentRunService`，由后端统一发起 Run、记录消息和运行结果。
- 定义 `RuntimeEvent`、`RunStep`、`ToolCall` 的最小结构。
- 引入 `CapabilityPlan` MVP，先覆盖 Tool、MCP、Skill、Knowledge、模型策略。
- Skill 改成“索引可见 + 内容按需读取”。
- MCP 接入增加命名空间、启停、密钥引用、include/exclude 和调用审计。
- 高风险工具先进入 `ask` 或 `deny` 策略，不直接自动执行。

### 8.2 第二阶段：补齐治理与上下文能力

- 建立长期记忆 MVP，和会话历史、上下文压缩分离。
- 增加 Token 预算、压缩 Span、压缩前记忆刷写、压缩失败降级。
- 增加工具调用成本、耗时、错误、参数摘要和结果摘要统计。
- 支持只读工具并行、工具 schema 缓存、工具结果截断。
- 支持 SubAgent 独立上下文和摘要返回。
- 补充 Hook 生命周期，但默认只开放低风险确定性 Hook。
- 增加 Profile 版本、评测样例、灰度和回放对比。

### 8.3 第三阶段：扩展生态与 Worker 能力

- 建设 Worker/Sandbox，用于代码执行、文件写入、构建测试、浏览器自动化和 CLI Coding Agent。
- 扩展 Skill 市场、热加载、签名校验、版本依赖和人工审核发布。
- 扩展 MCP Resources、MCP Prompts、Agent as MCP Server。
- 扩展向量记忆、知识图谱、跨会话知识网络。
- 在需要复杂长流程时接入 LangGraph 或其他 Workflow Worker。

## 9. 采纳前检查清单

任何调研建议进入代码前，应先过以下检查：

- 是否落在 `.apboa/` 之外。
- 是否符合 `RTK.md` 和 `docs/v2/01-agent平台架构优化.md` 的模块边界。
- 是否避免业务模块直接依赖 AgentScope、Hermes 或 CLI Agent 类型。
- 是否保持第一阶段数据库表结构基本不变，或明确标记为后续评审项。
- 是否有权限策略、风险等级、审计事件和 traceId。
- 是否有失败处理、幂等语义和人工审批边界。
- 是否能通过小范围测试验证，不依赖一次性大迁移。
- 是否保留现有用户改动，不覆盖无关文件。

## 10. 结论

调研目录中最合理、最值得吸收的是工程化治理思想，而不是某个具体产品的完整实现形态。当前项目应继续沿着“企业 Agent 平台自己的稳定中间层”推进：用 Profile 表达专家智能体，用 Run/Event 记录事实，用 Runtime SPI 屏蔽实现，用 CapabilityPlan 管住能力，用 Governance 兜住权限审计，用 Worker/Sandbox 承接高风险执行。

这条路线能同时兼容 AgentScope Java、未来 Hermes/LangGraph/CLI Worker，也能让企业内部专家智能体以可复用、可治理、可审计的方式持续扩展。
