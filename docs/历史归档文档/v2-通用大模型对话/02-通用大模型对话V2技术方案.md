# 通用大模型对话 V2 技术方案

> 注意：本文档为历史阶段文档，仅作为需求、调研和演进参考。
> 当前 Agent 中台架构与后续开发以 `docs/v3-agent中台/` 为准。
> AI agent 执行开发任务前必须先阅读 `docs/README.md` 和 V3 架构文档。

> 版本：v2
> 日期：2026-05-15
> 依据文档：`01-通用大模型对话V2需求.md`、V1 设计文档、`docs/v1-通用大模型对话/评审/综合对比分析汇总.md`
> 目标：给出“带用户管理的 OpenClaw + Hermes Agent”式通用 Agent 对话平台的 V2 技术方案。

## 1. 总体架构

V2 的产品目标是先做通用 Agent 对话：用户进入平台后，只能使用被授权的 Agent；每个 Agent 可以配置模型、MCP server、skills、系统提示词和记忆策略；同一个 Agent 授权给多个用户时，共享 Agent 定义，但每个用户拥有独立会话、独立记忆和独立运行记录。

V2 沿用 V1 前后端分离和后端多模块结构：

- 后端：`source/htam-agent-platform`
- 前端：`source/htam-agent-platform-ui`
- 参考样例：`source/agentscope-demo`，仅用于 AgentScope Java API 参考，不在该目录实现业务能力。

后端继续保持：

```text
agent-web -> agent-core -> agent-api
agent-web -> agent-api
```

V2 新增四条架构主线：

1. **对话体验增强**：消息操作、会话组织、Markdown、主题和快捷键。
2. **运行时增强**：真正流式、多 Provider、模型切换、上下文预算保护。
3. **Agent 平台增强**：新增 Agent 定义、用户授权、用户隔离记忆、MCP/Skills 能力注册和 AgentScope ReAct 运行路径。
4. **可观测增强**：新增 Run/Span、token、耗时、错误、MCP/Skills 工具调用链路。

由于当前项目尚未正式上线，V2 不需要为未发布的 V1 HTTP/SSE/数据库契约背兼容包袱。技术方案应优先按“首次上线目标架构”收敛，在上线前统一调整 API 响应、SSE 事件格式、Flyway baseline 和前端状态模型；上线后再严格执行只增量演进的兼容策略。

## 2. 架构原则

- **上线前契约收敛**：项目未上线前允许破坏性调整 API、SSE、数据库 schema 和前端数据结构；不为未发布旧契约新增兼容层。
- **DB 是权威上下文**：历史消息、运行记录和工具调用记录以数据库为准，Agent 内存不得成为跨会话长期状态。
- **Agent 配置共享、用户数据隔离**：Agent 定义可授权给多个用户；会话、消息、记忆、Run/Span 必须按 `userCode + agentId` 隔离。
- **先授权再运行**：任何会话创建、消息发送、记忆读取、MCP/Skills 调用和运行详情查询，都必须先校验用户对目标 Agent 的授权。
- **Run 优先建模**：每次生成、重新生成、编辑重发都先创建 Run，再关联用户消息、助手消息、span 和 token usage，避免后续补观测时改造主链路。
- **运行时抽象高于模型适配**：`LlmProviderAdapter` 适合裸模型流式适配；V2 引入 ReAct 和工具后，应在其上抽象 `AgentRuntime` 或等价运行时接口，统一普通模型、ReActAgent 和后续工具型 Agent。
- **普通用户与开发者视图分离**：普通用户页面只展示必要运行摘要；开发者调试视图可展示更细 Run/Span 信息。
- **Provider 可回退但不静默**：支持多 Provider 配置和显式切换，但配置错误必须返回明确错误。
- **工具默认最小权限**：高风险技能默认关闭，启用必须有白名单、超时、审计和脱敏。
- **先观测再扩展**：工具、技能和 ReAct 路径进入正式链路前，必须能被 Run/Span 追踪。
- **上线前迁移脚本可重整**：在没有共享生产数据前，可压缩或重建 Flyway 初始迁移，减少 V1-Vn 修补式脚本；一旦进入联调共享库或上线环境，再只允许追加迁移。

## 3. 后端方案

### 3.0 未上线阶段的架构优化结论

当前方案已经覆盖 V2 主要能力，但考虑项目尚未上线，建议在正式开发前做以下架构收敛：

| 优化点 | 原方案倾向 | 建议调整 |
|--------|------------|----------|
| API 兼容策略 | 保留并扩展 V1 契约 | 上线前直接改为目标分页、消息操作和 Run 响应契约，不保留旧数组响应 |
| SSE 协议 | V1 事件 + V2 增量扩展 | 统一 JSON envelope，所有事件都带 `eventId`、`runId`、`messageId`、`sequence`，避免文本事件和 JSON 事件混用 |
| 运行时抽象 | `LlmProviderAdapter` 同时承载模型和 ReAct | 新增 `AgentRuntime`，普通模型、ReActAgent 都作为 runtime 实现；底层 provider adapter 只处理模型协议差异 |
| Run/Span | 作为 V2 新增观测能力 | 从第一条发送链路开始强制创建 Run，ChatService 只围绕 Run 编排 |
| 产品域模型 | 会话直接绑定模型 | 会话绑定 `agentId`，Agent 再绑定模型、MCP/Skills、系统提示词和记忆策略 |
| 用户隔离 | 仅按 `userCode` 隔离会话 | 按 `userCode + agentId` 隔离会话、记忆、Run/Span，并通过授权表控制可见 Agent |
| 能力体系 | Skills 为主 | MCP 与 Skills 统一建模为 Agent capability，运行前叠加 Agent 白名单、用户授权和安全策略 |
| 数据迁移 | 在现有 V1-V5 基础上追加 V2 | 未上线前重整 baseline，形成面向首次上线的一组清晰迁移脚本 |
| 可观测 | DB Run/Span 为主 | DB 记录用于产品查询，OpenTelemetry trace 用于运行诊断，两者通过 `traceId/runId/spanId` 关联 |
| 工具调用存储 | `agent_tool_call` 可选 | V2 先用 `agent_run_span + agent_message_part` 表达工具过程，避免过早拆表；确有独立检索需求后再加工具调用表 |

以上调整会减少兼容代码、降低后续重构成本，更适合未上线项目的当前阶段。

### 3.1 模块职责

`agent-core` 新增：

- Provider/模型查询接口。
- Run/Span 查询接口。
- SSE 新事件映射。
- 开发者调试接口的最小访问控制。

### 3.2 真正流式方案

当前 `OpenAiCompatibleAdapter` 使用 `HttpResponse.BodyHandlers.ofString()`，会先读取完整上游响应体再解析 SSE。V2 必须改为逐块读取。

推荐实现：

- 使用 `HttpResponse.BodyHandlers.ofInputStream()` 或自定义 line `BodySubscriber`。
- 在 `Schedulers.boundedElastic()` 或专用阻塞执行器中逐行读取上游响应。
- 每读取到一条完整 `data:` 行，即解析为底层 `LlmProviderEvent` 并 `sink.next(...)`。
- 收到 `[DONE]` 或上游完成时发出 `provider_completed`，再由 `OpenAiChatRuntime` 转成 `run_completed`。
- 上游非 2xx、JSON 解析失败、连接中断和线程中断都映射为失败事件。
- 客户端取消时中断上游读取、关闭输入流、释放会话锁。

V2 不要求更换 HTTP 客户端，但禁止继续以完整字符串作为流式实现基础。

### 3.3 Provider 与模型配置

配置结构从单模型扩展为多 Provider、多模型：

```yaml
htam:
  llm:
    default-provider: ${HTAM_LLM_DEFAULT_PROVIDER:openai-compatible}
    default-model: ${HTAM_LLM_MODEL_NAME}
    providers:
      openai-compatible:
        type: openai-compatible
        base-url: ${HTAM_LLM_BASE_URL}
        api-key: ${HTAM_LLM_API_KEY}
        models:
          - name: ${HTAM_LLM_MODEL_NAME}
      agentscope-react:
        type: agentscope-react
        base-url: ${HTAM_LLM_BASE_URL}
        api-key: ${HTAM_LLM_API_KEY}
        models:
          - name: ${HTAM_LLM_MODEL_NAME}
```

实际配置仍通过 `.env` 注入敏感值，文档和 `application.yml` 只引用变量名。

会话级模型选择规则：

- 新会话默认使用系统默认 Provider 和模型。
- 前端可在发送前选择模型。
- 每条助手消息记录实际使用的 Provider 和模型。
- 切换模型只影响后续消息，不改写历史消息。

### 3.4 AgentScope ReAct 运行路径

V2 不建议把 ReActAgent 直接塞进 `LlmProviderAdapter`。ReActAgent 已经包含模型推理、工具选择、工具执行和中间步骤，语义上是 Agent 运行时，不只是 LLM provider。推荐以 Agent 定义为入口构建运行时：

```text
ChatService
  -> AgentAccessService 校验 userCode + agentId
  -> AgentDefinitionService 读取 Agent 配置
  -> AgentMemoryService 读取当前用户当前 Agent 记忆
  -> CapabilityRegistry 裁剪 MCP/Skills 可用能力
  -> AgentRuntime
     -> OpenAiChatRuntime
        -> LlmProviderAdapter
     -> AgentScopeReActRuntime
        -> ReActAgent + Toolkit + SkillBox + AgentSkill + MCP tools
  -> AgentStreamEvent
```

职责边界：

- `ChatService` 不感知 `ReActAgent`、`Toolkit`、`SkillBox` 的具体类型。
- `AgentRuntime` 负责统一普通模型对话、ReActAgent 对话和后续工具型 Agent 的流式输出。
- `AgentDefinition` 负责声明 Agent 的系统提示词、默认模型、可用 MCP/Skills、记忆策略和可见状态。
- `LlmProviderAdapter` 退回到更底层的模型协议适配，负责 OpenAI-compatible、Anthropic、Ollama 等模型差异。
- `AgentScopeReActRuntime` 负责把上下文、模型配置、技能配置转为 AgentScope 调用。
- `CapabilityRegistry` 负责在 Agent 白名单、用户授权、环境门控和安全策略共同约束下决定哪些 MCP/Skills 可用。
- `AgentMemoryService` 只注入当前 `userCode + agentId` 范围内的记忆。
- `RunSpanRecorder` 记录模型调用、工具调用、错误和耗时。

事件映射：

- reasoning/thinking 类内容映射为 `thinking_delta`。
- 最终文本映射为 `message_delta`。
- 工具调用开始映射为 `tool_call_started`。
- 工具调用结果映射为 `tool_call_delta` 或 `tool_call_completed`。
- 运行步骤状态映射为 `span_started`、`span_completed` 或 `span_failed`。
- 完成和失败使用 `run_completed`、`run_failed`、`error`。

### 3.5 MCP/Skills 能力安全策略

V2 MCP/Skills 能力默认关闭。启用能力时必须满足：

- 配置层显式启用。
- Agent 定义显式加入能力白名单。
- 用户被授权使用该 Agent。
- 环境门控通过，例如必需命令、环境变量、MCP server 连接状态可用。
- 高风险工具按工具类型单独启用。
- 文件工具限制在配置的工作目录内。
- Shell 工具限制命令白名单、超时和输出长度。
- 网络工具和 MCP server 限制目标域名、协议和认证方式。
- 工具参数和结果进入日志、Run/Span 前执行脱敏。
- 工具失败不会导致会话锁泄漏。

### 3.6 上下文预算保护

`ContextAssembler` 新增预算配置：

- `maxInputTokens`
- `reservedCompletionTokens`
- `maxHistoryMessages`
- `tokenEstimateRatio`

V2 默认策略：

- 系统提示词和当前用户消息必须保留。
- 从最近消息向前累计历史。
- thinking 默认不进入模型上下文。
- 超预算时裁剪更早历史，并在 Run 中记录裁剪数量。
- 如果当前用户消息本身过长，返回 `CONTENT_TOO_LONG`。

V2 暂不强制自动摘要，但保留摘要边界字段，后续可引入摘要消息替代更早历史。

### 3.7 用户隔离记忆

V2 记忆先做可解释、可控、按用户隔离的文本型记忆，不直接进入复杂向量检索。

默认记忆类型：

- `profile`：用户偏好、称呼、常用约束。
- `fact`：长期事实。
- `summary`：跨会话摘要。
- `instruction`：用户对某个 Agent 的稳定操作约定。

注入规则：

- 只读取当前 `userCode + agentId` 的 active 记忆。
- 每轮运行前按 token 预算裁剪记忆。
- 记忆注入记录到 Run/Span。
- 用户可查看和清空自己的 Agent 记忆。
- V2 不做自动记忆提炼和后台学习闭环，后续再引入 Hermes 风格的记忆刷新和技能自创建。

## 4. 数据方案

V2 首次上线以“用户、Agent、会话、消息、记忆、运行”作为核心域模型。

新增平台域表：

- `agent_user`：平台内部用户，V2 可由 `X-App-Code` 首次访问时自动映射或创建。
- `agent_definition`：Agent 定义，保存名称、描述、运行时类型、默认模型、系统提示词、状态和记忆策略。
- `agent_user_grant`：Agent 授权，控制哪个用户可以使用哪个 Agent。
- `agent_capability`：MCP server、skill、内置工具的统一能力定义。
- `agent_definition_capability`：Agent 到能力的白名单绑定。
- `agent_memory`：按 `user_code + agent_id` 隔离的用户记忆。

对话核心表：

- `agent_session`
- `agent_message`
- `agent_message_part`

对话表在此基础上新增或扩展：

- 会话字段：`agent_id`、收藏、手动标题标记、默认 provider、默认模型。
- 消息字段：`agent_id`、provider、run_id、parent_message_id、版本号、删除状态。
- 运行表：`agent_run`。
- 运行步骤表：`agent_run_span`。

V2 不单独新增 `agent_tool_call` 表。工具调用先通过 `agent_run_span` 记录执行过程，通过 `agent_message_part` 记录面向用户展示的工具摘要。只有当后续出现工具调用独立检索、重放、权限审计报表等明确需求时，再拆出专用工具调用表。

推荐最小运行模型：

```text
agent_run
  id
  agent_id
  session_id
  user_code
  user_message_id
  assistant_message_id
  provider
  model_name
  status
  prompt_tokens
  completion_tokens
  total_tokens
  first_token_latency_ms
  total_duration_ms
  error_message
  created_at
  started_at
  completed_at

agent_run_span
  id
  run_id
  parent_span_id
  trace_id
  span_type
  name
  status
  start_time
  end_time
  duration_ms
  input_summary
  output_summary
  error_message
  metadata_json
```

敏感字段不得保存明文 API Key、token、数据库密码或完整认证头。

可观测采用双通道：

- `agent_run` / `agent_run_span`：产品侧可查询的运行账本，用于详情抽屉、问题排查和审计摘要。
- OpenTelemetry trace：运行诊断链路，用于对接日志、指标、AgentScope Studio 或其他观测系统。

两者通过 `trace_id`、`run_id`、`span_id` 关联。DB 中保存脱敏摘要，完整诊断信息进入受控观测系统。

## 5. API 方案

所有 API 继续要求：

- `X-Token`
- `X-App-Code`

### 5.1 会话接口

保留：

- `POST /api/agent/sessions`
- `DELETE /api/agent/sessions/{sessionId}`

调整：

- `GET /api/agent/sessions?pageSize=&cursor=&keyword=&favorite=`
  - 返回 `{ items, nextCursor, hasMore }`。

新增：

- `PATCH /api/agent/sessions/{sessionId}`：更新标题、收藏状态、默认模型。
- `POST /api/agent/sessions/{sessionId}/duplicate`：复制会话。
- `GET /api/agent/sessions/{sessionId}/export?format=markdown|text`：导出会话。

新建会话必须携带或解析出 `agentId`。如果前端未传，服务端使用当前用户的默认授权 Agent；如果用户无默认 Agent，返回明确错误。

### 5.2 消息接口

调整：

- `GET /api/agent/sessions/{sessionId}/messages?pageSize=&before=&after=`
  - 返回 `{ items, nextCursor, hasMore }`。

保留并扩展：

- `POST /api/agent/sessions/{sessionId}/messages/stream`
  - 请求可携带 `provider`、`modelName`。

新增：

- `POST /api/agent/sessions/{sessionId}/messages/{assistantMessageId}/regenerate`
- `POST /api/agent/sessions/{sessionId}/messages/{userMessageId}/edit-and-resend`
- `DELETE /api/agent/sessions/{sessionId}/messages/{messageId}`

重新生成和编辑重发均返回 `text/event-stream`，事件协议与普通发送保持一致。

### 5.3 Provider 与运行接口

新增：

- `GET /api/agent/providers`
- `GET /api/agent/runs/{runId}`
- `GET /api/agent/sessions/{sessionId}/runs?messageId=`

开发者调试接口可在 V2 先使用请求头或 profile 控制访问；正式权限体系不纳入 V2。

### 5.4 Agent、能力与记忆接口

新增：

- `GET /api/agent/agents`：查询当前用户可用 Agent。
- `GET /api/agent/agents/{agentId}`：查询当前用户可用 Agent 详情。
- `GET /api/agent/agents/{agentId}/capabilities`：查询 Agent 对当前用户可见的 MCP/Skills 能力摘要。
- `GET /api/agent/agents/{agentId}/memories`：查询当前用户在该 Agent 下的记忆摘要。
- `DELETE /api/agent/agents/{agentId}/memories`：清空当前用户在该 Agent 下的记忆。

管理员接口可后续扩展 Agent 创建、授权和能力绑定；V2 首次上线可以先通过配置或数据库初始化提供默认通用 Agent。

由于项目尚未上线，V2 直接采用分页响应作为正式契约，不再保留 V1 的数组响应格式。

## 6. SSE 协议

V2 直接采用统一 JSON envelope。HTTP SSE 的 `event` 名称表示事件类别，`data` 一律是 JSON 字符串，不再混用纯文本 data。

通用字段：

```json
{
  "eventId": "event-id",
  "runId": "run-id",
  "sessionId": "session-id",
  "messageId": "message-id",
  "sequence": 1,
  "createdAt": "2026-05-15T10:00:00Z"
}
```

事件类型：

- `run_started`
- `thinking_delta`
- `message_delta`
- `tool_call_started`
- `tool_call_delta`
- `tool_call_completed`
- `span_started`
- `span_completed`
- `span_failed`
- `run_completed`
- `run_failed`
- `error`

`run_started` 包含：

- `provider`
- `modelName`
- `userMessageId`
- `assistantMessageId`

`thinking_delta` 和 `message_delta` 包含：

- `delta`
- `partId`
- `partType`

`run_completed` 包含：

- `finishReason`
- `usage`
- `firstTokenLatencyMs`
- `totalDurationMs`

前端必须忽略未知事件，以便后续协议扩展。

## 7. 前端方案

V2 将 `App.vue` 拆为更清晰的结构，并引入 Pinia：

```text
src/
  api/
  stores/
    authStore.ts
    sessionStore.ts
    messageStore.ts
    streamStore.ts
    preferenceStore.ts
  components/
    layout/
    session/
    message/
    composer/
    run/
  composables/
    useSseStream.ts
    useKeyboardShortcuts.ts
    useTheme.ts
  types/
```

组件拆分方向：

- 会话侧边栏：列表、搜索、收藏、分页加载、重命名、复制、删除。
- 消息列表：虚拟或分页加载、锚点导航、消息操作栏。
- 消息渲染：Markdown、代码高亮、thinking、工具调用块。
- 输入区：草稿、排队、快捷键、停止生成。
- 运行详情：抽屉、Run/Span、token、耗时、错误摘要。
- 顶部模型选择：Provider/模型切换和当前模型展示。

前端状态管理：

- `sessionStore` 管理会话列表、分页、搜索、收藏。
- `messageStore` 管理当前会话消息、分页、临时 ID 替换和消息操作。
- `streamStore` 管理当前生成、AbortController、队列和 SSE 事件。
- `preferenceStore` 管理主题、详情抽屉和本地偏好。
