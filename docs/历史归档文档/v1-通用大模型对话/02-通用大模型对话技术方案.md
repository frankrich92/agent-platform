# 通用大模型对话技术方案

> 注意：本文档为历史阶段文档，仅作为需求、调研和演进参考。
> 当前 Agent 中台架构与后续开发以 `docs/v3-agent中台/` 为准。
> AI agent 执行开发任务前必须先阅读 `docs/README.md` 和 V3 架构文档。

## 1. 总体架构

新增前后端分离目录：

- 后端：`source/htam-agent-platform`
- 前端：`source/htam-agent-platform-ui`

`source/agentscope-demo` 仅作为已验证的 `agentscope-java` 示例参考，不在该目录内进行修改。

第一版技术栈：

- 后端：JDK 21 + Spring Boot 4.0.5 + Spring WebFlux + `agentscope-java`
- 后端工程：多模块 Maven 项目
- 前端：Vue 3 + Vite + Element Plus
- 数据库：PostgreSQL
- 持久化：MyBatis-Plus + Flyway

版本基线：

- `source/agentscope-demo` 已验证 Spring Boot 4.0.5 和 `agentscope-java` 1.0.12。
- 第一版建议以 Spring Boot 4.0.5 起步，统一锁定 `agentscope-java` / `agentscope-spring-boot-starter` 为 1.0.12。
- 如需升级到 Spring Boot 4.0.6，必须先验证 `agentscope-spring-boot-starter` 1.0.12 的兼容性。

## 2. 架构设计原则

第一版保持 Web 端通用对话的交付边界，但参考 Hermes Agent 和 OpenClaw 的运行时设计，明确以下长期约束：

- **Core 层与 Web 层解耦**：`agent-core` 承担领域服务、持久化、模型适配和上下文组装，不依赖 WebFlux 请求/响应类型；`agent-web` 负责 HTTP/SSE、鉴权过滤器和协议适配。
- **会话内 Prompt 稳定性**：会话启动后，系统级 prompt 在当前会话过程中保持稳定；后续如引入用户偏好、长期记忆或项目上下文，变更默认在新会话或新上下文窗口中生效。
- **同会话串行、跨会话并行**：同一 `userCode + sessionId` 的生成请求必须串行处理，不同会话可以并行处理。
- **可选模块松耦合**：后续工具、插件、记忆、检索、Agent 编排等能力采用注册表 + 可用性检查模式，不让可选模块加载失败影响核心对话链路。
- **先做访问控制，再让模型行动**：V1 无工具执行，但安全边界、日志脱敏和用户隔离必须先明确；后续工具能力必须先有权限、审计和沙箱策略。

## 3. 后端设计

后端提供会话、消息和流式对话接口。

核心职责：

- 校验请求头中的 `X-Token`、`X-App-Code` 非空。
- 将 `X-App-Code` 映射为 `userCode` mock 值。
- 按 `userCode` 隔离会话和消息数据。
- 使用 `agentscope-java` 调用大模型。
- 基于当前会话历史消息组装多轮对话上下文。
- 将助手的 thinking 内容和最终回复以流式方式返回前端。
- 持久化用户消息、助手最终回复、助手 thinking 内容和消息分段。
- 控制同一会话内的服务端处理顺序，避免并发请求打乱上下文。
- 通过模型 provider 适配层隔离业务逻辑与具体模型调用实现。
- 通过上下文组装组件统一处理历史消息、系统提示词和后续 token 预算。

WebFlux 线程模型约束：

- Spring WebFlux 的 Netty 事件循环线程不能执行阻塞等待、JDBC 查询或同步模型调用。
- MyBatis-Plus 基于 JDBC，属于同步阻塞持久化能力，必须放到 `Schedulers.boundedElastic()`、虚拟线程或明确的阻塞任务执行器中运行。
- 如果会话锁使用 `Semaphore`，第一版应优先使用 `tryAcquire` 非阻塞获取，失败返回 `409`；如采用阻塞等待，必须调度到阻塞线程池，不能阻塞事件循环线程。

模型 provider 抽象：

- 第一版只实现 OpenAI-compatible / `agentscope-java` 适配。
- 对业务服务暴露统一的 `LlmProviderAdapter`，隐藏不同 provider 的请求格式、stream 事件格式、thinking 字段差异和后续 fallback 策略。
- 配置中预留 `provider`、`apiMode`、`modelName`、`baseUrl`、`apiKey` 等字段；第一版 `provider` 可固定为 `openai-compatible`。

上下文组装抽象：

- 第一版使用 `ContextAssembler` 统一组装模型输入。
- V1 只读取当前会话中 `completed` 状态的 user/assistant text 内容，不注入 thinking。
- 当前用户消息总是放在上下文末尾。
- 暂不实现压缩和检索，但预留 token 估算、摘要边界和后续检索增强。

## 4. 前端设计

前端使用 Vue 3 + Vite + Element Plus，页面采用 ChatGPT 风格的经典布局：

- 左侧会话侧边栏。
- 右侧主聊天区。
- 底部输入框。
- 输入框上方的排队消息区。

前端入口流程：

1. 从页面 URL 读取 `token`、`appCode`。
2. 保存到浏览器会话状态。
3. 后续所有 API 请求携带请求头 `X-Token`、`X-App-Code`。

对话交互规则：

- 当前没有大模型响应时，用户发送消息后立即进入对话区，并请求服务端生成回复。
- 当前大模型正在响应时，用户发送的新消息不立即进入对话区，也不立即请求服务端。
- 响应中的新消息展示在输入框上方的排队消息区，并带有排队标识。
- 当前助手回复完成后，前端按排队顺序自动发送下一条消息，进入下一轮对话。
- 排队消息属于前端临时状态，不在进入实际发送流程前持久化。
- 前端排队是同一会话串行发送的主策略；服务端会话锁是兜底防线，用于防止前端异常、重复点击、接口重放或多标签页并发导致上下文错乱。
- 如果服务端返回 `409`，前端按当前轮发送失败处理，提示用户稍后重试，不自动重复提交。

## 5. 模型配置

模型配置通过 `source/htam-agent-platform/.env` 管理敏感值，`application.yml` 只保留变量引用和非敏感默认值，不在代码、`application.yml` 或实施文档中硬编码密钥、数据库 URL、用户名、密码等敏感信息。

需要支持的配置项：

- `provider`
- `apiMode`
- `baseUrl`
- `apiKey`
- `modelName`
- `stream`
- `thinkingBudget`
- `systemPrompt`

后端基于配置初始化 `agentscope-java` 的模型调用能力。

最终联调验收必须使用 `.env` 中的真实 LLM 配置走完整大模型链路。mock provider、接口桩和模拟 SSE 只用于单元测试或组件测试，不能作为 V1 最终验收通过依据。

## 6. 流式接口

第一版不使用浏览器原生 `EventSource`，因为 `EventSource` 不能方便地携带自定义请求头。

前端使用 `fetch` 发起流式请求：

- 请求头携带 `X-Token`。
- 请求头携带 `X-App-Code`。
- 响应读取 `text/event-stream` 流。
- 前端按流式片段分别增量更新 thinking 内容和助手最终回复。

后端使用 Spring WebFlux 返回流式响应，并对接 `agentscope-java` 的 stream 能力。

建议 SSE 事件类型：

- `thinking`：大模型 thinking 增量片段。
- `message`：助手最终回复增量片段。
- `done`：当前轮回复完成。
- `error`：当前轮回复失败。

agentscope 流式事件映射约束：

- `agentscope-java` 1.0.12 的 stream 事件中，`Msg.getContent()` 返回 `ContentBlock` 列表，同一事件可能同时包含 `ThinkingBlock` 和 `TextBlock`。
- 后端不能直接把 `MsgUtils.getTextContent()` 的拼接结果作为单一 `message` 事件返回；必须逐个 `ContentBlock` 判断类型，并分别发出 `thinking` 或 `message` SSE 事件。
- 使用 `StreamOptions.incremental(true)` 时仍需兼容模型或版本返回累积内容的情况，适配层应识别增量与累计文本，避免重复追加。

错误处理策略：

- LLM 调用失败时，已创建的助手消息标记为 `failed`，保存错误摘要，并向前端发送 `error` 事件。
- 流中断或连接断开时，后端需要释放会话锁，并将未完成的助手消息置为 `failed` 或由超时清理机制兜底。
- 第一版不做自动重试，避免重复写入用户消息和重复消耗模型 token；重试由用户在前端显式触发。
- 前端收到 `error`、HTTP 非 2xx 或 SSE 解析失败时，当前助手消息进入失败态，并展示错误提示。

## 7. 数据设计

参考 Codex、OpenCode 等开源对话产品的会话设计，第一版采用“会话元数据 + 消息元数据 + 消息分段”的结构。

可借鉴点：

- Codex 的会话文件采用 JSONL 事件流形式，保留 `session_meta`、用户输入、模型输出等过程事件，适合完整回放会话过程。
- OpenCode 的会话表保存标题、父会话、消息数、token、费用、摘要消息等元数据；消息内容使用 typed parts 保存，part 类型包括 reasoning、text、tool、finish 等。
- 本项目是 Web 端通用对话，不需要照搬代码 Agent 的工具调用模型，但需要借鉴 typed parts 思路，将 thinking 与最终回复拆开保存，避免只保存最终文本导致历史回放缺失推理过程。

建议使用三张核心表：

- `agent_session`
- `agent_message`
- `agent_message_part`

### agent_session

用于保存用户会话。

关键字段：

- `id`
- `user_code`
- `parent_session_id`
- `title`
- `status`
- `message_count`
- `prompt_tokens`
- `completion_tokens`
- `summary_message_id`
- `last_message_at`
- `created_at`
- `updated_at`

字段说明：

- `parent_session_id`：预留给后续分支、压缩续聊或基于历史会话创建新会话；第一版可以为空。
- `message_count`：当前会话消息数量，用于列表展示和后续统计。
- `prompt_tokens`、`completion_tokens`：预留 token 统计字段，便于后续成本分析。
- `summary_message_id`：预留上下文压缩摘要边界；它指向一条摘要消息，该消息之前的历史在模型上下文组装时可由摘要替代。第一版不实现自动压缩时可以为空。

### agent_message

用于保存消息元数据，不直接承担完整内容存储。具体内容保存到 `agent_message_part`。

关键字段：

- `id`
- `session_id`
- `user_code`
- `sequence`
- `role`
- `status`
- `model_name`
- `finish_reason`
- `error_message`
- `created_at`
- `updated_at`

字段说明：

- `sequence`：会话内消息顺序，历史回放按该字段升序展示。
- `role`：消息角色，第一版使用 `user`、`assistant`。
- `status`：消息状态，建议使用 `streaming`、`completed`、`failed`。
- `model_name`：助手消息使用，记录本轮调用的模型。
- `finish_reason`：助手消息使用，记录模型结束原因，例如 `stop`、`length`、`error`。
- `error_message`：生成失败时保存错误摘要，便于前端展示和排查。

### agent_message_part

用于保存消息内容分段。用户消息、助手 thinking、助手最终回复都以 part 形式保存。

关键字段：

- `id`
- `message_id`
- `session_id`
- `user_code`
- `part_sequence`
- `part_type`
- `content`
- `status`
- `created_at`
- `updated_at`

字段说明：

- `part_sequence`：同一消息内的分段顺序，历史回放按该字段升序拼接或展示。
- `part_type`：分段类型，第一版使用 `text`、`thinking`；预留 `finish`、`error`。
- `content`：分段内容。
- `status`：分段状态，建议使用 `streaming`、`completed`、`failed`。

保存规则：

- 用户消息写入一条 `agent_message`，并写入一条 `part_type = text` 的 `agent_message_part`。
- 助手消息写入一条 `agent_message`。
- 助手 thinking 增量写入或追加到 `part_type = thinking` 的 part。
- 助手最终回复增量写入或追加到 `part_type = text` 的 part。
- 如果后续需要更细粒度回放，可以改为每个流式 chunk 一条 part；第一版默认同类型内容聚合为一条 part，降低写入量。

所有查询和写入都必须带上 `userCode` 条件，第一版中 `userCode = appCode`。查询历史消息时返回消息元数据和 parts，前端按用户消息、助手 thinking、助手最终回复分别展示。

### parts 化保存与 JSONL 事件流的区别

parts 化保存和 Codex 的 JSONL 事件流不是同一种数据模型：

- parts 化保存面向业务查询和页面渲染。它把一条消息拆成 `text`、`thinking` 等结构化分段，存入关系表，适合按用户、会话、消息顺序查询，也适合做权限隔离、分页、删除和后台管理。
- JSONL 事件流面向过程追踪和完整回放。它按时间追加记录 `session_meta`、用户输入、模型输出、工具事件等原始事件，适合审计、调试和重放完整执行过程。
- parts 化更像“当前可展示的消息状态”，JSONL 更像“从开始到结束发生过什么的流水账”。
- 第一版 Web 对话优先选择 parts 化保存，因为核心需求是历史会话展示、多轮续聊、thinking 展示和用户隔离。
- 如果后续需要精确审计每个流式 chunk、重放生成过程或排查模型调用问题，可以额外增加 `agent_session_event` 作为追加式事件日志表，而不替代 `agent_message_part`。

流式保存策略：

- 用户消息实际发送到服务端时，立即写入 `agent_message`。
- 用户消息内容写入 `agent_message_part(part_type = text)`。
- 服务端创建一条 `assistant` 消息，初始状态为 `streaming`。
- 收到 thinking 增量时追加到助手消息的 `thinking` part。
- 收到最终回复增量时追加到助手消息的 `text` part。
- 流结束后将助手消息状态更新为 `completed`，并更新会话 `last_message_at`、`updated_at`。
- 流失败时将助手消息状态更新为 `failed`，保存 `error_message`，并向前端发送 `error` 事件。

流式追加需要保证数据一致性。第一版可以采用应用内缓冲加结束落库，或使用数据库原子追加语句（如 PostgreSQL `content = content || :delta`）更新 part 内容；不能采用“先读旧值、拼接、再覆盖写入”的非原子方式。

## 8. 关键接口

建议第一版提供以下接口：

- 查询会话列表。
- 新建会话。
- 删除会话。
- 查询会话消息列表。
- 发送消息并流式返回助手回复。

发送消息接口使用 `fetch` 读取流式响应，响应格式为 `text/event-stream`。请求进入服务端后，服务端基于当前会话已完成消息组装历史上下文，调用 `agentscope-java` 生成当前轮回复。

## 9. 数据库迁移

使用 Flyway 管理数据库结构初始化和后续变更。

第一版迁移脚本负责创建：

- `agent_session`
- `agent_message`
- `agent_message_part`

迁移脚本命名使用 Flyway 标准格式，例如 `V1__init_agent_chat_tables.sql`，后续变更按版本递增。

数据扩展说明：

- 第一版通过 `user_code`、`session_id`、`sequence`、`updated_at` 等索引满足基础查询。
- 分区表、冷热归档、审计事件表和 token 成本统计属于后续演进，不作为第一版上线前置条件。

## 10. 安全、限流与日志

- 开发期前端通过 Vite proxy 访问后端；生产如前后端独立域名部署，需要明确 CORS 白名单，不使用全开放策略。
- 第一版建议预留按 `userCode` 和 `sessionId` 的基础限流策略，防止短时间大量请求绕过前端排队。
- 关键日志至少覆盖鉴权失败、会话锁获取失败、流式开始、流式完成、流式异常、客户端断开和模型调用错误。
- 第一版 `X-Token` 非空校验和 `appCode -> userCode` 只适合内部验证，不构成生产鉴权；生产接入前必须替换真实鉴权、授权和租户隔离。
- 日志默认脱敏 `X-Token`、`Authorization`、`apiKey`、请求头和模型原始异常中的敏感内容。
- thinking、traceId、errorMessage 只能在当前用户上下文中展示或排查，不应跨用户、跨应用或进入公开渠道。

## 11. 后续演进参考

以下能力来自 Hermes Agent 与 OpenClaw 调研，只作为演进方向，不进入 V1 必做范围：

- **Gateway 控制平面**：当系统扩展到多端、多渠道、后台任务或工具调用时，可从 REST + SSE 演进到统一 Gateway / WebSocket 事件协议。
- **Lane Queue**：当前 `tryAcquire + 409` 是 V1 简化的单 lane 串行策略；引入后台任务、工具调用或持久化队列后，可升级为同 session 串行、后台 lane 并行的队列模型。
- **长期记忆与跨会话检索**：优先考虑 PostgreSQL full-text search 与 `pg_trgm`，后续可增加 `message_embedding` 或 `memory_fact` 表实现语义检索。
- **上下文压缩**：压缩应在请求前 preflight 阶段执行，保留最近 N 轮完整消息，将旧消息摘要为一条摘要消息；历史回放仍保留原始消息。
- **Tool / Skill / Plugin 体系**：Tool 表示结构化执行能力，Skill 表示提示词级操作指南，Plugin 表示能力交付单元；后续采用 manifest-first + registry pattern，默认 deny，并配套审批、审计和 sandbox。
- **幂等与步骤级重试**：V1 不自动重试完整流程；后续副作用操作应支持 idempotency key，只重试当前失败步骤，不重复写入用户消息或重复执行工具。
- **子 Agent 委派约束**：如后续支持子 Agent，需限制委派深度、工具白名单、独立预算和结果摘要，避免权限递归放大。

## 12. 部署形态

开发期：

- 后端在 `source/htam-agent-platform` 中独立启动 Spring Boot 应用。
- 前端在 `source/htam-agent-platform-ui` 中通过 Vite dev server 启动。
- Vite 配置代理到后端接口。

生产期：

- 前端执行构建生成静态资源。
- 前后端独立部署；如后续需要，也可以由网关或静态资源服务托管前端构建产物。
- 后端连接 PostgreSQL 并读取环境变量中的模型配置。
