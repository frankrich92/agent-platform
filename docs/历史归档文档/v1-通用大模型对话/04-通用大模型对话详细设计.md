# 通用大模型对话详细设计

> 注意：本文档为历史阶段文档，仅作为需求、调研和演进参考。
> 当前 Agent 中台架构与后续开发以 `docs/v3-agent中台/` 为准。
> AI agent 执行开发任务前必须先阅读 `docs/README.md` 和 V3 架构文档。

## 1. 设计目标

本文档用于指导后端 `source/htam-agent-platform` 和前端 `source/htam-agent-platform-ui` 的实际代码开发。`source/agentscope-demo` 仅作为 `agentscope-java` 已验证样例参考，不修改其代码。

第一版只实现 Web 端通用大模型对话，核心能力包括：

- 基于 URL 中的 `token`、`appCode` 进入系统。
- 前端将身份信息转换为 `X-Token`、`X-App-Code` 请求头。
- 后端校验请求头非空，并将 `appCode` 作为 `userCode` mock 值。
- 用户按 `userCode` 隔离会话和消息。
- 支持会话新建、列表、打开、删除和自动标题。
- 支持多轮对话和基于历史会话继续对话。
- 支持流式输出 thinking 和最终回复。
- 大模型响应中允许用户继续发送消息，但消息先进入前端排队区，待当前回复完成后自动进入下一轮。

## 2. 工程结构

新增前后端分离目录：

```text

├── agent-api/

```

后端使用 JDK 21、Spring Boot 4.0.5、Spring WebFlux、`agentscope-java`、MyBatis-Plus、Flyway、PostgreSQL。前端使用 Vue 3、Vite、Element Plus。

版本基线：

- `source/agentscope-demo` 已验证 Spring Boot 4.0.5 和 `agentscope-java` 1.0.12。
- 第一版以 Spring Boot 4.0.5 起步，父 POM 统一锁定 `agentscope-java` / `agentscope-spring-boot-starter` 为 1.0.12。
- 如果后续升级 Spring Boot 4.0.6，需要先验证 `agentscope-spring-boot-starter` 1.0.12 兼容性。

后端 Maven 模块关系：

- `agent-api`：不依赖 Spring WebFlux，不依赖数据库，沉淀前后端接口契约和通用枚举。
- `agent-core`：依赖 api，负责核心业务、持久化、模型调用。
- `agent-web`：依赖 api 和 core，负责 HTTP/SSE 接入、鉴权过滤器、启动配置。
- `agent-core` 不引入 `spring-boot-starter-webflux`，不得依赖 `ServerHttpRequest`、`ServerHttpResponse`、`ServerSentEvent` 等 Web 层类型；WebFlux 协议对象只允许出现在 `agent-web`。

## 3. 后端模块设计

### 3.0 Maven 多模块约束

父工程 `source/htam-agent-platform/pom.xml`：

- `packaging` 为 `pom`。
- Spring Boot 版本固定为 `4.0.5`。
- JDK 版本固定为 `21`。
- 统一管理 `agentscope-java` 1.0.12、MyBatis-Plus、PostgreSQL Driver、Flyway、测试依赖版本。

模块职责：

```text
agent-api
  对外 DTO/VO、枚举、接口常量。不得依赖 web/core 模块。

agent-core
  业务服务、数据库实体、MyBatis-Plus Mapper、LLM 适配。依赖 api。

agent-web
  Spring Boot 启动模块、Controller、WebFilter、异常处理、配置装配。依赖 api 和 core。
```

依赖方向固定为：

```text
agent-web -> agent-core -> agent-api
agent-web -> agent-api
```

禁止 `api` 反向依赖 `core` 或 `web`。

### 3.1 包职责

```text

  通用响应对象、异常定义、枚举、时间工具。

```

### 3.2 身份上下文

请求头：

- `X-Token`：必填，第一版只校验非空。
- `X-App-Code`：必填，第一版只校验非空，并作为 `userCode`。

后端提供 `UserContext`：

```java
public record UserContext(
        String token,
        String appCode,
        String userCode
) {}
```

WebFlux 过滤器逻辑：

1. 读取 `X-Token`、`X-App-Code`。
2. 任一为空返回 `401`。
3. 构造 `UserContext(token, appCode, appCode)`。
4. 放入 Reactor Context 或 request attribute，Controller/Service 从统一工具中读取。

## 4. 数据库详细设计

### 4.1 agent_session

保存会话元数据。

```sql
create table agent_session (
    id varchar(64) primary key,
    user_code varchar(128) not null,
    parent_session_id varchar(64),
    title varchar(200) not null,
    status varchar(32) not null default 'active',
    message_count integer not null default 0,
    prompt_tokens integer not null default 0,
    completion_tokens integer not null default 0,
    summary_message_id varchar(64),
    last_message_at timestamptz,
    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now()
);

create index idx_agent_session_user_updated
    on agent_session (user_code, status, updated_at desc);
```

字段规则：

- `id` 使用后端生成的字符串 ID，推荐 UUID 或雪花 ID。
- 原型数据结构页与实际实现保持一致，ID 使用 `varchar(64)` 字符串 ID，避免前端处理 JavaScript 大整数精度问题。
- `user_code` 必须来自 `UserContext.userCode`。
- `title` 新会话默认 `新对话`，第一条用户消息写入后按内容截断更新。
- `status = deleted` 表示软删除。原型中的“不可恢复”是用户视角：前端不提供恢复入口，但后端仍保留数据。
- `message_count` 统计真实进入会话的消息数，不统计前端排队但未发送的消息。
- `summary_message_id` 第一版为空，预留上下文压缩。后续启用压缩时，它指向一条摘要消息；该摘要消息之前的历史消息在模型上下文组装时可由摘要替代，但历史回放仍查询原始消息。
- `parent_session_id` 第一版为空，后续用于分支会话、压缩续聊或从历史会话派生新会话的 lineage 关系。

### 4.2 agent_message

保存消息元数据。

```sql
create table agent_message (
    id varchar(64) primary key,
    session_id varchar(64) not null,
    user_code varchar(128) not null,
    sequence integer not null,
    role varchar(32) not null,
    status varchar(32) not null,
    model_name varchar(128),
    finish_reason varchar(64),
    error_message text,
    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now(),
    constraint uk_agent_message_session_sequence unique (session_id, sequence)
);

create index idx_agent_message_session_seq
    on agent_message (user_code, session_id, sequence);
```

字段规则：

- `sequence` 为会话内递增序号，历史回放按 `sequence` 升序。
- `role = user` 时 `model_name`、`finish_reason` 为空。
- `role = assistant` 时记录 `model_name`。
- `status = streaming` 的助手消息表示生成中。
- 服务端组装历史上下文时只使用 `status = completed` 的消息。

### 4.3 agent_message_part

保存消息内容分段。

```sql
create table agent_message_part (
    id varchar(64) primary key,
    message_id varchar(64) not null,
    session_id varchar(64) not null,
    user_code varchar(128) not null,
    part_sequence integer not null,
    part_type varchar(32) not null,
    content text not null default '',
    status varchar(32) not null,
    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now(),
    constraint uk_agent_message_part_message_sequence unique (message_id, part_sequence)
);

create index idx_agent_message_part_message_seq
    on agent_message_part (user_code, message_id, part_sequence);
```

Flyway 迁移脚本放在 `agent-web/src/main/resources/db/migration/`，命名使用 `V版本号__描述.sql` 格式，例如：

```text
V1__init_agent_chat_tables.sql
V2__add_agent_chat_indexes.sql
```

字段规则：

- 用户消息写一条 `part_type = text`。
- 助手消息最多写一条 `part_type = thinking` 和一条 `part_type = text`。
- 第一版同类型流式内容聚合追加到同一 part，降低数据库写入量。
- 后续如果要精确回放每个 chunk，可以改为每个 chunk 写一条 part。

### 4.4 事务与并发

同一会话必须串行处理服务端生成请求：

- 查询并锁定当前会话，确认 `user_code` 匹配。
- 获取当前最大 `sequence`。
- 写入用户消息和用户 text part。
- 写入助手消息，状态为 `streaming`。
- 流式过程中追加助手 parts。
- 完成后更新助手消息状态、会话统计和时间。

服务端需要防止同一 `session_id` 同时存在多个 `streaming` 助手消息。实现方式：

- 前端排队是主策略，服务端锁是兜底防线，用于处理前端异常、多标签页并发、重复点击或接口重放。
- 第一版推荐在应用内使用 `ConcurrentHashMap<String, Semaphore>` 按 `userCode + sessionId` 串行化发送接口。
- 锁获取使用 `tryAcquire` 非阻塞方式；获取失败立即返回 `409`，不能在 Netty 事件循环线程中阻塞等待。
- 如果确实采用阻塞等待，必须通过 `Schedulers.boundedElastic()`、虚拟线程或专用阻塞任务执行器调度。
- MyBatis-Plus 是同步 JDBC ORM，数据库读写同样不能直接阻塞 WebFlux 事件循环线程。
- 后续多实例部署时改为 PostgreSQL advisory lock 或 Redis 分布式锁。
- 当前策略对应 OpenClaw Lane Queue 中的单 lane 串行简化版：V1 失败即返回 `409`，不做服务端持久化排队。后续引入后台任务、工具调用或跨端队列后，再升级为 per-session lane queue。
- 服务端锁只限制同一 `userCode + sessionId`，不同会话可以并行生成。

标题更新与第一条用户消息写入应在同一业务流程中完成。推荐使用条件更新：

```sql
update agent_session
set title = :newTitle, updated_at = now()
where id = :sessionId
  and user_code = :userCode
  and title = '新对话'
```

标题生成规则为直接取第一条用户消息前 30 个字符，第一版不做语义摘要或按标点智能截断。

流式 part 内容追加必须使用并发安全策略：

- 方案一：应用层按当前请求维护 `StringBuilder`，流式过程中更新内存和前端，流结束时一次性写入最终 thinking/text 内容。
- 方案二：流式过程中使用数据库原子追加语句，例如 PostgreSQL `update ... set content = content || :delta`。
- 不能采用“先查询旧 content、应用层拼接、再覆盖 update”的非原子写法。

应用启动或定时任务需要清理超时 `streaming` 消息：将超过阈值仍未完成的助手消息标记为 `failed`，写入 `error_message`，避免历史会话长期展示生成中状态。

## 5. API 详细设计

所有 API 都要求请求头：

```http
X-Token: <token>
X-App-Code: <appCode>
```

统一错误响应：

```json
{
  "code": "UNAUTHORIZED",
  "message": "X-Token and X-App-Code are required",
  "traceId": "optional-trace-id"
}
```

API 响应约定：

- `2xx` 直接返回业务数据，不使用统一外层包裹。
- `4xx/5xx` 返回统一错误对象，前端按 HTTP 状态码进入错误解析流程。
- 流式接口在 HTTP 建连失败时按普通错误对象处理；建连成功后的生成异常通过 SSE `error` 事件返回。

### 5.2 新建会话

```http
POST /api/agent/sessions
Content-Type: application/json
```

请求：

```json
{
  "title": "新对话"
}
```

响应：

```json
{
  "id": "session-id",
  "title": "新对话",
  "status": "active",
  "messageCount": 0
}
```

`title` 可省略，默认 `新对话`。

### 5.3 删除会话

```http
DELETE /api/agent/sessions/{sessionId}
```

行为：

- 只允许删除当前 `userCode` 下的会话。
- 与原型删除确认一致，第一版对用户表现为不可恢复删除。
- 后端实际执行软删除，将 `agent_session.status` 更新为 `deleted`。
- 第一版不物理删除 `agent_message` 和 `agent_message_part`，用于审计、排查和后续可能的后台恢复。
- 删除前必须按 `user_code` 和 `session_id` 校验归属，禁止跨用户删除。

### 5.5 发送消息并流式返回

```http
POST /api/agent/sessions/{sessionId}/messages/stream
Content-Type: application/json
Accept: text/event-stream
```

请求：

```json
{
  "content": "请基于上面的方案继续说明前端排队怎么实现"
}
```

SSE 响应事件：

```text
event: meta
data: {"sessionId":"s1","userMessageId":"m1","assistantMessageId":"m2"}

event: thinking
data: {"delta":"先判断当前会话是否已有响应中消息..."}

event: message
data: {"delta":"前端需要维护一个 pendingQueue..."}

event: done
data: {"finishReason":"stop"}
```

错误事件：

```text
event: error
data: {"code":"LLM_STREAM_FAILED","message":"模型响应失败，请稍后重试"}
```

接口行为：

1. 校验请求头和会话归属。
2. 获取会话锁。
3. 校验 `content` 非空，最大长度第一版为 8000 个 Unicode 字符；校验在 Controller DTO 校验和 Service 入口各保留一层兜底。
4. 写入用户消息和用户 text part。
5. 如果会话标题为 `新对话`，使用用户第一条消息截断生成标题，最大 30 字符。
6. 创建助手消息，状态 `streaming`。
7. 返回 `meta` 事件。
8. 查询当前会话 `completed` 历史消息，组装多轮上下文。
9. 调用 `agentscope-java` stream。
10. 收到 thinking 增量，写入/追加 thinking part，并发送 `thinking` 事件。
11. 收到文本增量，写入/追加 text part，并发送 `message` 事件。
12. 正常结束时更新助手消息为 `completed`，更新会话统计，发送 `done`。
13. 异常时更新助手消息为 `failed`，保存 `error_message`，发送 `error`。
14. 释放会话锁。

校验失败响应：

- `content` 为空：HTTP `400`，错误码 `CONTENT_EMPTY`。
- `content` 超过 8000 字符：HTTP `400`，错误码 `CONTENT_TOO_LONG`。
- 同一会话已有请求处理中：HTTP `409`，错误码 `SESSION_BUSY`。
- 前端排队超过上限：不请求服务端，前端错误码或状态使用 `QUEUE_LIMIT_EXCEEDED`。

## 6. LLM 适配设计

### 6.1 配置

敏感值统一写入 `source/htam-agent-platform/.env`。`application.yml` 只引用环境变量和非敏感默认值：

```yaml
spring:
  config:
    import: optional:file:.env[.properties]
  datasource:
    url: ${HTAM_DB_URL}
    username: ${HTAM_DB_USERNAME}
    password: ${HTAM_DB_PASSWORD}

htam:
  llm:
    provider: ${HTAM_LLM_PROVIDER:openai-compatible}
    api-mode: ${HTAM_LLM_API_MODE:chat_completions}
    base-url: ${HTAM_LLM_BASE_URL}
    api-key: ${HTAM_LLM_API_KEY}
    model-name: ${HTAM_LLM_MODEL_NAME:ark-code-latest}
    stream: true
    thinking-budget: ${HTAM_LLM_THINKING_BUDGET:1024}
    system-prompt: ${HTAM_LLM_SYSTEM_PROMPT:You are a helpful AI assistant. Be concise, accurate, and explain reasoning when useful.}
```

配置类：

```java
@ConfigurationProperties(prefix = "htam.llm")
public class LlmProperties {
    private String provider = "openai-compatible";
    private String apiMode = "chat_completions";
    private String baseUrl;
    private String apiKey;
    private String modelName;
    private boolean stream = true;
    private Integer thinkingBudget = 1024;
    private String systemPrompt;
}
```

### 6.1.1 Provider 适配接口

V1 通过 `LlmProviderAdapter` 隔离业务服务和具体模型调用实现。第一版只提供 `OpenAiCompatibleAdapter`，内部使用 `agentscope-java`。

```java
public interface LlmProviderAdapter {
    String provider();

    Flux<LlmStreamEvent> stream(ChatRequestContext context, List<LlmMessage> messages);

    Mono<String> complete(ChatRequestContext context, List<LlmMessage> messages);
}
```

接口约束：

- `stream` 输出统一的 `LlmStreamEvent`，由适配层处理不同 provider 的 thinking/text 字段差异。
- `complete` 预留给标题生成、摘要、上下文压缩等非流式辅助任务；V1 标题不调用模型，可以先不使用。
- 显式配置的 provider 或 apiMode 无法解析时应 fail closed，返回配置错误，不静默回退到其他 provider。

### 6.2 上下文组装

只使用当前会话中 `status = completed` 的消息：

- `user` 消息取 `part_type = text`。
- `assistant` 消息取 `part_type = text`。
- `thinking` 不进入下一轮模型上下文，避免把模型推理过程当作业务事实重复注入。

上下文顺序：

1. 系统提示词。
2. 历史 `user/assistant` 文本消息。
3. 当前用户消息。

默认系统提示词：

```text
You are a helpful AI assistant. Be concise, accurate, and explain reasoning when useful.
```

系统提示词从 `htam.llm.system-prompt` 读取，允许通过环境变量覆盖，不在业务代码中硬编码。

会话内 Prompt 稳定性：

- 当前会话开始后，系统级 prompt 在当前生成链路中保持稳定。
- 后续如引入用户偏好、长期记忆、项目上下文或工具说明，默认在新会话或新上下文窗口中生效，避免每轮动态修改系统 prompt。

上下文组装由 `ContextAssembler` 承担：

```java
public interface ContextAssembler {
    List<LlmMessage> assemble(ChatRequestContext context, String currentUserContent);
}
```

V1 组装规则：

- 只读取当前会话中 `status = completed` 的消息。
- 用户消息取 `part_type = text`。
- 助手消息取 `part_type = text`。
- thinking 不进入下一轮上下文。
- 当前用户消息追加在历史消息之后。
- 暂不做压缩、检索和摘要，但预留 `ContextBudgetEstimator` 用于后续 token 估算。

数据库消息到 agentscope-java `Msg` 的映射：

- 系统提示词：按 agentscope-java 支持方式构造 system 消息或传入模型调用选项；如果当前 API 不支持独立 system 角色，则在适配层明确记录降级策略。
- 用户消息：`Msg.builder().role(MsgRole.USER).content(TextBlock.builder().text(content).build()).build()`。
- 助手消息：`Msg.builder().role(MsgRole.ASSISTANT).content(TextBlock.builder().text(content).build()).build()`。
- `thinking` part 不进入下一轮上下文。
- 只使用 `completed` 状态消息组装上下文；`streaming`、`failed` 消息不参与模型输入。

### 6.3 agentscope-java 流式事件映射

参考 `source/agentscope-demo` 的 stream 调用方式：

- `ThinkingBlock` 映射为 SSE `thinking`。
- `TextBlock` 映射为 SSE `message`。
- 流完成映射为 SSE `done`。
- 异常映射为 SSE `error`。

`includeReasoningResult` 第一版设为 `false`，避免 thinking 被混入最终回复；最终以独立 `thinking` part 展示和保存。

适配层要求：

- 对每个 stream 事件中的 `Msg.getContent()` 列表逐个判断 `ContentBlock` 类型，同一个事件中可能同时存在 `ThinkingBlock` 和 `TextBlock`。
- 不使用 demo 中 `MsgUtils.getTextContent()` 的拼接结果作为正式 SSE 输出，因为它会混合 thinking 和最终回复。
- 使用 `StreamOptions.incremental(true)`，同时兼容模型或版本返回累计文本的情况；如果当前块内容以前一次完整内容为前缀，则只取新增 delta，避免重复追加。
- agentscope 调用属于可能阻塞或长时间运行的操作，必须在适合阻塞任务的调度器或虚拟线程中执行。

### 7.4 发送与排队流程

用户点击发送或按 Enter：

1. 输入为空则忽略。
2. `isStreaming = false`：
   - 输入内容立即追加为本地用户消息。
   - 调用流式接口。
   - `isStreaming = true`。
3. `isStreaming = true`：
   - 不追加到消息列表。
   - 不请求服务端。
   - 将文本加入 `queuedPrompts`。
   - 在输入框上方展示排队消息。

当前流结束：

1. 收到 `done` 后将当前助手消息置为 `completed`。
2. `isStreaming = false`。
3. 如果 `queuedPrompts` 不为空：
   - 取出队首。
   - 自动调用发送流程。
   - 进入下一轮。

排队消息允许用户移除。第一版不做拖拽排序。

排队边界：

- 排队消息只保存在前端内存状态，不写入数据库；刷新、关闭页面或浏览器会话丢失时不恢复。
- 第一版排队数量上限为 10 条；超过上限时不入队，前端使用 `QUEUE_LIMIT_EXCEEDED` 状态提示用户等待当前回复完成。
- 自动发送队首消息失败时，该消息进入消息列表并展示为发送失败或助手失败状态，提供重试入口，不静默丢弃，也不自动无限重试。
- 自动发送过程中如果用户继续发送消息，仍然追加到同一个 `queuedPrompts` 队尾，保持 FIFO 顺序。
- 排队等待时间超过阈值时建议记录前端埋点或日志，便于后续判断是否需要升级为持久化 Lane Queue。

### 7.5 fetch 流式解析

前端不能用 `EventSource`，因为需要带自定义请求头。使用 `fetch`：

```ts
const response = await fetch(url, {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Accept': 'text/event-stream',
    'X-Token': auth.token,
    'X-App-Code': auth.appCode
  },
  body: JSON.stringify({ content })
})
```

使用 `ReadableStreamDefaultReader` 读取响应，按 SSE 格式解析：

- 遇到 `event: meta`，保存服务端消息 ID。
- 遇到 `event: thinking`，追加到当前助手消息 `thinking` part。
- 遇到 `event: message`，追加到当前助手消息 `text` part。
- 遇到 `event: done`，结束当前轮。
- 遇到 `event: error`，标记当前助手消息失败并展示错误。

abort 与解析异常：

- 每次流式请求创建并保存 `AbortController`。
- 用户切换会话、删除当前会话、刷新前清理或主动停止当前本地流时，调用 `abortController.abort()`。
- `AbortError` 不作为普通模型错误重复弹窗，但当前未完成助手消息需要展示为已中断或失败态。
- SSE 解析遇到格式异常、JSON 解析失败、HTTP 非 2xx 或 reader 异常时，当前助手消息标记为 `failed`，展示错误摘要，并释放 `isStreaming`。
- 后端通过 WebFlux `doOnCancel()` 感知客户端断开，取消下游模型调用、更新消息状态并释放会话锁。

### 8.1 主布局

- 原型侧边栏包含搜索输入框。搜索不属于第一版需求，实现时作为禁用或静态占位，不接后端搜索接口。

- 原型中的“今天 / 昨天 / 过去7天”是前端展示分组。后端仍按 `updated_at desc` 返回普通列表，前端基于客户端本地日期对 `updatedAt` 计算分组。

### 8.2 页面状态

原型覆盖以下页面状态，开发时需要至少实现对应状态或等价交互：

- `欢迎态`：无当前消息时显示欢迎区域，引导用户开始新对话。
- `聊天态`：展示历史用户消息、助手 thinking、助手最终回复。
- `流式响应态`：助手消息为 `streaming`，thinking 和 text 区域显示光标。
- `排队态`：当前响应未完成时，用户再次发送的消息展示在输入框上方排队区，不进入消息列表。
- `历史续聊态`：从侧边栏打开历史会话后，历史消息完整展示，并可继续发送新问题。
- `删除确认态`：点击删除后弹出确认，不直接删除；确认后对用户表现为不可恢复，后端执行软删除。
- `助手失败态`：助手消息 `status = failed` 时，在消息列表中展示错误摘要和重试入口。
- `鉴权失败态`：缺少 `token` 或 `appCode` 时展示错误页面和正确入口示例。
- `接口流程说明态`、`数据结构说明态`：属于原型说明页，不进入正式产品路由，但其流程和表结构应作为开发参考。

正式产品路由建议：

```text
/
  读取 token/appCode；合法时进入对话页，缺失时展示鉴权失败态。

/chat
  对话主页面。第一版也可以只使用根路径承载。
```

### 8.3 thinking 展示

- thinking 是助手消息的一部分。
- thinking 与最终回复视觉分离。
- thinking 使用原型中的可折叠区域展示，标题显示 `thinking` 或 `思考过程`。
- 流式生成中默认展开。
- 完成后仍可查看。
- 用户可以手动折叠/展开 thinking。

### 8.4 排队区展示

排队区位置固定在输入框上方。展示规则：

- 仅当 `queuedPrompts.length > 0` 时显示。
- 每条排队消息展示 `排队中` 标识。
- 每条排队消息提供移除按钮。
- 排队消息不显示在消息列表中，也不写入数据库。
- 当前回复完成后，队首消息自动进入发送流程。
- 如果自动发送过程中失败，该消息进入消息列表失败态并提供重试入口，不重新回到排队区，不静默丢弃。

### 8.5 删除确认

原型使用确认弹窗表达删除行为。实现规则：

- 点击侧边栏删除按钮时，弹出确认框。
- 弹窗显示会话标题。
- 点击取消关闭弹窗。
- 点击删除后调用 `DELETE /api/agent/sessions/{sessionId}`。
- 删除成功后从侧边栏移除该会话。
- 如果删除的是当前会话，切换到最近一个会话；没有会话时进入欢迎态。
- 删除对用户不可恢复，但后端为软删除，普通会话列表不返回 `status = deleted` 的会话。

### 8.6 错误展示

- 鉴权失败：缺少 `token` 或 `appCode` 时，前端展示无法进入对话，并提示正确入口示例；第一版不提供页面内手动输入 token/appCode。
- 第一版鉴权只做非空校验，适用于内部验证和调用方联调，不构成生产级账号、租户或权限边界。
- 服务端返回 `401` 时，前端清理本地身份状态并展示鉴权失败态，便于后续真实鉴权接入。
- 流式失败：当前助手消息展示失败状态和错误摘要。
- SSE 解析失败或客户端主动中断：当前助手消息展示失败或已中断状态，释放输入区。
- 会话不存在或无权限：返回列表页或创建新会话。

### 8.7 日志与脱敏

- 服务端日志不得输出完整 `X-Token`、`Authorization`、模型 `apiKey` 或完整请求头。
- 模型原始异常进入日志前需要摘要化，避免泄漏上游密钥、用户输入或供应商返回的敏感内容。
- thinking、traceId、errorMessage 只能在当前用户上下文中展示或用于内部排查，不得跨用户、跨应用或进入公开渠道。
- 关键日志保留事件类型、sessionId、messageId、userCode 摘要、错误码、耗时和 traceId。

### 11.1 后端测试

- 无 `X-Token` 返回 `401`。
- 无 `X-App-Code` 返回 `401`。

- 日志脱敏 `X-Token`、`Authorization`、`apiKey` 和模型原始异常中的敏感内容。
- `.env` 中 LLM 配置有效时，真实模型 smoke 测试可以收到可解析的流式响应。

### 11.2 前端测试

- URL 中 `token/appCode` 能写入 sessionStorage。
- API 请求携带 `X-Token/X-App-Code`。
- 会话列表可加载、切换、新建、删除。
- 历史消息可恢复展示。
- thinking 与最终回复分区展示。
- 响应中再次发送消息时进入排队区。
- 当前轮完成后排队消息自动发送。
- 排队消息可以移除。
- 流式错误能展示失败状态。
- 自动发送失败时，失败消息保留在消息列表中并提供重试入口。
- 切换会话时可以 abort 当前流式请求，并释放输入状态。
- 搜索框作为禁用占位，不触发接口请求。
- 模型标签展示配置模型名，不写死具体模型。
- 排队超过 10 条时提示 `QUEUE_LIMIT_EXCEEDED`，不继续入队。

### 11.3 联调场景

- 新用户通过 `/?token=t1&appCode=app-a` 进入，创建会话并发送第一条消息。
- 使用 `.env` 中的真实 LLM 配置调用实际大模型服务，不使用 mock provider。
- 在模型响应中连续发送两条消息，两条消息依次排队并自动进入后续轮次。
- 刷新页面后重新打开会话，历史消息、thinking 和最终回复完整恢复。
- 换成 `appCode=app-b` 后无法看到 `app-a` 的会话。
- 前端异常并发调用同一会话流式接口时，后端只允许一个请求进入生成流程。
- 模型调用超时或 SSE 中断时，前端展示失败态，后端释放锁。
- 基础并发基准：多用户不同会话并发请求时不互相阻塞；同一会话串行化生效。

## 12. 非首版范围

以下能力不在第一版实现：

- 正式账号体系。
- 真实鉴权服务接入。
- 会话搜索、置顶、归档、手动重命名。
- 停止生成按钮。
- 模型切换。
- 多模态输入输出。
- 历史会话检索。
- 跨会话长期记忆。
- 上下文压缩与自动摘要。
- 多入口接入（API、移动端、WebSocket 或消息渠道）。
- 移动端原生 App。
- 桌面客户端。
- Agent 工具管理。
- 插件化能力管理。
- 子 Agent 委派与多 Agent 编排。
- 定时自主任务或主动触发任务。
- 平台级 Agent 编排和管理能力。
- `agent_session_event` JSONL 风格事件日志。

后续数据与运行时预留：

- `source_type` 可作为后续字段标识会话来源，例如 `WEB`、`API`、`MOBILE`。
- `message_embedding` 或 `memory_fact` 可作为后续表承载语义检索和长期记忆。
- 工具执行能力必须先设计 ToolPolicy、审批、审计和 sandbox，不直接复用 V1 对话链路。
