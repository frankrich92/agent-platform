## 总体评价

四份文档形成了较完整的"需求 → 技术方案 → 原型 → 详细设计"链路，层次清晰，追溯性好。本次评审新增**第五章「业界参考」**，通过对比 OpenCode、Codex、Claude Code、DeepSeek Chat 四款产品的实现模式，验证当前设计决策的合理性并发现可借鉴的最佳实践。

主要优点：
- 需求文档明确划定了第一版边界和非首版范围，有效防止范围蔓延。
- 技术方案提出的 parts 化存储模型和 JSONL 对比说明有深度，与 OpenCode 的 12 类 Part 系统理念一致。
- 详细设计覆盖了前端状态管理、API 契约、并发控制、测试计划等关键细节。
- 原型覆盖了 8 种以上页面状态，交互表达充分。
- **业界验证**：SSE 事件分离 thinking/message 的方案优于 DeepSeek 生态的 XML 标签解析方式；parts 化存储与 OpenCode/Codex 的主流做法方向一致。

存在的主要问题：**四份文档之间存在若干不一致**，**部分关键细节缺失**，**异步排队方案的异常路径缺少设计**。与业界对标后发现的**新增差距**：缺少"停止生成"中断机制、SSE 心跳保活、消息级 token 统计。

## 一、01-通用大模型对话需求.md

### 1.1 优点

- **边界清晰**：第 7 节明确列出非首版范围（共 12 项），有效管理预期。
- **用户故事完整**：覆盖了创建/打开/删除会话、发送消息、流式返回、thinking 展示、历史续聊等核心路径。
- **鉴权方案务实**：第一版采用最小鉴权（非空校验 + appCode 作为 userCode mock），避免过度工程。
- **排队语义明确**：第 2 节和第 6 节清晰地定义了"响应中发送消息 → 进入排队 → 完成后自动发送"的交互规则，并强调"不立即请求服务端"。

### 1.2 问题

#### 1.2.1 排队消息的持久化边界不明确

需求文档第 6 节提到排队消息"不立即请求服务端"，但未说明：
- **排队消息是否持久化？** 页面刷新后排队消息是否丢失？如果丢失，用户是否知情？
- **排队消息的移除行为**：需求未提及用户能否移除排队消息。详细设计中允许移除，但需求文档应包含此能力描述。

**建议**：明确排队消息为临时前端状态，刷新后丢失，且为用户可知的行为。

#### 1.2.2 会话删除语义需要澄清

第 5 节"删除会话"未说明是物理删除还是逻辑删除，也未说明删除后数据是否可恢复。详细设计中明确为软删除（`status = deleted`），但需求应对用户视角的删除行为做出说明。

**建议**：补充"删除为不可撤销操作，已删除会话不再出现在列表中"的声明。

#### 1.2.3 thinking 内容的显示策略不完整

需求说"thinking 内容作为辅助信息展示，不能影响用户继续发送消息和阅读最终回复"，但未说明：
- thinking 默认展开还是折叠？
- 用户能否手动折叠/展开？
- thinking 是否需要流式展示？

**建议**：在页面体验章节补充 thinking 的交互规则。

#### 1.2.4 自动标题生成规则模糊

需求说"基于用户第一条消息截断生成"，但未定义截断长度、截断策略（字符数 vs 字节数），也未说明标题何时生成（消息发送后立即？还是回复完成后？）。

**建议**：补充"取前 30 个字符"之类的具体规则。

### 1.3 综合评价

| 维度 | 评分 | 说明 |
|------|------|------|
| 完整性 | ★★★★☆ | 核心功能覆盖良好，边界交互略有缺失 |
| 清晰性 | ★★★★☆ | 表述清晰，排队语义尤为出色 |
| 可行性 | ★★★★★ | V1 范围控制合理，技术选型务实 |

## 二、02-通用大模型对话技术方案.md

### 2.1 优点

- **parts 化存储的对比分析出色**（第 6 节末尾）：将 parts 模型与 Codex JSONL 事件流做了详细对比，说明了各自适用场景和后期演进路径。这是整个方案中最有价值的分析段落。
- **流式接口设计合理**：明确了使用 `fetch` 而非 `EventSource` 的原因（需要自定义请求头），SSE 事件类型设计清晰。
- **数据库设计有前瞻性**：`parent_session_id`、`summary_message_id`、`prompt_tokens`/`completion_tokens` 等字段预留了后续分支对话、压缩和成本分析等需求。
- **工程约束明确**：技术栈版本（JDK 21、Spring Boot 4.0.6）均已固定。

### 2.2 问题

#### 2.2.1 "同一会话串行处理"的实现方式有缺陷

技术方案提到"控制同一会话内的服务端处理顺序，避免并发请求打乱上下文"，但在详细设计中才补上 `ConcurrentHashMap<String, Semaphore>` 方案。技术方案层面应至少描述并发控制的思路。

更严重的问题——前端已设计排队队列，理论上不会同时发送两个请求。服务端并发控制应是最后一道防线，但方案未讨论：
- 如果前端 bug 导致并发请求到达服务端，`409` 的返回如何处理？
- 排队消息的自动发送是否会有竞态？

**建议**：补充"前端排队是主策略，服务端锁是兜底"的说明。

#### 2.2.2 缺少错误处理的技术策略

方案描述了正常流程（thinking → message → done），但未说明：
- LLM 调用中途失败时，已产生的 thinking 和 message 增量是否保留？
- 重试策略是什么？前端还是后端负责重试？
- 流中断时前端如何感知（连接断开 vs error 事件）？

**建议**：增加错误处理与重试策略一节。

#### 2.2.3 数据分区与扩展性考虑不足

方案中所有表都按 `userCode` 隔离，但由于第一版 `userCode = appCode`，实际隔离粒度是整个应用。如果后续接入真实鉴权，`userCode` 可能变为用户级，大量用户共用一个 `appCode`。方案未讨论数据量增长后的索引策略或分区方案。

**建议**：补充数据库扩展考虑，哪怕标记为"后续版本"。

#### 2.2.4 前端技术方案缺少组件状态细节

前端设计描述了布局和交互规则，但缺少：
- Vue Router 路由设计
- Pinia store 的结构设计
- 流式解析的 abort 策略（用户切换会话时如何取消正在进行的流）

**建议**：补充前端架构图和组件树。

### 2.3 综合评价

| 维度 | 评分 | 说明 |
|------|------|------|
| 完整性 | ★★★☆☆ | 正常流程完整，异常路径缺失 |
| 清晰性 | ★★★★☆ | 数据设计分析出色，工程约束明确 |
| 可行性 | ★★★★☆ | 技术选型合理，部署方案清晰 |

## 三、03-原型设计 (chat-prototype.html)

### 3.1 优点

- **状态覆盖全面**：原型包含 8 个页面状态——欢迎态、聊天态（含 thinking）、流式生成态、排队态、删除确认态、数据结构说明态、接口流程说明态、鉴权失败态。
- **交互细节丰富**：thinking 可折叠、排队消息可移除、删除弹窗确认、流式光标闪烁、移动端响应式等均已表达。
- **深色主题完整**：CSS 变量体系设计良好，便于后续主题切换。
- **侧边栏折叠有移动端预留**：通过 `@media (max-width: 768px)` 实现了移动端侧边栏滑动交互。

### 3.2 问题

#### 3.2.1 原型与需求/详细设计存在不一致

| 问题点 | 原型表现 | 需求/设计约定 | 严重程度 |
|--------|---------|-------------|---------|
| 搜索框 | 侧边栏展示搜索输入框 | 非首版范围，明确不做 | **中等** |
| Model badge | 顶部显示 `GLM-4` | 第一版无模型切换，模型名应来自配置 | **轻微** |
| 会话分组标签 | `今天`、`昨天`、`过去7天` | 需求未定义分组规则，详细设计按 `updated_at desc` 简单排序 | **轻微** |

**关于搜索框**：原型包含搜索输入框，但需求文档第 7 节明确"会话搜索"不在第一版。详细设计 8.1 节也明确"搜索不属于第一版需求，实现时作为禁用或静态占位"。原型应注明该控件为预留占位而非首版功能，或直接移除避免误导。

#### 3.2.2 移动端响应式实现不足

原型中移动端使用了 `transform: translateX(-100%)` 滑动显示侧边栏，但缺少：
- 手势滑动触发（仅有 JS 调用 `openSidebar()`/`closeSidebar()`）
- 遮罩层的 `touchstart` 事件处理
- 安全区域适配（iPhone 底部 Home Indicator）

**建议**：在原型代码注释中注明"移动端手势交互待实际开发补充"。

#### 3.2.3 排队消息区的视觉区分不够

排队消息使用黄色系（`--queue-bg: #2a2a1a`），在深色主题中与聊天区域颜色接近（`--chat-bg: #212121`），视觉区分度不够明显。

**建议**：增强排队区的视觉权重（加大 padding、增加 icon、使用更鲜明的边框色）。

#### 3.2.4 数据结构和接口说明页是静态 HTML

原型中的"数据结构说明"和"接口流程说明"页面是静态示意，其内容应与 04 详细设计保持一致。当前原型中的示例数据（如 `BIGINT` ID、`GLM-4` 模型名）与实际设计（`varchar(64)` ID、`ark-code-latest` 默认模型）不一致。

**建议**：在原型中更新示例数据以匹配详细设计，或添加注释说明"数据为示意，以详细设计为准"。

### 3.3 综合评价

| 维度 | 评分 | 说明 |
|------|------|------|
| 完整性 | ★★★★☆ | 状态覆盖全面 |
| 一致性 | ★★★☆☆ | 搜索框等细节与需求/设计不匹配 |
| 可用性 | ★★★★☆ | 交互细节到位，移动端有基础支持 |

## 四、04-通用大模型对话详细设计.md

### 4.1 优点

- **工程结构设计清晰**：Maven 三模块划分（api/core/web）依赖方向明确，`agent-api` 不依赖 WebFlux 和数据库的设计合理。
- **数据库设计翔实**：三张表的 DDL、索引、字段规则、保存/查询逻辑完整。ID 使用 `varchar(64)` 而非 `BIGINT` 的决策有明确说明（JavaScript 大整数精度问题）。
- **API 契约完整**：每个接口均有请求/响应示例、错误码、SSE 事件格式。
- **并发控制有实现方案**：`ConcurrentHashMap<String, Semaphore>` + `409` 返回，并标注了后续多实例的演进方向（PostgreSQL advisory lock / Redis）。
- **测试计划覆盖三层**：后端单元测试、前端测试、联调场景均有具体用例。
- **Thinking 不与最终回复混淆**：`includeReasoningResult = false` + thinking 不进入下一轮上下文的决策正确。

### 4.2 问题

#### 4.2.1 严重：排队消息自动发送的异常处理缺失

详细设计 7.4 节描述：

> 当前流结束后，如果 `queuedPrompts` 不为空，取出队首，自动调用发送流程。

但缺少以下关键异常路径的设计：

1. **自动发送失败**（例如网络断开、服务端返回错误）：当前排队消息如何处理？是标记失败后继续发送下一条，还是全部丢弃？
2. **用户在自动发送过程中关闭页面**：未发送的排队消息是否丢失？是否需要 `beforeunload` 提示？
3. **自动发送过程中的流式响应再次出现并发排队**：如果队首消息的 LLM 响应中用户又发送了消息，形成嵌套排队，队列逻辑是否正确？

8.4 节提到"如果自动发送过程中失败，该消息进入正常错误处理，不重新回到排队区"，这个处理不够充分——用户的消息丢失了却没有任何提示或重试入口。

**建议**：为自动发送失败设计明确的 fallback：将失败的消息回退到消息列表显示为"发送失败"状态，并提供重试按钮，而不是静默丢弃。

#### 4.2.2 严重：流式写入策略存在数据一致性问题

详细设计 4.4 节描述了串行操作流程（加锁 → 写用户消息 → 写助手消息 → 流式追加 parts → 完成），但流式写入中的 parts 追加是分步进行的。如果进程在流式写入中途崩溃：

- `agent_message` 状态为 `streaming`，但 parts 可能不完整。
- 下次用户打开会话时，这条 `streaming` 消息如何展示？是否需要后台清理 job？

**建议**：
- 增加应用启动时清理 `status = streaming` 的超时消息逻辑。
- 或设计为：在 `meta` 事件返回后才开始流式响应，如果前端未收到 `meta` 则整个流无效。

#### 4.2.3 中等：自动标题生成时机与并发竞态

4.4 节事务与并发描述中要求"获取当前会话锁 → 写用户消息 → 写助手消息 → 流式 → 完成"。但自动标题生成需要读取"第一条用户消息"来判断。如果两个请求几乎同时到达（排队逻辑故障时），可能存在：

1. 请求 A 获取锁，写入消息，标题还是"新对话"。
2. 请求 A 还在流式生成中。
3. 请求 A 完成后更新标题。
4. 但标题更新不在事务内。

**建议**：标题更新与消息写入放在同一事务内，或使用独立的乐观锁字段。

#### 4.2.4 中等：前端 abort 处理不完整

7.5 节描述了 `fetch` 流式解析的 happy path，但未说明：

- 用户切换会话时如何 abort 当前 fetch（需要保存 `AbortController` 引用）。
- abort 后服务端是否感知（连接断开 → 是否触发流失败处理）。
- SSE 解析错误时（格式异常）的前端 fallback。

**建议**：补充 abort 策略和 SSE 解析的 robust 处理。

#### 4.2.5 中等：鉴权失败的页面设计缺陷

8.1 节提到"缺失时展示鉴权失败态"，原型有对应的 auth 页面。但前端路由设计（8.1 节）只提到：

```
/ → 读取 token/appCode；合法时进入对话页，缺失时展示鉴权失败态
```

缺少以下细节：
- 鉴权失败态是否允许用户手动输入 token/appCode？还是只能通过 URL 参数进入？
- 如果 token 被服务端拒绝（非空但无效），前端如何处理？

第一版 token 只做非空校验，不存在"无效 token"的场景，但设计应预留扩展点。

#### 4.2.6 轻微：测试计划缺少性能基准

11 节测试计划覆盖了功能场景，但缺少：
- 流式响应的首 token 延迟要求
- 并发会话数上限
- 消息历史加载的性能目标

对第一版而言这些问题不是 blocker，但建议标注"后续版本补充性能测试"。

#### 4.2.7 轻微：缺少日志与监控设计

详细设计未涉及：
- 关键操作的日志级别和格式（如 LLM 调用耗时、token 消耗）
- 错误追踪的 traceId 透传（API 响应中有 `traceId` 字段但未说明生成和透传方式）

### 4.3 综合评价

| 维度 | 评分 | 说明 |
|------|------|------|
| 完整性 | ★★★★☆ | API 和数据设计翔实，异常路径有遗漏 |
| 清晰性 | ★★★★★ | 接口契约、数据库设计、状态流转表达优秀 |
| 一致性 | ★★★★☆ | 与需求/技术方案基本对齐，搜索框等细节已标注 |

## 五、业界参考：主流 Agent / 对话产品的实现模式

为验证当前设计方案的合理性并发现可借鉴的最佳实践，对四类产品进行了调研：

| 产品 | 类型 | 协议 | 思维/推理展示 | 会话模型 |
|------|------|------|-------------|---------|
| **OpenCode** (sst/opencode) | CLI+Web Agent | REST + SSE | `ReasoningPart` 独立 part 类型，流式 delta 更新 | Session → Message → 12 种 Part |
| **Codex** (OpenAI) | CLI Agent | JSON-RPC 2.0 双向 | `reasoning` item 类型，summary + raw 双通道流式 | Thread → Turn → Item（原子单元） |
| **Claude Code** (Anthropic) | CLI Agent | SSE / stream-json | `thinking` content block，支持 `display: "omitted"` 跳过 | Session（复用 Claude API content blocks） |
| **DeepSeek Chat** | Web 对话 | SSE (OpenAI 兼容) | `reasoning_content` 独立字段，`<think>` 标签包裹 | 标准 messages 数组 |

### 5.1 Parts / 分段存储模型验证

**结论：当前设计的 parts 化存储模型与业界主流方向一致。**

OpenCode 是目前 parts 模型最成熟的实现，定义了 **12 种 Part 类型**：

| Part 类型 | 用途 | 我们对应的设计 |
|-----------|------|--------------|
| `TextPart` | 文本内容 | `part_type = text` ✅ 一致 |
| `ReasoningPart` | 思维链 | `part_type = thinking` ✅ 一致 |
| `ToolPart` | 工具调用（4 状态机） | V1 不做，设计预留 ✅ |
| `FilePart` | 文件附件 | V1 不做 |
| `StepStartPart` / `StepFinishPart` | 步骤边界标记 | 未设计，后续可加 |
| `SnapshotPart` | 状态快照 | 未设计 |
| `CompactionPart` | 上下文压缩标记 | `summary_message_id` 预留 ✅ |
| `RetryPart` | 重试标记 | 未设计 |
| `SubtaskPart` / `AgentPart` | 子任务/Agent 引用 | V1 不做 |

**我们的 V1 设计（text + thinking + finish + error）完全满足基础对话需求。** OpenCode 的 12 类 part 是面向代码 Agent 场景（工具调用、文件变更、步骤追踪），Web 对话不需要如此复杂。

**值得借鉴的点**：
- OpenCode 的 `ToolPart` 使用 **4 状态机**（pending → running → completed/failed），我们的 `MessageStatus`（streaming → completed → failed）和 `PartStatus` 设计思路一致。
- OpenCode 的 `StepStartPart` / `StepFinishPart` 标记步骤边界，如果后续引入 Agent 编排（工具调用链），这是一个好的事件边界模式。

### 5.2 思维/推理展示模式对比

**结论：当前设计的 thinking 独立 SSE 事件 + 可折叠 UI 是业界标准做法。**

| 产品 | 思维内容载体 | 流式方式 | UI 展示 |
|------|------------|---------|--------|
| **OpenCode** | `ReasoningPart`（独立 part） | `message.part.updated` + delta | 终端内联展示 |
| **Codex** | `reasoning` item（summary + raw） | `item/reasoning/textDelta` + `summaryTextDelta` | VS Code 面板 |
| **Claude Code** | `thinking` content block | `content_block_start/delta/stop` + `thinking_delta` | 终端 verbose 模式 |
| **DeepSeek Chat** | `reasoning_content` 字段 | 流式 delta，独立于 `content` | 可折叠 `<think>` 区域 |
| **我们的设计** | `part_type = thinking` | SSE `event: thinking` + delta | 可折叠 ThinkingBlock 组件 ✅ |

**关键发现与建议**：

1. **Codex 的双通道推理**：Codex 同时提供 `summaryTextDelta`（人类可读摘要）和 `textDelta`（原始推理）。对 V1 来说不需要，但如果 thinking 内容很长（如 R1 模型的数千 tokens），后续可以考虑生成摘要用于折叠态展示。

2. **Claude Code 的 `display: "omitted"` 模式**：允许跳过 thinking 内容流式传输，仅保留签名用于多轮连续性。这解决了**流式传输 thinking 导致首 token 延迟增加**的问题。我们的设计中 `includeReasoningResult = false` 避免了 thinking 混入最终回复，但 thinking 仍通过 SSE 传输。如果模型 thinking 内容较长，建议考虑：
   - 短期：thinking 流式传输即可，V1 场景下 thinking 不会过长。
   - 后续：提供前端设置允许用户选择"隐藏 thinking 过程"。

3. **DeepSeek / Open WebUI 的 `<think>` 标签检测**：Open WebUI 通过正则匹配 `<think>...</think>` 标签来分离 reasoning，这种方式更脆弱（依赖模型输出格式）。我们使用独立的 SSE 事件类型（`event: thinking` vs `event: message`）是更可靠的做法。

4. **LibreChat 的经验教训**：从 LibreChat PR #5440 的讨论可以看到，推理 UI 的常见坑包括——标题生成时混入 thinking 内容、TTS 朗读时读出 thinking、文件对话模式下不生效。我们的设计中标题由后端生成（基于用户第一条消息截断），不会混入 thinking；且第一版无语音和文件对话功能，避开了这些坑。

### 5.3 消息排队 / 并发控制模式对比

**结论：我们的"前端排队 + 服务端串行锁"双层策略在业界有验证，但中断控制是短板。**

| 产品 | 用户发送新消息时的行为 | 中断/取消机制 |
|------|---------------------|-------------|
| **ChatGPT (Web)** | 允许输入，上一条继续生成；发送后似乎会中断当前生成 | 隐式中断（发送新消息） |
| **DeepSeek Chat (Web)** | 与 ChatGPT 类似 | 停止生成按钮 |
| **Codex** | `turn/steer` — 向活动 turn 添加输入 | `turn/interrupt` — 显式取消 |
| **我们的设计** | 前端排队，不中断当前生成，自动续发 | **无中断机制** ⚠️ |

**关键差距**：

- **Codex 的 `turn/interrupt`** 允许用户显式中断当前 agent 工作流。对于 Web 对话，这意味着用户应该有一个"停止生成"按钮来取消当前 LLM 响应。
- **ChatGPT / DeepSeek Web** 在用户发送新消息时会自动中断当前生成（ChatGPT）或提供停止按钮。用户期望的是"我说新的话，旧的不要了"，而非"排队等着"。
- 我们的排队模式是一种**独特的交互设计**，在连续追问场景下有优势（比如"继续"、"还有呢"这样的追加指令），但在"用户想换个话题"场景下体验不佳——用户需要等当前回复完成后排队消息才发送。

**建议**：
- **P0**：增加"停止生成"按钮。点击后 abort 当前 fetch，丢弃排队消息，让用户自由开始新话题。
- 排队模式作为**默认行为保留**（适合连续追问），但提供**显式中断入口**（适合换话题）。

### 5.4 服务端架构模式对比

| 维度 | OpenCode | Codex | Claude Code | 我们的设计 |
|------|----------|-------|-------------|-----------|
| **通信协议** | REST + SSE | JSON-RPC 2.0 双向 | SSE / stream-json | REST + SSE ✅ |
| **服务端** | Hono (Node.js) | Rust (codex-rs) | Node.js (Claude Code) | Spring Boot 4.0.6 + WebFlux |
| **事件总线** | 中央 BusEvent，`message.part.updated` | JSON-RPC 通知流 | SSE 事件流 | 直接在 Controller 中写 SSE |
| **并发控制** | - | 有界队列，超载返回 `-32001` | - | `ConcurrentHashMap<Semaphore>` + `409` ✅ |
| **心跳/保活** | 30s SSE 心跳 | - | - | **未设计** ⚠️ |

**建议**：
- **SSE 心跳**：OpenCode 每 30 秒发送 SSE 心跳防止连接超时。我们的流式接口如果 LLM 响应较慢（thinking 阶段可能无输出），中间代理（Nginx、负载均衡器）可能超时断开。建议增加周期性 SSE 心跳或 comment 行。
- **Codex 的 backpressure** 模式：Codex 使用有界队列 + `-32001` 错误码实现 backpressure，避免服务端过载。我们的 `ConcurrentHashMap<Semaphore>` 方案在单会话级别有类似效果，但如果未来需要全局限流，可以借鉴此模式。

### 5.5 Token 统计与成本追踪

**结论：当前设计的 token 字段粒度不足。**

| 产品 | Token 统计粒度 |
|------|---------------|
| **OpenCode** | `input`、`output`、`reasoning`、`cache.read`、`cache.write`、`total` |
| **Codex** | `input_tokens`、`cached_input_tokens`、`output_tokens`、`reasoning_output_tokens` |
| **我们的设计** | `prompt_tokens`、`completion_tokens`（仅在 session 级别） |

**差距**：
- 当前设计缺少 **reasoning/thinking tokens 的单独统计**。对于 DeepSeek R1 等推理模型，thinking tokens 可能占总 token 消耗的 50% 以上。
- Token 统计仅在 `agent_session` 表级别汇总，不在 `agent_message` 级别记录，无法分析单轮对话成本。

**建议**：
- **P1**：在 `agent_message` 表增加 `prompt_tokens`、`completion_tokens`、`reasoning_tokens` 三个字段。
- `agent_session` 表的汇总字段可以保留，但应从消息级别聚合生成。

### 5.6 会话管理与标题生成

| 产品 | 标题生成方式 | 会话组织 |
|------|------------|---------|
| **OpenCode** | `message.slice(0, 50) + (length > 50 ? "..." : "")` | 按时间列表，支持 parentID 分支 |
| **ChatGPT** | 模型自动生成标题（首轮对话后） | 侧边栏时间分组 |
| **DeepSeek Chat** | 同上 | 同上 |
| **我们的设计** | 第一条用户消息截断，最大 30 字符 | 按 updated_at desc 排序 |

**分析**：
- OpenCode 的 50 字符截断比我们的 30 字符更宽松。中文场景下 30 字符约 15 个汉字，可能不足以表达完整语义。建议调整为 **50 字符** 或使用 **按字节截断**。
- ChatGPT 使用模型生成标题更智能但增加成本，V1 不适合。
- OpenCode 的 `parentID`（会话分支）是高级功能，我们的 `parent_session_id` 预留合理。

## 七、改进建议（按优先级，含业界对标）

### P0 - 必须在开发前解决

1. **排队消息自动发送失败的 fallback 设计**（影响 04-详细设计）
   - 失败后不应静默丢弃用户消息
   - 建议：失败消息回退到消息列表展示为"发送失败"，提供重试入口
   - **业界对标**：Codex 的 `turn/steer` 和 ChatGPT 的"发送新消息即中断"模式可以考虑作为替代方案

2. **流式写入中断的恢复策略**（影响 04-详细设计）
   - `streaming` 状态的 orphan 消息需要清理机制
   - 建议：应用启动时清理超时的 streaming 消息

3. **🆕 增加"停止生成"按钮**（影响 01-需求、03-原型、04-详细设计）
   - 当前设计只有排队模式，缺少中断当前生成的能力
   - **业界对标**：Codex 有 `turn/interrupt`，ChatGPT/DeepSeek 有停止按钮
   - 排队模式适合连续追问，但用户换话题时需要能立即中断
   - 建议：增加停止按钮，点击后 abort 当前 fetch，丢弃排队消息
   - 原型中需新增该交互状态

4. **🆕 SSE 流式心跳保活**（影响 04-详细设计）
   - LLM 的 thinking 阶段可能长时间无输出，中间代理可能超时断开连接
   - **业界对标**：OpenCode 每 30 秒发送 SSE 心跳
   - 建议：后端定期（建议 15-30 秒）发送 SSE comment 行 `: heartbeat` 保持连接

### P1 - 强烈建议修改

5. **原型中的搜索框应标记为"非首版"**（影响 03-原型设计）
   - 添加注释或 CSS 类标明为预留占位
   - 或在实现时渲染为 `disabled` 状态

6. **原型示例数据应与详细设计对齐**（影响 03-原型设计）
   - model badge 更新为默认模型名或改为可配置
   - ID 字段的注释更新

7. **需求文档补充自动标题的具体规则**（影响 01-需求）
   - 截断长度：**建议从 30 字符调整为 50 字符**
   - **业界对标**：OpenCode 使用 `message.slice(0, 50)` 截断，30 字符对中文偏短
   - 生成时机、是否可被后续消息覆盖

8. **🆕 增加 message 级别的 token 统计**（影响 02-技术方案、04-详细设计）
   - 当前仅在 session 级别汇总 token，无法分析单轮成本
   - **业界对标**：OpenCode 和 Codex 均在 message 级别记录 `input`、`output`、`reasoning` tokens
   - 建议：在 `agent_message` 表增加 `prompt_tokens`、`completion_tokens`、`reasoning_tokens` 字段

### P2 - 建议后续补充

9. **补充性能基准**（影响 04-详细设计）
10. **补充日志和监控设计**（影响 04-详细设计）
11. **移动端手势交互留设计备注**（影响 03-原型设计）

13. **🆕 thinking 完成后自动折叠**（影响 03-原型、04-详细设计）
    - **业界对标**：LibreChat 社区建议"reasoning section should auto-collapse once the final answer starts"
    - 当前设计 thinking 流式生成中默认展开，完成后仍展开
    - 建议：流式完成后自动折叠 thinking，减少视觉干扰

## 八、总结

四份文档整体质量较高，**"需求-方案-原型-设计"的四层链路完整且可追溯**。核心亮点包括：

- parts 化存储模型的设计决策有理有据，与 OpenCode（12 类 Part）、Codex（Item 类型系统）等顶级 Agent 产品的架构理念一致。
- 流式接口的 SSE 事件类型设计（thinking / message / done / error）比 DeepSeek 生态的 XML 标签解析方案更可靠。
- 原型状态覆盖全面，8 种页面状态 + 移动端响应式预留。
- 并发控制有单实例方案和多实例演进方向，与 Codex 的 backpressure 模式思路相通。

**业界验证结论**：当前设计在 parts 存储、thinking 分离、SSE 流式、会话隔离等核心设计决策上，与 OpenCode、Codex、Claude Code 等产品的主流做法一致。主要差距在于：

| 差距项 | 业界做法 | 我们的现状 | 优先级 |
|--------|---------|-----------|--------|
| 中断当前生成 | Codex `turn/interrupt`，ChatGPT 停止按钮 | 无中断机制 | **P0** |
| SSE 心跳保活 | OpenCode 30s 心跳 | 无心跳 | **P0** |
| Token 统计粒度 | OpenCode/Codex 在消息级记录 reasoning tokens | 仅在 session 级汇总 | **P1** |
| Thinking 自动折叠 | LibreChat 社区最佳实践 | 手动折叠 | **P2** |
| 标题截断长度 | OpenCode 50 字符 | 30 字符（偏短） | **P1** |

**总体评分：8.0/10**（维持不变——设计本身扎实，新增问题为对比业界后发现的功能缺失，非设计缺陷）

建议在开发启动前完成 P0 改进项（停止生成按钮、SSE 心跳、排队失败 fallback、orphan 消息清理），P1 改进项在开发中逐步完善，P2 可作为后续迭代内容。
