请解释一下Spring WebFlux和传统Spring MVC的主要区别是什么？在什么场景下应该选择WebFlux？

用户问的是Spring WebFlux和Spring MVC的对比，我需要从编程模型、线程模型、适用场景几个维度来回答。先梳理核心差异，再给出选型建议。

Spring WebFlux 和 Spring MVC 的主要区别如下：

1. 编程模型

Spring MVC 基于同步阻塞模型，使用传统的 Servlet API，每个请求占用一个线程。Spring WebFlux 基于异步非阻塞模型，使用 Reactor 库，通过 Mono 和 Flux 进行响应式编程。

2. 线程模型

MVC 依赖线程池，高并发时线程资源可能成为瓶颈。WebFlux 使用事件循环（如 Netty），少量线程即可处理大量并发连接。

3. 适用场景

推荐使用 WebFlux 的场景：I/O 密集型（如调用远程 API、数据库查询）、需要处理大量长连接、对资源利用率要求高。推荐使用 MVC 的场景：CPU 密集型、团队对响应式编程不熟悉、已有大量 MVC 代码。

在 Spring WebFlux 中实现 SSE 流式响应非常简洁，核心是返回 Flux<ServerSentEvent> 类型。

示例代码如下：

@GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<ServerSentEvent<String>> stream() {
    return Flux.interval(Duration.ofMillis(100))
        .map(seq -> ServerSentEvent.<String>builder()
            .event("message")
            .data("chunk " + seq)
            .build());
}

我的PostgreSQL数据库中有一张订单表，数据量大概500万行，查询速度越来越慢，能帮忙看看怎么优化吗？

500万行的订单表查询变慢，需要从索引、查询模式、表结构几个方面分析。先给出通用的索引优化建议，再说明如何定位慢查询。

针对500万行的订单表，以下是一些索引优化建议：

1. 为常用查询条件创建索引

根据你的查询模式，优先为 WHERE 子句中的高频列创建索引。例如如果经常按 user_id 和 created_at 查询：

CREATE INDEX idx_orders_user_created
ON orders (user_id, created_at DESC);

2. 使用部分索引减少体积

如果经常只查询特定状态的订单：

CREATE INDEX idx_orders_pending
ON orders (user_id) WHERE status = 'pending';

3. 定期执行 VACUUM ANALYZE

确保查询计划器有最新的统计信息来选择最优执行计划。

联合索引和单独建多个单列索引有什么区别？应该怎么选择？

联合索引 vs 单列索引是经典问题。需要说明最左前缀原则、覆盖索引、以及不同查询模式下的选择策略。

联合索引和单列索引的核心区别在于查询匹配规则和使用效率：

联合索引遵循最左前缀原则：索引 (a, b, c) 可以覆盖查询 WHERE a=1、WHERE a=1 AND b=2、WHERE a=1 AND b=2 AND c=3，但不能覆盖 WHERE b=2。

选择建议：如果多个列经常一起出现在查询条件中，优先使用联合索引；如果列之间查询组合不固定，可以考虑单列索引组合。

SSE 事件类型说明

meta 当前轮消息元信息 — 包含 sessionId、userMessageId、assistantMessageId thinking 大模型思考过程增量片段 — 追加到 thinking part，UI 展示在可折叠区域 message 助手最终回复增量片段 — 追加到 text part，UI 展示在回复区域 done 当前轮回复完成 — 消息状态变更为 completed，前端检查排队队列 error 当前轮回复失败 — 消息状态变更为 failed，前端展示错误提示

数据模型设计

三表结构：agent_session + agent_message + agent_message_part。ID 实际使用 VARCHAR(64)，避免前端 JavaScript 大整数精度问题。
