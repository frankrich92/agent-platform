## 2. 文档体系结构评审

### 2.1 三层文档架构

```text
docs/v3-agent中台/
├── 全局基线层（8份正式文档 + RTK）
├── 工程迭代层（小工程目录）
│   └── 01-chat-minimal/
│       ├── 工程范围与验收目标
│       ├── 工程契约切片
│       ├── 工程技术设计
│       ├── 工程测试策略
│       ├── 工程路线图
│       └── ai-tasks/（任务包）
└── 共享模板层（4份模板）
```

**评审意见**：
- ✅ 职责分离清晰。全局基线只维护长期方向和候选契约，不侵入小工程实现细节。
- ✅ 小工程内 5 份文档的命名和阅读路径在 `README.md`、`09-小工程切片与验收门禁.md` 中保持一致。
- ✅ 任务包目录结构（`task.md` / `contract-notes.md` / `test-report.md` / `handoff.md`）规范统一。
- ⚠️ 缺少 `03-xxx` 编号文档（从 `01-` 直接跳到 `04-`），虽然不影响使用，但索引表和文件列表中会出现编号断层，容易让新成员产生"是否有遗漏文档"的疑问。

### 2.2 文档维护边界规则

`README.md` 第 4 节规定了明确的维护边界：
- 全局技术架构 → `02-...`
- 全局候选接口契约 → `04-...`
- 全局数据模型 → `05-...`
- 小工程具体实现 → `工程迭代/<小工程>/`

**评审意见**：规则明确，但需要一条补充规则——当小工程验证稳定后，由谁负责把局部契约合并回全局基线、合并频率和触发条件是什么？目前仅在 `07-AI-Native交付规约.md` 第 7 节提到"由主 Agent 或 Review Agent 判断"，建议 `README.md` 也增加一句指引。

**问题发现**：
- ⚠️ **P0** **Spring Boot 4 版本确认**。当前文档规定使用 "Spring Boot 4"，但截至 2026 年 5 月，Spring Boot 最新稳定版为 3.3.x/3.4.x 系列（基于 Spring Framework 6.1.x）。Spring Boot 4 可能指：
  1. 尚未发布的下一代版本（基于 Spring Framework 7）
  2. 笔误，实际应为 Spring Boot 3.x
  3. 内部代号或特定分支

  **建议立即确认**：如果是指 Spring Boot 3.x，应修正文档；如果确指 4.x（alpha/milestone），需说明具体版本号并评估稳定性风险。这是一个会直接影响工程骨架创建的关键决策。

- ⚠️ **P1** 前端规范过于简略。仅提到 Vue 3 + TypeScript + Pinia + 组件/store/api/types 分层，未说明：
  - 构建工具（Vite / Webpack / 其他）
  - UI 组件库（Element Plus / Ant Design Vue / 自研）
  - SSE 客户端封装方式（EventSource / fetch + ReadableStream / 第三方库）
  - 路由方案（Vue Router 版本、权限路由控制方式）

## 7. 关键风险与改进建议

### 7.1 P0 级问题（阻塞启动）

1. **Spring Boot 版本确认**
   - 影响：决定 Maven 依赖、Spring 配置和工程骨架。
   - 行动：确认 `08-...` 中的 "Spring Boot 4" 是指具体哪个版本，或修正为当前稳定版。

2. **`biz-execution` 模块归属**
   - 影响：chat-minimal 需要执行详情查询（`GET /api/executions/{runId}`），但后端模块未明确由谁负责。
   - 行动：确认是 `biz-chat` 兼管还是应补充 `biz-execution` 模块。

3. **`WorkflowRun` 状态枚举完整性**
   - 影响：如果后续工作流需要等待状态，当前枚举缺失会导致状态机设计返工。
   - 行动：确认是否补充 `waiting` 状态。

### 7.2 P1 级问题（启动后可并行修复）

4. **前端技术栈补充**
   - 建议：在 `08-...` 或 chat-minimal `03-...` 中明确构建工具（Vite）、UI 库（建议 Element Plus 或 Ant Design Vue）、SSE 客户端封装方案。

5. **SSE 语义补全**
   - 建议：在 chat-minimal `02-...` 中补充 SSE 连接建立时的初始事件序列、`heartbeat` 间隔、重连时的 `Last-Event-ID` 处理。

6. **Capability Gate "最小"定义**
   - 建议：在 chat-minimal 契约切片中明确最小 gate 的行为（例如：只校验 Agent 启用状态 + 用户授权，不做 capability 细粒度过滤）。

7. **Thinking 内容持久化策略**
   - 建议：明确 `agent_message` 是否存储 thinking 内容，或是否需要单独的字段/表。

8. **POC-2 任务包提前设计**
   - 建议：在 POC-1 进行到 50% 时启动 POC-2 任务包的详细设计，避免 POC-1 完成后阻塞等待。

### 7.3 架构设计亮点（应坚持）

- ✅ **架构不变量**：特别是"不自研 ReAct 循环"和"平台不绕过 AgentScope 触发工具"，这是避免技术债务的关键红线。
- ✅ **Capability Gate**：将能力授权、风险分级、运行时路由统一在一个 gate 中，设计优雅且可扩展。
- ✅ **MyBatis-Plus + R2DBC 分离**：普通 CRUD 与流式高频写入的职责分离，避免了性能瓶颈。
- ✅ **小工程切片策略**：按可验收业务闭环拆分，而不是按技术模块拆分，这是正确的敏捷/迭代策略。
- ✅ **AI Native 交付规约**：owned files、验证命令、L0-L5 验收、Review Agent 检查清单等机制，有效约束了 AI agent 的"随意性"。
- ✅ **参考项目采纳/不采纳表格**：在 `04-...` 中对 10 个参考项目逐一分析采纳边界，避免了盲目照搬。
