# V3 Agent 中台文档评审报告 v1

> 评审模型：dpsk-v4
> 评审日期：2026-05-19
> 评审范围：`docs/v3-agent中台/` 全量文档（含 templates/ 和 工程迭代/01-chat-minimal/）
> 评审目的：评估文档体系作为 AI Native 编程基础的完备性、一致性和可执行性

---

## 1. 总评

**总体评分：B+（良好，距"可直接用于 AI 多 Agent 并行开发"尚有 8-12 个补项缺口）**

该文档体系统一度较高，分层清晰（全局基线 → Epic → 小工程 → 任务包），AI 任务单、owned files、契约冻结、验收等级等机制设计成熟。文档在"约束 AI agent 不越界"方面表现出色，但在"告诉 AI agent 精确该怎么做"方面存在若干关键缺口——契约定义的精确度、实体 Schema 的形式化程度、错误码目录的缺失、并行冲突处理机制的空白，是当前最大的风险点。

**作为 AI Native 编程基础的适用性评估：**
- 人类开发者可独立理解并开发：**是**
- AI agent 可独立理解并开发（无人类干预）：**有条件**（POC-0/POC-1 可，POC-2 需补契约精确化后方可）
- 多 AI agent 并行开发无冲突：**有条件**（需补并行冲突协调机制和共享文件仲裁规则）

## 3. 逐文档详细评审

### 3.1 `README.md` — 文档索引

**优点：**
- 分层阅读路径清晰（按场景：产品/前端、后端、运行时、AI Native 开发）
- 小工程隔离阅读规则明确（"不同小工程文档不互相作为默认阅读材料"）

**问题：**

- **[P0-阻断] 内容截断**：第 4 节"维护规则"在第 128 行处末句不完整（`- 全局候选接口契约改` 后面无内容），这是一个文件损坏级别的缺陷，AI agent 读到此处会认为文档不完整。
- **[P2-改善] 缺失说明**：未解释为什么编号跳过了 `03`，也未说明 `03` 是刻意留空还是被废弃。

### 3.2 `RTK.md` — 需求/任务/知识追踪表

**优点：**
- REQ → CAP → TASK 三层追踪闭环设计合理
- 小工程追踪表 + 任务追踪表双维度索引实用
- 状态字段（Planned/In Progress/Review/Pending）使 AI agent 可定位当前任务

**问题：**

- **[P1-重要] 表格行截断**：任务追踪表末尾 `TASK-V3-902` 行被截断，可能是文件保存不完整或内容过多。截断的追踪表对 AI agent 是不可靠的信息源。
- **[P1-重要] REQ 追踪存在引用断裂**：例如 `REQ-V3-002` 引用了 `TASK-V3-020, TASK-V3-024, TASK-V3-040`，但任务追踪表中这些任务的状态分别为 Pending、Pending、Pending，而 REQ 状态也是 Pending。缺少"部分完成"的中间状态，当一个 REQ 对应多个任务时，无法表达部分进展。
- **[P2-改善] 缺少状态变更历史**：状态字段只有当前值，没有变更时间和原因，难以审计追踪。
- **[P2-改善] 缺少契约版本号**：contract slice 和 ADR 没有版本标识（如 v1.0、v1.1），当多 AI agent 并行修改时无法判断谁持有最新版本。

### 3.3 `01-产品蓝图与体验目标.md`

**优点：**
- 五类用户画像清晰，各自目标明确
- Agent 标签体系设计成熟（七维度标签，治理边界清晰）
- "通用配置 Agent / 外部复杂 Agent / Runtime 风险判定"三层模型合理
- Capability Gate 概念贯穿始终，安全边界明确

**问题：**

- **[P2-改善] 缺少用户旅程映射**：虽然有用户画像，但缺少典型的端到端用户旅程（如"业务老师首次使用 Chat 完成合同初审"的完整步骤）。这对 AI agent 理解 E2E 测试场景设计有帮助。
- **[P2-改善] 部分术语未在首次出现时定义**：如 "Capability gate"、"RuntimeCapabilityPlan" 在第 1 节就已出现，但概念定义在后面文档中才展开。AI agent 线性阅读时会遇到未解析概念。

### 3.4 `02-Agent中台技术架构方案.md`

**优点：**
- 架构不变量列表（第 2 节）是 AI agent 的行为约束基线，每一条都可验证
- 模块地图的 `[Core]/[Ext]/[Off]` 标记清晰区分当前和候选
- 模块职责描述（第 5 节）给出了清晰的依赖方向约束
- 小工程架构收敛六步流程（第 3 节）是 AI agent 的任务启动 checklist

**问题：**

- **[P0-阻断] 模块职责表述依赖自然语言，缺少可机器检查的约束**：例如 "`agent-domain` 不依赖 Spring、Web、MyBatis、R2DBC、AgentScope" 这条约束，AI agent 理解后需要自己决定如何验证——建议补充对应的 ArchUnit 测试用例名称或规则描述（实际上 `TASK-V3-014` 创建了 architecture test 任务，但全局基线中未标注具体的约束规则名）。
- **[P1-重要] Core/Ext/Off 状态迁移规则未定义**：`[Ext]` 如何变为 `[Core]`？需要满足什么条件？谁来决定？AI agent 在扩展功能时可能需要知道这个流程。
- **[P2-改善] 缺少架构决策记录索引**：虽然架构不变量列表很清晰，但没有关联到具体的 ADR 编号。AI agent 需要知道"为什么做这个决定"才能在不变量需要调整时做出正确判断。
- **[P2-改善] 包依赖关系图缺失**：虽然文字描述了依赖方向，但缺少可视化的包依赖图（Mermaid 或 ASCII art），AI agent 难以快速理解模块间的允许/禁止依赖关系。

### 3.5 `04-API-SSE-运行时契约-全局基线.md`

**优点：**
- 参考项目与采纳边界表（第 2 节）是优秀实践——明确告诉 AI agent 参考了什么、采纳了什么、为什么不采纳
- 代码级接口引用要求（第 2.2 节）设定了高标准的接口设计引用粒度
- 参考内容到平台契约的映射表（第 2.1 节）提供了清晰的转换路径

**问题：**

- **[P0-阻断] 缺少形式化的 OPENAPI/JSON Schema 定义**：当前契约以 Markdown 文字和清单形式描述（如 SSE event 列表），但没有定义每个 event 的精确 payload JSON Schema。AI agent 实现 API 和 SSE 时，只能从文字推断字段名、类型、必填/可选、嵌套结构。这会导致不同 AI agent 对同一契约产生不同理解，造成集成问题。建议至少为第一个小工程（chat-minimal）的 SSE event 提供 JSON Schema。
- **[P0-阻断] 缺少错误码目录**：文档多次提及"错误码"（如 `VALIDATION_FAILED`、`RUNTIME_UNAVAILABLE`），但没有集中定义的错误码枚举或目录。AI agent 在处理异常路径时无法确定应该返回什么错误码。
- **[P1-重要] SSE envelope 结构描述不精确**：文档提到 `run.started`、`assistant.delta` 等 event type，但未定义 envelope 的通用结构——例如 `{ "eventType": "run.started", "sequence": 1, "timestamp": "...", "payload": {...} }`。AI agent 对 envelope 的假设必须一致。
- **[P1-重要] 缺少 API 请求/响应示例**：虽然 API 列表出现在 `02-工程契约切片.md` 中，但全局基线中缺少具体的请求/响应 JSON 示例。AI agent 实现时需要具体的字段级说明。

### 3.6 `05-数据模型与安全审计-全局基线.md`

**优点：**
- 数据域分类清晰（9 大类）
- 表清单结构合理，命名规范统一（`agent_` 前缀）
- E2E 数据边界（testRunId）约束严格
- 附件与 OCR 派生上下文字段设计细致

**问题：**

- **[P0-阻断] 字段类型和约束未定义**：表清单只列出字段名，没有 Java 类型映射、SQL 类型、NOT NULL 约束、长度限制、默认值。例如 `agent_definition.agent_type` 是 VARCHAR 还是 ENUM？长度多少？NOT NULL？AI agent 在创建 Flyway 迁移脚本时无法确定 DDL 细节。
- **[P0-阻断] 缺少外键关系和级联策略**：虽然第 2 节画了核心关系图，但如 `Session -> Message` 是 `ON DELETE CASCADE` 还是 `SET NULL`？这些对 AI agent 至关重要。
- **[P1-重要] 缺少索引建议**：没有推荐哪些字段需要建索引。AI agent 实现的查询可能性能极差。
- **[P1-重要] `metadata` 字段过度使用**：多个表（agent_definition、agent_tag、agent_message_attachment 等）都有 `metadata` JSON 字段，但约束只说"非敏感扩展信息"。缺少 metadata 字段的 schema 约定（至少应有 JSON key 的命名规范）。
- **[P2-改善] 缺少数据迁移策略**：虽然提到 Flyway，但未说明从 V1/V2 到 V3 的迁移路线。如果确实不做迁移，也应该明确声明。

### 3.7 `06-测试策略与验收等级-全局基线.md`

**优点：**
- L0-L5 验收等级定义清晰，每个 AI 任务必须声明目标等级
- 测试数据隔离（testRunId）规则和执行要求一致
- CI 质量门禁定义到位

**问题：**

- **[P1-重要] L3 与 L4 边界尚可更清晰**：L3（API/SSE E2E）和 L4（Playwright UI E2E）的边界在"验证用户体验"层面是清晰的，但在"验证前端状态"这块有重叠——例如 SSE 接收后的前端状态更新，是 L3 的断言范围还是 L4 的？可能造成验收标准争议。
- **[P1-重要] 缺少测试数据工厂/夹具规范**：要求所有 E2E 创建独立测试数据，但没有提供或规范如何构建测试夹具。AI agent 可能会各自实现不同的测试数据初始化逻辑。
- **[P2-改善] 缺少 Mock/Stub 策略指南**：虽然要求"单元测试可以用 mock，但不能替代 E2E"，但没有提供推荐的 mock 粒度或 mock 库选择指南。
- **[P2-改善] 缺少测试命名约定**：除了给出一个示例命名（`shouldReturnSessionBusyWhenSameSessionStreamsConcurrently`），没有系统性的命名规范。

### 3.8 `07-AI-Native交付规约.md`

**优点：**
- 流程定义完整（需求澄清 → 文档交接 10 步）
- owned modules / owned files 模型是防止 AI agent 越界的核心机制
- 子 Agent 并行开发就绪条件详尽
- 禁止事项清单具体且可执行
- Review Agent 检查清单实用

**问题：**

- **[P1-重要] "方案竞争"步骤未展开**：基本流程第 3 步是"方案竞争"，但正文中对这一步骤没有任何说明。AI agent 不知道方案竞争的形式（提交设计文档？代码原型？）、参与方（多个 AI agent？人类 vs AI？）、评判标准。
- **[P1-重要] 缺少并行子 Agent 冲突协调机制**：文档规定了 owned files 互斥原则，但没有说明当子 Agent A 发现子 Agent B 的 owned file 有问题时的处理流程。当前的"E2E/Review Agent 默认不顺手改"只解决了单向问题。
- **[P1-重要] 缺少共享文件（如 Flyway 迁移脚本、pom.xml）的写入仲裁规则**：并行子 Agent 都可能需要添加 Flyway 迁移或修改 `pom.xml` 依赖。当前只说"指定唯一 owner"，但没有流程指导如何在不阻塞并行的情况下管理共享文件。
- **[P2-改善] 缺少 AI agent 失败恢复流程**：当 AI agent 执行任务失败时（如编译错误、测试失败），重试策略、回滚策略、人工介入时机都不明确。
- **[P2-改善] "必须阅读" 清单存在冗余**：AI 任务单模板中"全局规则"列出了 7 个文件（含 README.md ← RTK.md），而任务单本身又要求列出"本小工程"的 7 个文件。对于执行型 AI agent，这 14+ 文件会产生巨大的上下文开销。建议区分"精读"和"了解"层级。

### 3.9 `08-开发规范与本地环境.md`

**优点：**
- 技术栈明确（Java 21、Spring Boot 4、Vue 3、TypeScript）
- 模块约束清晰（"agent-domain 不依赖基础设施"）
- 安全规范具体可验证

**问题：**

- **[P0-阻断] 缺少本地开发环境完整搭建指南**：文档给出了工具链路径（JAVA_HOME、MAVEN_HOME 等），但没有说明：
  - 如何初始化本地数据库（PostgreSQL 安装、创建数据库、运行 Flyway）
  - 如何获取和配置 `.env` 文件
  - 如何启动完整开发环境（后端 + 前端 + 数据库）
  - 前后端开发时的端口和跨域配置
  AI agent 在没有人工介入的情况下无法自行搭建开发环境。
- **[P1-重要] 缺少版本兼容性声明**：给出了具体版本号（Java 21.0.11-tem、Maven 4.0.0-rc-5），但没有声明兼容范围（是否必须精确匹配这些版本？还是 21+ / 4.x 即可？）。
- **[P2-改善] 缺少 Git 工作流规范**：虽然提到了 Conventional Commits，但没有分支策略（如 trunk-based vs GitFlow）、PR 标题格式、合并策略（squash/merge/rebase）。

### 3.10 `09-小工程切片与验收门禁.md`

**优点：**
- 小工程原则明确（独立交付、独立验收、独立回滚）
- 不建议按技术模块拆分小工程，强调纵向闭环——这是关键的正确决策
- 并行开发就绪门禁清单详尽且可检查
- 文档维护边界清晰（第 6 节）

**问题：**

- **[P1-重要] 缺少跨小工程依赖管理机制**：如果 EPIC-V3-B（admin-config）需要 EPIC-V3-A（chat-minimal）提供的 Agent 库 API，B 如何声明对 A 的契约依赖？A 的契约变更如何通知 B？
- **[P2-改善] POC 阶段命名过于通用**：所有小工程使用同样的 POC-0/POC-1/POC-2 命名，但这些阶段在不同小工程中的语义可能不同（chat-minimal 的 POC-1 是做模块骨架，但 admin-config 的 POC-1 可能就是做真实 CRUD 了）。建议阶段定义加入内容语义。

### 3.11 `templates/` — 模板文件

- AI 任务单模板包含所有必需字段

**问题：**

  - 需要人工确认的事项清单
- **[P2-改善] 缺少子 Agent 完成报告模板**：`07-AI-Native交付规约.md` 第 6 节定义了子 Agent 输出格式，但没有独立模板文件，AI agent 可能遗漏部分输出字段。
- **[P2-改善] 缺少 Code Review 检查清单模板**：Review Agent 检查清单嵌入在 `07` 中，但没有独立模板供 Review Agent 填写。

### 3.12 `工程迭代/01-chat-minimal/` — 首个小工程

**优点：**
- 五份文档（范围、契约、设计、测试、路线图）结构完整
- 契约切片精确，明确标注"只实现"和"暂不实现"
- 验收等级按阶段分解（L1→L5 渐进）
- 测试策略与全局基线对齐良好

**问题：**

- **[P0-阻断] POC-2 任务包全部为"待创建"**：chat-minimal 最核心的 Chat 主链路实现任务（TASK-V3-020 至 TASK-V3-024）都没有创建任务包。AI agent 在 POC-1 完成后将无法继续。
- **[P1-重要] SSE payload 定义仍不够精确**：契约切片列出了 SSE event 名称（如 `assistant.delta`），但没有定义每个 event 的 payload 字段。AI agent 实现 SSE 映射时需要这些信息。
- **[P1-重要] 缺少消息格式约定**：`POST /api/chat/send` 的请求格式除了"只接收文本 message"外，没有定义字段结构。是 `{ "message": "string" }` 还是 `{ "content": [{"type": "text", "text": "..."}] }`？这直接影响前后端集成。

## 4. 一致性与连贯性评审

### 4.1 跨文档一致性

### 4.3 连贯性断裂点

1. **架构基线 → 契约基线之间的桥梁薄弱**：`02` 描述了模块职责，`04` 描述了参考项目和采纳边界，但两者之间缺少一个"模块到接口的映射表"——例如哪个模块负责哪些 API，哪些模块产生哪些 RuntimeEvent。AI agent 需要自己建立这个映射。

### 5.2 AI agent 自主决策边界

文档在以下方面的"自主决策空间"设计良好：
- ✅ 不能跨模块顺手修（`07` §4）
- ✅ 不能绕过 AgentScope 触发工具（`07` §9）
- ✅ 不能修改历史 Flyway 迁移（`08` §5）

但以下方面的"自主决策空间"过大（存在理解歧义风险）：
- ⚠️ DDL 细节（字段类型、约束、索引）——不同 AI agent 会产生不同实现
- ⚠️ SSE event payload 结构——不同 AI agent 对同一 event 可能有不同 payload 假设
- ⚠️ 错误处理策略——没有统一的错误处理模式，AI agent 各自决定

### 5.3 多 AI agent 并行开发风险矩阵

## 8. 结论

V3 Agent 中台文档体系在"防 AI agent 越界"方面设计成熟——owned files、契约冻结、禁止事项清单等机制有效地约束了 AI 的行为空间。但在"告诉 AI agent 精确做什么"方面，当前文档的精确度不足，主要体现在：

- **契约精确度**：SSE event payload 和 API 请求/响应只有名称，没有 Schema
- **数据精确度**：表结构只有字段名，没有类型和约束
- **协作精确度**：并行冲突处理流程和共享文件仲裁规则空白

这些问题在人类开发者为主力的开发模式下可以通过口头沟通解决，但在 AI Native 多 Agent 并行开发模式下，会成为理解分歧、集成失败和返工的主要来源。

**关键建议**：在 POC-1 启动前优先完成第一阶段的 6 个阻断修复项。在 POC-2 启动前必须完成第二阶段的 6 个增强项（尤其是 F7-F10）。第三阶段的改善项可在各 POC 阶段之间穿插完成。

当前文档体系作为 **L0-L2 验收等级**（文档检查 → 单元测试 → 模块集成）的 AI Native 开发基础是合格的。但要支撑 **L3-L5**（API/SSE E2E → Playwright → 真实链路）的 AI Native 开发，还需要补上契约形式化和协作机制两个关键缺口。
