# 测试策略与真实 E2E

## 1. 总体原则

本文是 V3 测试策略和验收等级的全局候选基线。真实开发时，小工程必须在自己的测试策略文档中抽取当前验收范围；未进入当前小工程的场景不作为该工程门禁。

- 单元测试可以使用 mock，但不能作为核心链路完成证明。
- API/SSE E2E 验证协议和服务链路。
- Playwright UI E2E 验证用户体验，不可被 API E2E 替代。
- `e2e-real` 在具备 `.env` 时验证真实 LLM + AgentScope + PostgreSQL + SSE + 前端链路。
- 所有 E2E 数据必须带 `testRunId`，避免相互污染。

## 2. 验收等级 L0-L5

```text
L0 文档/静态检查：格式、链接、规则完整。
L1 单元测试：DTO、Schema、状态机、映射、策略和模块内部逻辑可验证。
L2 模块集成测试：数据库、runtime stub、SSE buffer、权限 gate、依赖方向等可验证。
L3 API/SSE E2E：真实服务协议、错误码、SSE sequence 和恢复链路可验证。
L4 Playwright UI E2E：真实页面操作、用户体验和前端状态可验证。
L5 e2e-real：真实 LLM、AgentScope、PostgreSQL、SSE、前端全链路可验证。
```

每个 AI 任务必须声明目标验收等级。未达到目标等级不能标记完成。

## 3. 单元测试

覆盖：

- 领域状态机。
- Capability gate。
- 权限 Specification。
- RuntimeEvent 映射。
- Stream sequence 和 checkpoint 策略。
- Task/Workflow 状态流转。

要求：

- 测试名描述行为，例如 `shouldReturnSessionBusyWhenSameSessionStreamsConcurrently`。
- mock 只能证明局部逻辑，不能替代 E2E。

## 4. 集成测试

建议使用 Testcontainers PostgreSQL 覆盖：

- MyBatis CRUD。
- R2DBC checkpoint / final flush。
- MyBatis 读取 R2DBC 写入后的历史结果。
- Flyway 迁移。
- 权限和审计写入。

## 5. API/SSE E2E

覆盖：

- 新建会话。
- 发送消息。
- SSE 接收 `run.started`、`assistant.delta`、`run.completed`。
- 停止生成。
- 重新生成。
- 编辑重发。
- Session busy。
- Agent 未授权。
- Capability 未审核。
- 任务中心查询任务成果。仅后续 `task-center` 小工程要求。
- 工作流顺序执行。仅后续 `workflow-sequential` 小工程要求。

验收：

- SSE sequence 单调递增。
- 最终消息落库。
- Run/Span 可查询。
- 错误码符合契约。

## 6. Playwright UI E2E

Playwright 用于验证页面真实操作，不是 API 测试包装。

必须覆盖：

- 打开 Chat 页面。
- 选择 Agent。
- 新建会话。
- 输入消息并发送。
- 页面看到流式输出。
- 停止生成。
- 编辑历史消息并重发。
- 查看执行详情。
- 进入任务中心查看成果。仅后续 `task-center` 小工程要求。
- 管理端配置 Agent、Provider、Capability 的基础流程。仅后续 `admin-config` 小工程要求。

要求：

- 页面使用稳定 `data-testid`。
- 测试不能通过直接调用后端 API 替代页面点击、输入、等待。
- E2E 失败产物保存 screenshot、video、trace。

`data-testid` 命名规范：

- 使用 kebab-case。
- 页面级前缀使用 `chat-`、`sessions-`、`agents-`、`executions-`、`admin-`、`tasks-`、`workflows-`。
- 动态元素使用稳定业务 ID 或测试 ID 后缀，例如 `chat-message-{messageId}`、`sessions-row-{sessionId}`。
- 动态后缀必须先做字符清洗，只保留小写字母、数字和 `-`。
- 不使用会随文案、排序或 CSS 变化的选择器作为核心断言。

Playwright 基线：

- `baseURL` 必须来自环境变量或 Playwright config，不在测试中硬编码。
- 失败时保留 trace、screenshot 和 video；成功用例可按 CI 成本选择保留策略。
- UI E2E 使用测试用户 fixture 登录或注入 POC mock token，不复用人工本地登录态。
- 每个 E2E run 生成唯一 `testRunId`，通过请求 header、fixture 或公开 API 写入后端测试数据。
- 对流式输出的断言必须等待真实页面状态变化，不能只等待固定 sleep。
- 核心链路默认允许少量 retry，但 retry 后仍失败必须保留第一次失败证据。

## 7. e2e-real

`e2e-real` 只在 `.env` 配置完整时运行。

验证：

- 真实 LLM。
- 真实 AgentScope ReActAgent。
- 真实 PostgreSQL。
- 真实 SSE。
- 真实前端页面。

如果 `.env` 不存在，可以跳过，但最终交付必须说明未运行原因。

## 8. 测试数据初始化

所有 E2E 必须创建独立测试数据：

```text
testRunId
testUser
testAgent
testSession
testTask
testWorkflow
```

初始化方式：

- 优先通过公开 API 或测试 fixture。
- 不依赖人工预置的本地脏数据。
- 不读取或输出 `.env` 密钥。
- 需要持久化清理的数据优先写入显式 `test_run_id` 列；无法新增列时才使用 `metadata.testRunId`。
- 测试用户、默认 Agent、Provider / Model、Capability seed 必须可重复创建或幂等更新。

## 9. 测试数据清理

清理策略：

- 所有 E2E 数据必须带 `testRunId`。
- 测试结束按 `testRunId` 清理。
- 清理失败必须记录，不能静默吞掉。
- 不允许清理不带 `testRunId` 的真实数据。

## 10. 推荐命令

以下命令只有在对应源码目录创建、依赖安装完成、任务单声明可执行后才作为门禁；工程尚未创建时不得伪造验证结果。

后端：

```bash
mvn test
mvn verify
mvn -P integration verify
mvn -P e2e-real verify
```

前端：

```bash
npm run lint
npm run typecheck
npm run test
npm run build
npm run e2e
npm run e2e:real
```

实际命令以项目脚本为准，AI agent 最终汇报必须写清楚执行过哪些命令。

## 11. CI 质量门禁

quick：

- 格式检查。
- 单元测试。
- 类型检查。
- 架构依赖检查。

integration：

- Testcontainers PostgreSQL。
- MyBatis / R2DBC 集成。
- runtime stub 集成。

ui-e2e：

- 启动后端和前端。
- Playwright 操作真实页面。

e2e-real：

- 需要 `.env`。
- 可作为人工触发或夜间任务。

阻断合并条件：

- 编译失败。
- 架构依赖违规。
- 契约测试失败。
- 安全测试失败。
- 核心 E2E 失败。
- AI agent 未报告验证命令。
