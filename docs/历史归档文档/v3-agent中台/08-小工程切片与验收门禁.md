# V3 小工程切片与验收门禁

## 1. 定位

V3 总蓝图保持为企业内部 Agent 中台的长期方向，但真实交付不再按完整产品一次性冻结和评审。后续采用“小工程切片”推进：每个小工程都有独立范围、契约切片、任务包、验收等级和人工评审口径。

`03-API-SSE-运行时契约-全局基线.md`、`04-数据模型与安全审计-全局基线.md` 是全局候选基线。小工程只冻结自己实际使用的契约切片；未进入当前小工程的能力不阻塞实现和评审。

## 2. 小工程原则

- 一个小工程必须能独立交付、独立验收、独立回滚。
- 每个小工程只冻结自己需要的 API、SSE、RuntimeEvent、数据表、权限和测试。
- 人工评审只审当前小工程，不要求一次性确认完整 V3 产品形态。
- 新小工程启动前，应先从全局候选基线抽取本工程的 contract slice。
- 小工程按可验收业务闭环拆分，不按 AI 子 Agent 角色或单一技术模块拆分。
- 小工程内部的阶段和任务包可以按多 Agent 并行范式拆分，但必须保证 owned files 可隔离、公共契约已冻结、最终能回到同一个可运行闭环。
- 小工程内仍遵守 AI Native 任务单、owned files、验证命令和 L0-L5 验收等级。
- 小工程之间共享的公共契约变更必须回写全局候选基线，并更新 RTK。

## 3. 小工程与多 Agent 并行范式

V3 拆分层级：

```text
V3 大工程
 -> 小工程：按业务可验收闭环拆分
 -> 阶段 / 任务包：按交付阶段和多 Agent 并行边界拆分
 -> 子 Agent：按 owned modules / owned files 执行
```

小工程必须是纵向闭环，例如 Chat、Admin 配置、任务中心、顺序工作流。它必须能被业务或技术负责人独立评审、独立验收、独立回滚。

任务包可以是横向技术切片，例如 runtime、repo、biz、frontend、e2e，但它必须隶属于某个小工程，并服务该小工程的同一个 contract slice。

不建议把小工程拆成以下形态：

- `runtime-agent 工程`
- `frontend-agent 工程`
- `repo-agent 工程`
- `biz-agent 工程`

这类拆法只方便并行写代码，但缺少用户可验收闭环，容易把人工评审重新拉回模块级细节。

### 3.1 并行开发就绪门禁

一个小工程进入多 Agent 并行开发前，必须满足：

- 本小工程 `02-工程契约切片.md` 已冻结当前阶段 API、SSE、RuntimeEvent、数据、权限、错误码和验收等级。
- 本小工程 `03-工程技术设计.md` 已明确激活模块、主链路、依赖方向和暂缓技术项。
- 任务包 `task.md` 已列出子 Agent 分工、owned modules、owned files、禁止修改范围和验证命令。
- 并行子 Agent 的 owned files 尽量互斥；确实共享的公共 DTO、SPI、迁移脚本或测试夹具必须指定唯一 owner。
- 公共契约只允许 contract owner、主 Agent 或 Review Agent 汇总回写；其他子 Agent 的细化先写入任务目录 `contract-notes.md`。
- E2E / Review 子 Agent 默认只验证和复核，不顺手改业务实现；如需修改，必须先补充 owned files。

### 3.2 推荐并行角色

小工程内可按任务包裁剪以下角色，不要求每个任务都启用全部角色：

| 角色 | 典型 owned modules / files | 主要职责 |
| --- | --- | --- |
| contract-agent | `agent-api`、`runtime-spi`、`contract-notes.md` | DTO、SSE、RuntimeEvent、错误码和兼容规则 |
| domain-agent | `agent-domain` | 领域对象、状态、值对象和领域约束 |
| runtime-agent | `agent-runtimes/*` | AgentScope / sandbox / 外部 runtime 适配 |
| repo-agent | `agent-repo/*`、Flyway | Repository port、MyBatis、R2DBC、迁移脚本 |
| biz-agent | `agent-biz/*` | 小工程主业务流程和权限编排 |
| frontend-agent | `source/v3-agent-platform-ui` | 页面、组件、SSE client、状态管理 |
| e2e-agent | API/SSE E2E、Playwright、`e2e-real` | 真实链路验证和测试数据隔离 |
| review-agent | 任务报告、owned files、契约和安全复核 | 独立评审，不接管业务实现 |

## 4. 小工程拆分

| Epic | 名称 | 目标 | 不做 | 目标验收 |
| --- | --- | --- | --- | --- |
| EPIC-V3-A | chat-minimal | 跑通业务老师选择 Agent、创建 Session、发送消息、接收 SSE、落库 Message/Run/Span 的最小闭环 | 不做 Admin UI、任务中心、工作流、外部复杂 Agent、高风险沙箱真实执行 | L5 |
| EPIC-V3-B | admin-config | 管理员配置 Agent、Provider、Capability，并让业务老师只能使用被授权 Agent 和能力 | 不做复杂工作流和任务成果中心 | L4-L5 |
| EPIC-V3-C | task-center | 从任务模板发起任务，查看任务状态和成果，关联 Session/Run/Trace | 不做工作流编排和外部复杂 Agent 真实调用 | L4 |
| EPIC-V3-D | workflow-sequential | 管理员配置顺序工作流，业务老师执行并查看步骤进度 | 不做 DAG、并行节点、人工审批、定时触发 | L4-L5 |
| EPIC-V3-E | external-agent | 登记外部复杂 Agent，完成 stub 调用、授权、审计和观测 | 不默认替代 AgentScope 普通 Chat 路径 | L3-L4 |
| EPIC-V3-F | hardening-ci | 补齐 CI、真实 E2E、审计查询、失败恢复和发布门禁 | 不新增业务能力 | L4-L5 |
| EPIC-V3-G | input-ocr | 支持独立图片、扫描页和上传文件内嵌图片，通过受控 OCR / input-preprocessor 生成派生上下文，让非多模态主模型也能理解图片信息 | 不要求主对话模型多模态，不做真实业务副作用动作 | L4-L5 |

## 6. 文档维护边界

- `08-小工程切片与验收门禁.md` 只维护小工程拆分原则、Epic 列表、并行开发门禁和已启动小工程索引。
- 具体小工程的范围、契约切片、技术设计、测试策略、路线图、阶段任务和暂缓范围只写入 `工程迭代/<小工程>/`。
- 任务状态、任务编号、知识依据和跨文档追踪只写入 `RTK.md`。
- 小工程任务执行记录、局部契约草案、测试报告和交接证据只写入该小工程 `ai-tasks/`。
- 如果本文和具体小工程文档出现冲突，以具体小工程文档作为当前实现和验收权威；本文只修正治理规则或索引。
