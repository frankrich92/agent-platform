# 工程技术设计

## 0. 设计参考落地规则

`chat-minimal` 的工程设计不是从零自研 Agent 运行协议。API、SSE、Runtime SPI、DTO、数据模型、表结构和状态枚举必须优先对照 `02-工程契约切片.md` 中的固定参考基线，并在任务目录 `contract-notes.md` 中记录实际采用的 API / 模型依据。

POC-1 任务落地要求：

- `TASK-V3-011 agent-domain 契约`：记录 AgentScope `Msg` / `MsgRole`、AgentScope Runtime `Message` / `Session` 与 V3 领域对象之间的字段取舍。
- `TASK-V3-012 runtime-spi 契约`：记录 `StreamableAgent.stream(...)`、`StreamOptions`、`EventType`、`AgentRequest`、`Event`、`AgentHandler.streamQuery(...)` 与 V3 Runtime SPI 的映射关系。
- `TASK-V3-013 repo-spi 契约`：记录 AgentScope `MysqlSession` 增量状态存储、V3 数据切片和本地历史 Flyway 表结构对仓储端口的影响。
- `TASK-V3-015 agent-api 契约`：记录 V3 API/SSE 切片、历史 `StreamEnvelope`、历史前端 `streamRequest(...)` 与 V3 DTO / SSE envelope 的字段取舍。

## 2. 主链路

```text
前端 Chat
 -> agent-boot
 -> biz-chat
 -> platform-security / platform-capability
 -> platform-provider
 -> runtime-agentscope
 -> AgentScope Java ReActAgent
 -> RuntimeEvent
 -> platform-stream
 -> SSE
 -> R2DBC checkpoint/final flush（PostgreSQL `agent_message_checkpoint`）
 -> repo-mybatis 历史查询（普通 CRUD / 历史读取已收敛到 MyBatis-Plus Mapper）
 -> platform-observability Run/Span/Audit
 -> biz-execution 执行详情查询
```

## 3. 实现边界

- `biz-chat` 负责编排业务流程，不直接拼装 AgentScope 对象。
- `biz-execution` 负责 `GET /api/executions/{runId}` 的 Run / Span / ToolCall 读取和脱敏展示，不发起新的 runtime 执行。
- `runtime-agentscope` 只接收过滤后的 `RuntimeCapabilityPlan`。
- `platform-stream` 负责 RuntimeEvent 到 SSE envelope 的映射。
- `repo-r2dbc-stream` 目标只处理 checkpoint / final flush；当前 POC-2 已用 R2DBC 写入 PostgreSQL checkpoint，后续可继续拆成独立 adapter。
- `repo-mybatis` 负责普通 CRUD 和历史查询；当前 POC-2 已使用 MyBatis-Plus Mapper 接入 PostgreSQL，保留内存仓储作为无 DB 环境下的本地验收替代。
- `platform-observability` 负责 Run / Span / Audit 的观测模型、脱敏摘要和执行详情支撑；本工程不单独拆 `platform-audit` 模块。
- 工具调用必须来自 AgentScope runtime 事件，不允许平台关键词触发。

### 3.1 关键假设与风险

- 基础依赖兼容性：`TASK-V3-010` 必须验证 Spring Boot 4.0.6、Java 21、Maven 4 RC、MyBatis-Plus、R2DBC、Flyway 和 Testcontainers 的最低兼容性；失败时按 ADR-0003 新增 supersede ADR，不静默降级。
- AgentScope API 稳定性：`runtime-agentscope` 默认参考 AgentScope Java `13a71676`；若 POC-2 前 `StreamableAgent`、`StreamOptions`、`EventType` 或 `Msg` API 变化，必须先更新 `02-工程契约切片.md` 和对应 `contract-notes.md`。
- 部署假设：POC 阶段按单节点部署验证，SSE 断线恢复依赖持久化 checkpoint，不依赖进程内缓存；多节点 sticky session、消息队列或分布式 stream fan-out 留到后续 hardening 小工程。
- Tool calling 假设：普通文本 Chat 是 L5 必选链路，工具调用是条件链路；只有任务单启用 tool path 时才强制 provider 支持 tool calling。

## 4. 前端范围

```text
/chat
/sessions
/agents
/executions/:runId
```

前端技术栈：

- Vue 3。
- TypeScript。
- Pinia。
- Vite。
- Vue Router 4。
- Element Plus。
- API client 使用 fetch wrapper。
- SSE client 使用 `fetch` + `ReadableStream` + `AbortController`，支持 `Authorization`、`Last-Event-ID` 和主动取消。
- UI E2E 使用稳定 `data-testid`，命名规则遵循 `05-测试策略与验收等级-全局基线.md`。

最小组件：

- 会话列表。
- Agent 选择。
- 消息流。
- 输入框。
- 停止 / 重新生成 / 编辑重发。
- 执行详情面板。

## 5. 最小身份链路

POC 阶段不实现完整登录系统，先通过本地 / 测试身份过滤器生成 `UserContext`：

```text
Authorization: Bearer <test-token>
 -> agent-boot auth filter
 -> platform-security UserContext
 -> biz-agent / biz-session / biz-chat 授权校验
```

约束：

- HTTP API 和 SSE stream 使用同一身份来源。
- 前端请求统一通过 fetch wrapper 注入 `Authorization`。
- Playwright 和 API/SSE E2E 使用测试 fixture 提供 token 和 `testRunId`。
- 生产登录、刷新 token、角色管理和 SSO 留到后续 Admin / Security 小工程。
