### 2.3 02-工程契约切片.md

**结论：通过，3 个问题（1 个阻塞、2 个建议）。**

**B-01（阻塞）**：§2 API 切片中 `POST /api/chat/send` 返回值未明确。当前只约束了请求端（只接收文本 message、attachments 必须为空），但没有定义成功时的响应结构。对于 SSE 流式场景，`POST /api/chat/send` 应返回什么？两种常见模式：

- (a) 同步返回 `runId` + `messageId`，客户端再通过 `GET /api/chat/{runId}/stream` 建立 SSE 连接。
- (b) 直接升级为 SSE 连接（历史 V2 使用的模式，已被标注为"不沿用"）。

`02-工程契约切片.md` §8 已明确 `GET /api/chat/{runId}/stream` 负责建立 SSE 连接，且 `03-工程技术设计.md` §2 主链路也是先 send 后 stream 的两步模式。但 §2 本身没有写出 `POST /api/chat/send` 的成功响应体。建议补充明确：成功时返回 `201` + `{ runId, messageId, sessionId }`（或等价结构），并注明客户端随后应通过 `GET /api/chat/{runId}/stream` 接收事件。

**S-03（建议）**：§3 SSE Event 切片列出了 14 种事件，但没有标注哪些事件是 `chat-minimal` POC-2 必须实现的，哪些是可选 / 可降级的。例如 `tool.call.*` 系列：如果 POC-2 选择的 LLM provider 不支持 tool calling（`04-工程测试策略与真实E2E.md` §6 明确写了"工具调用能力在 chat-minimal 中不是 L5 必选项"），那么 `tool.call.started / delta / done / failed` 是否可以跳过？建议对每个事件标注 `[required]` 或 `[conditional]`。

**S-04（建议）**：§5 数据切片中 `agent_message` 的 `content` 字段语义未明确区分 role=user 和 role=assistant 场景。对于 role=assistant，`content` 是最终完整正文还是只存 delta 聚合后的结果？§8 和 checkpoint 语义中提到 `accumulated_content` 保存累计快照，但 `agent_message.content` 和 `agent_message_checkpoint.accumulated_content` 之间的关系没有说清。建议补充一段说明：`agent_message.content` 在 run 进行中是否更新、final flush 时是否从 checkpoint 回写、还是只在 run 完成时一次性写入。

### 2.5 04-工程测试策略与真实E2E.md

**结论：通过，2 个问题（0 阻塞、2 建议）。**

**S-07（建议）**：§3 L2 验收中"建议命令"使用 `mvn -P integration verify`，而 §2 L1 使用 `mvn test`。建议明确说明 `integration` profile 在 POC-1 是否一定存在、是否在骨架创建时同步建立。如果 POC-1 只创建骨架不建立 integration profile，此处的命令会给验证者造成困惑。

**S-08（建议）**：§7 数据隔离中"测试用户、默认 Agent、Provider / Model、Capability seed 优先通过公开 API 或测试 fixture 幂等创建；POC-1/POC-2 尚无 API 时可使用 Flyway seed 或测试初始化脚本"。这条比较务实，但"POC-1/POC-2 尚无 API 时"的判定标准不清晰。建议补充：由哪个任务负责判断"API 是否可用"并决定使用 Flyway seed 还是 API 创建测试数据。

### 2.6 05-工程路线图与任务.md

**结论：通过，1 个阻塞、1 个建议。**

**B-02（阻塞）**：§6 POC-2 任务中 `TASK-V3-020` 至 `TASK-V3-024` 尚未创建任务包目录，但 `05-工程路线图与任务.md` 已列出了子 Agent 分工表（runtime-agent / capability-agent / biz-agent / stream-repo-agent / frontend-agent / e2e-agent / review-agent）。然而 §6 同时写着"创建前必须先复核 02-工程契约切片.md 是否仍满足当前实现范围"。

问题：子 Agent 分工表中的 `owned modules / files` 范围是否已在 POC-0 / POC-1 评审中确认？如果尚未确认，这张表在 POC-2 任务包创建时可能需要调整。当前表中 `biz-agent` 同时拥有 `biz-chat`、`biz-session`、`biz-agent`、`biz-execution` 四个子模块，范围较大；如果 POC-2 发现需要进一步拆分，会影响并行策略。

建议：在 POC-2 任务包创建时，先由一个 review-agent 冻结子 Agent 分工表，再并行启动。当前文档中可以加一句"POC-2 子 Agent 分工表为候选方案，以 POC-2 任务包创建时冻结版本为准"。

**S-09（建议）**：§9 阶段切换规则中"POC-2 未达到 L5 前，不启动 Admin 完整治理、任务中心、工作流、外部复杂 Agent 或 input-ocr 小工程"。这条规则很严格，但 L5 依赖 `.env` 和真实 LLM 可用性。如果 `.env` 存在但 LLM provider 配额耗尽或暂时不可用，按 `04-工程测试策略与真实E2E.md` §6 降级口径应该报告 L5 failed / degraded。但阶段切换规则没有给出"L5 degraded 时是否可以启动后续小工程"的判断标准。建议补充降级情况下的推进口径。

## 5. 人工评审重点建议

基于以上评审，建议人工评审时聚焦以下几点：

1. **B-01（阻塞）**：确认 `POST /api/chat/send` 的响应模式。这是 send + stream 两步模型还是直接升级 SSE？当前文档内部暗示是两步模型，但缺少显式定义。
2. **B-02（阻塞）**：确认 POC-2 子 Agent 分工表的约束力。是否需要在 POC-2 冻结前由 review-agent 重新确认？
3. **S-04**：确认 `agent_message.content` 与 `agent_message_checkpoint.accumulated_content` 的关系。这直接影响 POC-2 中 `repo-r2dbc-stream` 和 `repo-mybatis` 的实现策略。
4. **S-09**：确认 L5 degraded 时的推进口径。如果真实 LLM 长期不可用，`chat-minimal` 是否可以基于 L4 通过推进后续小工程？
