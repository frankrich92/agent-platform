# 产品蓝图与体验目标

## 1. 产品定位

HTAM Agent Platform 的 V3 目标是企业内部 Agent 中台。

它不是单一 Chat 应用，也不是简单的大模型代理，而是统一管理 Agent、模型、MCP、Skills、Tool、记忆、权限、审计、任务成果和运行观测能力的平台。

V3 的第一落点是 Web Chat 工作台和后台管理，但产品边界应面向中台能力设计：

- Agent 库：沉淀可复用 Agent 定义、版本、状态、标签、能力边界和可见范围。
- Agent 配置：管理员尽可能通过界面配置出通用 Agent，不为每个常规场景新增代码。
- Agent 工作流：管理员可以把多个已有 Agent 编排成业务流程，复用而不是复制能力。
- 任务中心：业务老师从任务模板、Agent、Chat 或工作流发起任务，并看到状态、过程和成果。
- 能力治理：统一管理 MCP、Skills、Tool 的注册、审核、风险等级、授权、启停和审计。
- 输入理解：预留文档、表格、图片等多源输入的受控预处理能力，主对话模型不强制要求多模态。
- 执行观测：统一记录 Run/Span、SSE、工具调用、错误、耗时、traceId 和审计线索。
- 业务接入：未来可通过受控 API、SDK 或组件把 Agent 能力输出给业务系统。

## 2. 目标用户

业务老师：

- 按业务域、业务场景、任务意图、交付物等标签选择 Agent。
- 使用被授权 Agent 或工作流完成资料整理、规则判断、内容生成、风险初筛、运营分析等任务。
- 看到任务进度和可验收成果，而不是只看到一段聊天回复。

Agent 管理员：

- 通过后台创建、复制、编辑、审核、发布、下架 Agent。
- 配置模型、系统提示词、MCP、Skills、Tool、记忆策略、标签和授权范围。
- 登记外部复杂 Agent，配置输入输出契约、风险等级、负责人和可用范围。
- 配置任务模板和 Agent 工作流。

平台管理员：

- 管理用户、角色、权限、菜单、功能开关、系统参数和审计。

平台开发者：

- 扩展 runtime、repo、capability、provider、stream、observability 等平台能力。
- 通过 Run/Span、traceId、工具调用过程和 E2E 产物定位问题。

业务系统开发者：

- 后续通过受控 API、SDK 或组件复用中台 Agent 能力。

## 3. Agent 库、标签与类型分层

Agent 是中台可复用资产，不应只属于一个业务域、一个页面或一个固定场景。V3 通过 Agent 库统一沉淀 Agent 定义、版本、状态、负责人、标签、能力边界和可见范围。

标签用于检索、筛选、推荐和展示，不直接表达权限、运行风险或实际能力授权。V3 采用维度化标签，避免把所有分类语义堆进一组扁平标签：

- 业务域：合同、财务、客服、运营、知识、文档、通用办公等。
- 业务场景：初审、对比、合规检查、报告生成、回复建议、运营分析等。
- 任务意图：摘要、判断、生成、提取、复核、编排等。
- 交付物：报告、清单、表格、结构化 JSON、审核意见、回复草稿等。
- 输入上下文：会话、文档、表格、图片、外部只读 API、记忆等。
- 技术能力摘要：MCP、Skill、Tool、OCR / 输入预处理、外部 Agent、沙箱执行等，只作为展示和筛选摘要。
- 适用对象：业务老师、法务专员、财务专员、运营人员、管理员等，只表达推荐人群。

同一个 Agent 可以绑定多个维度的标签，并跨业务域复用。例如“付款条款 Agent”可以同时服务合同初审、付款审核、费用合规等流程。

标签治理边界：

- 可见范围和用户授权以 `visibility_scope`、`agent_user_grant` 和角色权限为准，不由标签决定。
- 实际 MCP / Skill / Tool 能力以 `agent_capability_binding` 和 Capability gate 为准，技术能力标签只做展示摘要。
- 高危脚本、沙箱路由和禁用原因以运行时风险判定为准，不由标签决定。
- `agent_type`、`status`、`audit_status`、`riskLevel` 不作为普通标签，避免筛选标签和治理状态混淆。
- 每个正式发布 Agent 至少应声明一个业务域或通用域、一个任务意图；其他维度按实际用途补充。

V3 目标不是“不开发 Agent”，而是把 Agent 按构建和接入方式分层：

通用配置 Agent：

- 优先通过后台界面配置。
- 通过系统提示词、模型、能力包、记忆策略、标签和输出边界组合形成。
- 默认走 `agentscope-java` 的 `ReActAgent`。
- 挂载能力必须经过平台审核、授权和风险 gate。
- 如果本次运行需要执行高危脚本或系统级工具，例如 Shell、Python、Browser 自动化、文件写入，则必须由 Capability gate 判定进入 `runtime-sandbox` 或直接拒绝。

外部复杂 Agent：

- 用于复杂工具编排、强业务判断、专用系统交互、多步骤专业流程等场景。
- 可以是外部 Agent API、内部服务或后续 runtime adapter。
- 不绕过平台治理，必须登记到 Agent 库，并纳入授权、审计、Run/Span、任务成果和工作流节点。
- 是否走沙箱不由“通用 Agent / 外部复杂 Agent”类型决定，而由本次执行是否触发高危脚本或高风险工具决定。

Runtime 与风险判定原则：

- 普通对话、低风险工具调用和外部复杂 Agent 的受控 API 调用，可以走普通 runtime 或外部 adapter。
- 高危脚本执行、浏览器自动化、文件写入、系统命令等系统级动作，必须走 `runtime-sandbox` 或被禁用。
- 发邮件、改业务数据、提交审批、触发支付、写 CRM / 工单 / 外部业务系统等真实业务副作用动作不进入 V3 当前范围，后续作为独立优化项设计。
- 平台不能因为 Agent 是“通用配置 Agent”就允许高危脚本进入普通 `ReActAgent`，也不能因为 Agent 是“外部复杂 Agent”就默认要求走沙箱。

图片型输入与 OCR 预留：

- V3 长期需要支持业务老师在 Agent 对话中提交图片型输入，包括独立图片、截图、扫描页，以及 PDF / Word / PPT / Excel 等上传文件中的内嵌图片。
- 主对话模型不强制要求多模态；当内部主模型是非多模态模型时，可以通过受控 OCR / vision preprocessor 先把图片解析为文本或结构化派生上下文，再进入 Agent 对话上下文。
- `glm-ocr` 这类小模型只作为可配置的 OCR provider / model 示例，不在产品蓝图中硬编码厂商或模型。
- OCR 能力必须和 MCP、Skill、Tool 一样纳入 Capability gate、授权、审计、限流和失败可观测，不允许前端或业务服务绕过平台直接调用。
- 图片原件、包含图片的上传文件、文件内嵌图片、OCR 文本和结构化识别结果都属于用户输入数据，应按用户归属、会话归属、脱敏和保留策略治理。
- 该能力是后续独立小工程预留，不进入 `chat-minimal` 当前实现和人工验收范围。

## 4. 核心页面体验

业务侧页面：

```text
/chat                 Chat 工作台
/sessions             会话列表和搜索
/agents               Agent 库
/agents/:agentId      Agent 详情
/tasks                任务中心
/tasks/:taskRunId     任务详情和成果
/workflows            可用工作流列表
/executions/:runId    执行详情
```

管理侧页面：

```text
/admin/iam
/admin/agents
/admin/tasks
/admin/workflows
/admin/capabilities
/admin/providers
/admin/system
/admin/audit
```

首屏应是可用工作台或业务入口，不做营销式首页。

## 5. Chat 工作台体验

Chat 工作台是 V3 第一个落地应用，用于验证中台能力是否真实可用。

必须包含：

- 左侧会话列表。
- Agent 选择或当前 Agent 信息。
- 中间消息区。
- 底部输入区。
- 发送、停止、重新生成、编辑重发。
- 当前模型、能力摘要、运行状态。
- 执行详情面板。

体验要求：

- 流式输出必须持续增量展示。
- thinking 与最终回复应能分区展示。
- 工具调用以过程块展示，普通用户不展示敏感参数。
- 刷新页面后能恢复会话、消息和运行状态。
- 未授权能力不会出现在当前 Agent 能力摘要中。
- 后续支持图片型输入时，用户应能看到附件处理状态、OCR 失败原因和进入对话的派生上下文摘要。

## 6. 任务中心与成果体验

任务中心是 V3 从“聊天工具”走向“Agent 中台”的产品承接层。

任务来源：

- Chat 会话。
- 任务模板。
- Agent 详情页。
- Agent 工作流。
- 外部复杂 Agent。

任务中心应展示：

- 任务标题。
- 来源类型。
- 使用的 Agent / Workflow。
- 状态：queued、running、waiting、completed、failed、cancelled。
- 进度摘要。
- 最终成果。
- 关联 `sessionId`、`runId`、`workflowRunId`、`traceId`。

V3 最小闭环：

- 业务老师能从任务模板发起任务。
- 任务执行后能看到状态和成果。
- 工作流执行后能看到步骤进度。
- 失败任务能看到安全脱敏后的失败原因。

## 7. Agent 工作流

Agent 工作流用于复用多个已有 Agent 完成业务任务，不是替代 Agent 库。

V3 基线：

- 管理员通过后台配置工作流。
- V3 最小闭环先支持顺序编排。
- 每个节点调用一个已有 Agent。
- 节点仍走 Agent 授权、Capability gate、runtime、Run/Span 和审计。
- 已登记的外部复杂 Agent 可以作为受控节点。

暂不做：

- 复杂 DAG。
- 并行节点。
- 人工审批节点。
- 定时触发。
- 外部系统主动触发。

## 8. V3 暂不追求

- 企业级 SSO/OIDC/LDAP。
- 完整多租户组织树。
- 知识库/RAG/向量检索。
- 自动 Skill 创建、自我修复、自主学习闭环。
- MCP 市场和插件市场。
- 桌面级电脑接管、手机远控、多端 Gateway。
- 7x24 长期自主 Agent 或无人值守生产执行。
- 面向外部第三方的生产开放平台。
- 生产级 AgentScope Studio 嵌入。

## 9. 产品验收口径

V3 产品验收至少包括：

- 业务老师能看到被授权 Agent。
- 业务老师能按标签组合选择 Agent 或工作流。
- 业务老师能通过真实 AgentScope ReActAgent 完成流式对话。
- 业务老师能停止生成、重新生成、编辑后重发。
- 任务中心能展示任务来源、执行状态、最终成果和关联执行记录。
- 管理员能配置通用 Agent、Provider、Capability、任务模板和用户授权。
- 管理员能登记外部复杂 Agent，并纳入授权、审计和观测。
- 管理员能把多个已有 Agent 编排成顺序工作流。
- 未授权或未审核能力不会进入运行时。
- 当后续启用图片型输入时，非多模态主模型也能通过已授权 OCR 预处理获得图片文本上下文，且 OCR 过程可审计、可追踪、可失败恢复。
- 高危脚本和高风险工具不会进入普通 `ReActAgent`；是否走沙箱按执行动作风险判断，不按 Agent 类型判断。
- 真实业务副作用动作不进入 V3 当前验收范围。
- Playwright 能通过页面真实操作验证核心路径。
